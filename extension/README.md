# 采购助手（浏览器插件）

采购控制台的浏览器插件：Chrome MV3 + TypeScript + Vite，本机 Chrome 与 AdsPower 浏览器环境都能加载。一个浏览器环境（一个 Chrome 用户，或一个 AdsPower 环境）装一份，**装好就能用**：没有配对码，也不用把浏览器和账号绑在一起。服务端与控制台的安装、启动和整体流程见仓库根目录的 [README](../README.md)。

插件读出这个浏览器当前登录的亚马逊买家号 ID（customerId），按它领任务：控制台里登记了这个买家号 ID 的账号，任何登录着这个买家号的浏览器都能执行它的任务，与哪台电脑、哪个浏览器无关。

**本版本只做模拟执行，不产生真实订单。** 插件领取服务端分给当前买家号、已到采购日期的任务，按任务数据推出一份结算信息交给服务端护栏裁决，再走提交登记与结果上报；它不打开、不点击、不修改任何亚马逊页面。真实下单流程在后续 PR 加入，并且由服务端单独开关。

|能做的|说明|
|---|---|
|自动登记|首次需要时生成一个令牌（只存在插件后台的 IndexedDB 里，亚马逊页面上的内容脚本读不到），向服务端登记这个浏览器；服务端给它起名「浏览器 <编号>」，可以在控制台改名|
|心跳|每分钟一次，带上最新身份；缓存服务端按当前买家号算出的登录状态与账号配置（执行方式、执行时间、额度、今天可执行笔数等）。打开面板、页面回到前台、开始执行前都会马上同步一次|
|买家号识别|亚马逊页面上读登录状态与买家号 ID，多个标签页的读数按页面加载先后对账后上报；服务端答复这个买家号是已登记（可以执行）、还没登记、已忽略，还是没读到|
|结果回执|上报结果之前先存一份回执；服务端重启、断网、插件后台被回收时，服务端恢复后自动补交同一份结果（插件后台启动时、每次心跳成功时立即补交，另有 30 秒一次的退避补交），最多保留 24 小时|
|页面内面板|订单历史页默认展开，其他亚马逊页面右下角是收起的悬浮按钮；需要所有者处理时悬浮按钮上带一句说明|
|模拟执行|手动点「开始执行（模拟）」，或到了控制台配置的执行时间自动开始|

## 构建与测试

需要 Node.js 22（与根目录 README 一致；`npm test` 用到 `node --test` 的通配符与 `mock.timers`，Node 21 以下跑不了）。

```bash
cd extension
npm ci            # 按 package-lock.json 安装依赖
npm run build     # 类型检查 + 构建 → extension/dist（可直接「加载已解压的扩展程序」）
npm test          # 编译纯函数、协议客户端与后台 → Node 单测（node --test）
npm run pack      # 构建并打包 → extension/release/采购助手-<版本>.zip（AdsPower 上传用）
```

`npm test` 覆盖：令牌生成与登记的退避规则、共享单飞闸；协议客户端（登记不带令牌头、心跳与身份上报的新形状、开始批次带买家号 ID 与时间点、错误映射、ACCOUNT_BUSY / DEVICE_BUSY 详情、只对「没说上话」与幂等接口的 5xx 重试、提交登记绝不自动重试、HTTP 200 也校验形状）；身份解析器对着夹具（`test/fixtures/`，虚构数据，含往标题、搜索框、商品标题里植入 `customerId` 的两张）；多标签页对账（基准是进行中批次的买家号 ID，上报带 conflict）；状态文案逐行对照规格的状态文案表；「开始执行」各步的对照表；执行时间换算与按买家号 ID 分键的当天记录；模拟执行引擎对着内存假服务端（`test/fake-server.mjs`，按规格与开发契约实现，边角路径照 `backend/services/` 的答复）的各条路径，含护栏 buyer 项拦下后服务端自己结束批次的那一条（不上报结果、不调用结束批次，之后的请求都得到「批次已结束」）；错误码表的顺序与中文说明；清单权限与源码里不读 Cookie、不上传页面 HTML 的检查；以及**真正的后台模块**对着假 chrome 环境（`test/fake-chrome.mjs`）跑：装好自动登记、退避与重试、401 后用同一个令牌重新登记并把原请求再发一次、特权消息的来源检查、改服务端地址换新令牌、快心跳的条件、开始执行前的对账与上报、执行页面刷新 / 关闭 / 不再答复时接管批次、批次被服务端结束后的收尾、回执补交的时机、定时触发的各种答复。

## 安装到本机 Chrome

1. 构建：`cd extension && npm ci && npm run build`，得到 `extension/dist`。
2. 在 Chrome 地址栏打开 `chrome://extensions`。
3. 打开右上角的「开发者模式」。
4. 点「加载已解压的扩展程序」，选择 `extension/dist` 文件夹（不是 `extension` 本身）。
5. 装好之后不会弹出任何页面，也没有必填的设置：服务端在本机、端口是默认的 8790 时，插件自己连上并登记。要改服务端地址，点工具栏的插件图标 →「打开设置」。

更新代码后重新 `npm run build`，再在 `chrome://extensions` 里点插件卡片上的刷新按钮，并刷新已打开的亚马逊页面（旧页面里的内容脚本已经和新后台断开）。

从 0.1.0 升级：先升级服务端（停服务 → `python cli.py db_init` → 启动），再按上面的办法重新加载插件。旧版配对得到的令牌原样沿用，不用重新登记；旧版插件连新服务端会看到「插件版本过旧」。

## 安装到 AdsPower

**AdsPower 里的具体菜单路径还没有核实过。** 下面的名称是常见叫法，不保证与你的 AdsPower 版本一致，请以客户端里实际看到的为准：

1. `npm run pack`，得到 `extension/release/采购助手-0.2.0.zip`。
2. 在 AdsPower 客户端里找到扩展管理（可能叫「扩展」「应用中心」或「插件」），选择添加自定义 / 本地扩展，上传上面的 zip（客户端要的是文件夹时，选 `extension/dist`）。
3. 把扩展分配给要使用的浏览器环境（可能可以按分组或逐个环境开启）。
4. 打开该环境就可以了：每个环境各自生成令牌、各自登记，不需要逐个环境做任何设置。升级时重新上传新的 zip。

如果 AdsPower 的浏览器允许打开 `chrome://extensions`，也可以按上面 Chrome 的步骤直接「加载已解压的扩展程序」选择 `extension/dist`。插件要求浏览器内核不低于 Chromium 103。

还没有在 AdsPower 里实机核实的几点：环境重置或清除数据后扩展的存储是否保留（不保留的话，这个环境会带着新令牌登记成一个新的「浏览器」，旧的那一行 30 天没有联系后由服务端清理）；环境里能否访问本机的 `http://127.0.0.1:8790`（环境配了代理时，本机地址是否绕过代理）；设置页在环境里能否正常打开。

## 使用步骤

1. 在本机启动服务端（`cd backend && ../.venv/bin/python cli.py serve`，默认 `http://127.0.0.1:8790`；首次安装见根目录 README）。
2. 在要用来采购的浏览器里装上插件（见上）。
3. 在这个浏览器里登录亚马逊买家号，打开订单页（`https://www.amazon.com/gp/css/order-history`）。插件读出买家号 ID 并上报。
4. 这个买家号还没有登记时，面板写「买家号 A… 还没有登记」：到控制台「账号」页，在顶部的待登记列表里点「登记」（确认名称、金额区间、额度）。也可以先在控制台新建账号时直接填买家号 ID。
5. 几秒后面板显示账号与今天可执行的笔数，点「开始执行（模拟）」。

服务端后启动也没关系：插件按 5 / 15 / 60 秒退避自动重试，面板上也有「重试」。

## 连接服务端（自动登记）

- **零设置可用。** 服务端地址缺省 `http://127.0.0.1:8790`；当前版本只支持本机（`http://127.0.0.1:<端口>` 或 `http://localhost:<端口>`），服务端的插件接口也只接受本机对端。
- **令牌由插件生成**：首次需要时用 `crypto.getRandomValues` 取 32 字节、编码成 base64url（43 个字符），连同它所属的服务端地址存在扩展源下的 IndexedDB。它只是会话标识（把批次、尝试、回执归到同一个浏览器），不代表身份；服务端只存它的哈希。
- **登记**：没有登记成功过、或任何接口回 401（服务端不认识这个令牌：换过数据库，或这一行太久没联系被清理了），插件带着**同一个**令牌调 `POST /plugin/v1/register`，成功后把原请求再发一次。同一时刻只发一个登记请求；登记是幂等的，重复登记不会多出一行。
- **登记失败**按 5 / 15 / 60 秒退避；每次心跳闹钟、面板展开、页面回到前台都会再试（受退避约束），点「重试」不等退避。429 按服务端给的 `retry_after_s` 等（没有则 60 秒）。下面几种不自动重试，面板写明原因，处理后点「重试」：

  |提示|原因与处理|
  |---|---|
  |连接失败：系统里有多个工作区……|服务端里不止一个工作区（409 `WORKSPACE_REQUIRED`）。在插件设置的「高级」里填工作区 ID（控制台「设置」页可以查到）并保存|
  |连接失败：插件版本过旧……|服务端要求插件不低于 0.2.0（409 `PLUGIN_OUTDATED`）。重新构建并加载新版插件|
  |连接失败：插件接口只接受本机请求……|服务端的入口闸拒绝了请求（403）：服务端不在本机，或请求经过了代理|
  |连接失败：插件的密钥库写不进去……|浏览器不让扩展用 IndexedDB。这时插件不登记（否则每次唤醒都会带着一个新令牌登记，服务端多出一串浏览器），重新加载插件后再试|

- **改服务端地址**（设置页）：正在执行、上一个批次还在收尾、或有结果回执没送到时拒绝；允许时**换一个新令牌**再向新地址登记，旧令牌绝不发往新地址。已经登记过的浏览器改填另一个工作区 ID 时同样换令牌重新登记。
- **改设置、重新登记只能在插件自己的页面里做。** 后台只接受扩展自己的页面发来的这类消息，亚马逊页面上的内容脚本发来的一律拒绝；`chrome.storage.local` 里的服务端地址被别处改了，后台仍按令牌所属的地址说话，并把设置改回来。
- 控制台「浏览器」页签里的「移除」只是把这一行从列表里收起来：这个浏览器再次联系服务端时自动回到列表，还是原来那一行。

## 买家号识别与状态

- 登录状态从导航栏读（落在 `/ap/signin`、有没有「Sign Out」节点、账户入口指向哪）；**买家号 ID 只从内联脚本的文本里读**（`script:not([src])` 里 `customerId: "A…"`、`customerId: 'A…'` 以及键上带引号的写法），所有形状合格的匹配必须是同一个值，否则当作没读到。不扫标题、属性、正文：搜索词会被回显进标题与搜索框，商品标题是卖家写的。
- 不是每张亚马逊页面的内联脚本里都有买家号 ID。读不到时面板提示打开订单页；「开始执行」也要求**当前这一页**自己读到了买家号 ID。
- 服务端要求登录状态 10 分钟内上报过（`identity_fresh_s`，默认 600 秒）：开着亚马逊页面时插件每 2 分钟重读一次、每分钟心跳捎带一次；执行中引擎每 3 分钟、以及每次提交登记之前再让所有亚马逊标签页重读并上报一次。
- 面板、弹出页、设置页上买家号 ID 完整显示、可以复制；日志里用遮掩形式（前 4 位 + … + 后 2 位）。

|状态|面板上的说明|按钮|
|---|---|---|
|连不上服务端|连接失败：连不上服务端 <地址>。请确认服务端已启动；地址不同时到设置里修改。插件会自动重试。|重试、打开设置|
|还没有读到登录状态|还没有读到登录状态。打开或刷新亚马逊页面后自动读取。|—|
|未登录|未登录亚马逊。请在这个浏览器登录要用来采购的买家号，登录后这里自动更新。|—|
|已登录，没读到买家号 ID|这一页没有读到买家号 ID。打开订单页后插件会自动读取。|打开订单页|
|标签页读数不一致|这个浏览器的亚马逊标签页显示的买家号不一致。请刷新或关闭较早打开的亚马逊标签页。|重新读取|
|买家号还没有登记|买家号 <ID> 还没有登记。在控制台「账号」页的待登记列表里点「登记」，之后这里自动更新。|复制买家号 ID、打开控制台|
|买家号已忽略|买家号 <ID> 已在控制台忽略，不会分到任务。要使用它，在控制台「账号」页恢复后登记。|复制买家号 ID|
|已登记|账号「<名称>」· 今天可执行 N 笔（另有 M 笔建议采购日期在未来）· 额度 已用 X / 上限 Y。|开始执行（模拟）|
|已登记，采购开关关闭|追加：控制台里这个账号的采购开关是关闭的，不会分到新任务；已分配的任务照常执行。|开始执行（模拟）|
|已登记，已暂停|已暂停执行：<原因>。处理后在控制台「账号」页恢复执行。|开始按钮禁用|
|插件过旧|连接失败：插件版本过旧，请重新构建并加载新版插件。|—|

点了「开始执行（模拟）」之后可能看到的：

|提示|含义|
|---|---|
|开始执行失败：这个买家号正在浏览器「<名称>」里执行（HH:MM 开始）。|同一个账号同时只有一个未结束的批次（409 `ACCOUNT_BUSY`）。时间是北京时间|
|开始执行失败：这个浏览器上一个批次还没有结束。|同一个浏览器同时只有一个未结束的批次（409 `DEVICE_BUSY`），页面刷新或异常退出留下的批次在租约到期后自动释放；后台在替上一个批次补交回执时也是这一句（这时不发请求）|
|开始执行失败：这个买家号还没有登记……|403 `ACCOUNT_NOT_REGISTERED`|
|开始执行失败：浏览器没有登录亚马逊 / 标签页显示的买家号不一致 / 页面上的买家号与插件最近上报的不一致 / 插件超过 10 分钟没有上报登录状态|403 `IDENTITY_MISMATCH`，按服务端的原话|
|浏览器登录的买家号变了，这一笔在提交前中止。|执行中途换了买家号。这一笔没有登记提交，任务回到已分配（不进「异常」），**不暂停账号**，不占额度。服务端从这个浏览器上报的登录状态里发现的（进度返回 `IDENTITY_MISMATCH`）：插件上报中止，之后领不到任务，照常结束批次。护栏从结算事实里发现的（结算页读到的买家号不是这个批次的）：服务端自己把批次结束，面板最后一行是「执行批次 #N 已结束：浏览器登录的买家号变了，这一笔在提交前中止（……）」。登录回原来的买家号后重新开始执行，会再领到这一笔|

「今天可执行 0 笔」时开始按钮不禁用（数字可能是一分钟前的），点了以服务端的答复为准；没有任何已分配任务时写「还没有任务分给这个买家号，可在控制台「待采购」里查看原因」。

「打开订单页」在所有者点击后新开一个标签页到 `https://www.amazon.com/gp/css/order-history`；「打开控制台」新开一个标签页到 服务端地址 + `/accounts`。AdsPower 环境里没有控制台的登录会话，更方便的做法是回到平时用控制台的浏览器里登记。

买家号还没有登记时，插件 10 秒同步一次（自这个状态出现起最多 10 分钟），控制台里一登记，面板几秒内显示账号；其余状态 60 秒一次。

## 页面内面板、弹出页与设置页

- **面板**显示：服务端连接、本浏览器的名称、账号、「模拟模式」标签、执行方式（定时则列出北京时间）、当前模拟结局、上面那张表的状态说明与按钮、当前批次与尝试进度、待补交的结果回执、最近 50 行日志（北京时间）。按钮：「开始执行（模拟）」（买家号已登记时出现）、「重新读取」；执行中变为「停止执行」（当前这一笔结束后停止）。
- 面板挂在封闭的 Shadow DOM 里，亚马逊页面的样式进不来，面板的样式也不影响页面。外观按 EasyQuick 设计系统（青绿主色、圆角、系统字体，跟随系统浅色 / 深色）。
- **弹出页**（点工具栏图标）：一眼看状态，带同样的状态按钮，外加「打开设置」「立即同步」。
- **设置页**只有：服务端地址、状态区（连接、本浏览器名称、当前买家号、账号）与「立即同步」「重新登记」、模拟结局、高级（工作区 ID）。没有配对码、设备名称、浏览器类型。

## 定时执行

- 当前买家号对应的账号执行方式为「定时」时，插件按控制台配置的执行时间（如 `14:00`）设闹钟，**一律按北京时间理解**，与电脑所在时区无关。
- 到点先同步一次心跳（缓存的配置最多一分钟前的，例如刚在控制台恢复执行），再请一个**登着这个买家号**的亚马逊标签页开始定时批次：`POST /runs {customer_id, trigger: "scheduled", slot: "HH:MM", simulated: true}`。标签页登的不是这个买家号、或那一页读不到买家号 ID 时换下一个标签页；一个能用的都没有，日志记一次「等待环境」。
- **「一个时间点一天只执行一次」由服务端保证**：它按（账号、北京日期、时间点）去重，重复时回 `SLOT_DONE`。同一个买家号登录在两个浏览器里，只有一个会真的开始。
- 插件本地的「今天已处理的时间点」**按买家号 ID 分键**，只用来少发请求：同一个浏览器当天先后登录两个买家号，各记各的。
- 到点之后的各种答复：

  |答复|插件怎么办|
  |---|---|
  |已开始|记为处理过|
  |`SLOT_DONE`（这个时间点今天执行过）|记为处理过|
  |账号已暂停执行|记为处理过，今天这次不执行|
  |422（账号改成手动了、时间点删了）|刷新配置，这个时间点记为处理过|
  |`ACCOUNT_BUSY`（这个买家号正在别的浏览器里执行）、`DEVICE_BUSY`（本浏览器上一个批次还没结束）|不记，下一分钟再问|
  |没连上服务端、登录状态对不上、没有能用的亚马逊页面|不记，稍后自动重试|

- 错过的时间点在**同一个北京日期**内补执行一次：电脑开机、浏览器启动、打开亚马逊页面时都会检查；跨过北京时间零点不再补（方案 v2 默认值 4）。今天错过了几个时间点时合成一次，向服务端申请最晚到期的那个。
- 本地记录说「本浏览器还在执行」时，先问执行页面引擎还在不在（页面可能已经刷新）：还在就等它结束再开始；不在了先结束旧批次再开始定时批次。

## 模拟执行做什么

**不产生真实订单。** 插件不打开、不点击、不修改任何亚马逊页面；只有「读结算页」这一步是按任务数据推出来的，服务端的护栏、提交登记、结果处理、额度与状态机全部走真实代码路径。服务端本阶段也拒绝非模拟批次。按开发契约 §5 一步一步走：

1. 当前页重读身份，交后台对账（其余亚马逊标签页也各自重读）；各标签页显示的买家号不一致时不开始。否则先 `POST /identity` 上报，再 `POST /runs {customer_id: 当前页读到的买家号 ID, trigger, simulated: true}` 开始批次（定时触发时另带 `slot`）。服务端按买家号 ID 找账号。本地还有没结束的批次（含后台替它补交回执的那段时间）时不发请求。
2. 循环 `POST /runs/{id}/next` 领取，直到没有任务（`attempt: null`）。候选任务只是暂时被别的操作（导入、同步、分配）锁着时，服务端回 `attempt: null` 且带 `retry_after_s`：插件等这么久（夹在 1 – 30 秒之间）再领，最多再领 6 次，等待期间照常续租，不结束批次；6 次之后仍被占用就以 `completed` 结束本批次。任务是来源（飞书表格或上传的表格）指定给这个账号的、人工改派的还是自动分配的，插件不看也不需要知道：领谁的任务由服务端按登录的买家号决定。来源指定的买家号已经不是这个账号而分配还没重算时，服务端在领取这一步解除分配、跳过那一笔，插件只把服务端给的原因（「N 笔来源指定的买家号已不是本账号、已解除分配」）写进日志。
3. 每一笔：进度（开始、读结算信息）→ 护栏（模拟的结算事实，带着取事实那一刻页面上读到的买家号 ID）→ 上报一次新鲜的身份（`POST /plugin/v1/identity`）→ 登记前最后一次进度确认 → 提交登记（只认 HTTP 200，绝不自动重试）→ 上报结果。
4. `POST /runs/{id}/finish {reason: "finished", detail}` 结束批次（`detail` 是插件的细分原因：completed、stopped、attempt_cap、result_unknown、submit_rejected……，服务端记进批次结束事件的 `plugin_detail`）。护栏的 buyer 项拦下时服务端自己结束批次，插件不调用这一步（见下）。期间按服务端给的租约有效期续租：每 min(35 秒, 有效期 / 3) 一次，每一步之前到点就补一次。

进度返回 `continue=false` 时插件不走护栏与登记，按服务端给的机读原因 `cancel_code` 上报中止，继续下一笔：

|`cancel_code`|含义|插件上报|服务端处理|
|---|---|---|---|
|`UPSTREAM_CANCELLED`|上游已取消|`ABORTED_UPSTREAM_CANCELLED`|尝试中止，任务取消|
|`ACCOUNT_ARCHIVED`、`ACCOUNT_PAUSED`|账号已归档、已暂停执行|`ABORTED_BY_SERVER`|尝试中止，任务回到已分配；不暂停账号，不占额度|
|`IDENTITY_MISMATCH`、`IDENTITY_STALE`|浏览器登录的买家号变了（含退出登录、标签页读数不一致）、超过 10 分钟没有上报登录状态|`ABORTED_BY_SERVER`|同上|
|`SOURCE_HOLD`、`SOURCE_CHANGED`|来源把任务暂停了、领取后来源有变化|`ABORTED_BY_SERVER`|同上，再按来源变化重新定状态（可能进待确认或待核实）|
|`ATTEMPT_FINISHED`|这一笔服务端已经结束了|不再上报|—|

服务端没给 `cancel_code`（旧版本服务端）时只报它认得的 `ABORTED_UPSTREAM_CANCELLED`。日志与 `error_detail` 里写服务端的中文原话。

护栏拦截时这一笔已经由服务端结束，插件按拦截码决定下一步。一般的拦截码（超限价、配送超时、数据不可靠……）：尝试失败、任务「异常」，插件照常上报同一份失败（服务端认出重复），计拦截，继续下一笔。

护栏的 buyer 项把「谁在下单」钉在下单那一页：事实里的买家号 ID 没读到 → 按数据不可靠拦截（`DATA_UNRELIABLE`，一般的拦截）；不是这个批次账号登记的 ID → 拦截（`IDENTITY_MISMATCH`）。后一种不是任务的问题，也不是账号的问题，服务端按中止类落地：

- 尝试记为中止（未登记提交，不占额度），任务回到已分配、保留分配（上游已取消则取消）；**不进「异常」、不暂停账号**。
- **服务端在同一个事务里把批次结束**（结束原因 `identity_mismatch`）：否则只要浏览器上报的登录状态没变，同一批次会马上再领到同一笔。
- 插件写「浏览器登录的买家号变了，这一笔在提交前中止」，**不上报这一笔的结果、不再领取、也不调用结束批次**：服务端都做完了，这个批次之后的领取、批次心跳、结束批次，以及这一笔的进度、护栏、提交登记，一律得到 409 `LEASE_LOST`「执行批次已结束（结算页登录的买家号不是这个批次的买家号），请重新开始批次」（`detail {run_id, end_reason: "identity_mismatch"}`）。本批次以「执行批次 #N 已结束：浏览器登录的买家号变了，这一笔在提交前中止（成功 …，中止 1）」结束，不算中断。
- 重新开始批次马上可以（不用等租约到期），新批次会再领到这一笔。
- 护栏的答复丢了、请求被重发（客户端在没说上话时原样再发，或浏览器在复用的连接上重发）时，拿到的就是上面那个 409：插件同样以「买家号变了」结束，不当成中断。

提交登记被拒（409）时：服务端说已登记（`detail.attempt_status` 为 submitting / verifying，浏览器在连接断开后重发了同一个 POST）→ 上报 `unknown` 并结束批次；按最新配置复核护栏不过（`GUARD_BLOCKED`）→ 按 `detail.block_code` 上报失败（没给时报 `GUARD_BLOCKED`），计拦截，继续下一笔；复核是被 buyer 项拦下的（`detail.block_code = IDENTITY_MISMATCH`，并且 `detail.run_ended = true`、`detail.attempt_status = aborted`：存下的结算页买家号 ID 已不是批次账号当前登记的 ID）→ 没有登记提交，服务端已经中止这一笔并结束了批次，插件和护栏判定处一样不上报结果、不调用结束批次，以「买家号变了」结束（登记的答复丢了、浏览器重发时拿到的是 409 `LEASE_LOST`、`detail.end_reason = identity_mismatch`，同样处理，不报 `unknown`）；其他（上游已取消、账号暂停、买家号变了或登录状态过期、来源有变化 `SOURCE_CHANGED`……）→ 再问一次进度，按上表的 `cancel_code` 上报中止；进度仍说继续才报 `SUBMIT_REJECTED`。

模拟的结算事实：小计 = 采购单价 × 数量（按整数分计算），运费 0，税费 0，总额 = 小计，送达日期 = 洛杉矶今天 + min(3, 配送上限)，邮编取任务的，卡尾号取尝试载荷里的期望卡尾号（未设置则为空），币种 USD，配送方 amazon，买家号 ID 取当前页面的读数（读不到为空，不拿别的值顶替）。成功时单号为 `SIM-<北京日期 YYYYMMDD>-<尝试 ID>`（尝试 ID 是服务端的 attempt_id，不是「第 N 次尝试」的序号）。模拟结果不写回飞书，可在控制台「清除模拟结果」。

设置页可以选模拟结局，用来验证服务端的各条处理路径：

|模拟结局|插件的动作|服务端应有的结果|
|---|---|---|
|正常通过（默认）|护栏放行 → 登记 → 上报成功|任务「已采购」|
|结算总额超过限价|总额 = 限价 + 1 美元|护栏拦截 `PRICE_OVER_CAP`，任务「异常」，其他任务继续|
|配送时长超过上限|送达日期 = 洛杉矶今天 + 上限 + 1 天|护栏拦截 `DELIVERY_TOO_LONG`|
|商品缺货|护栏之前上报失败 `OUT_OF_STOCK`|任务「异常」|
|页面加载失败|上报失败 `PAGE_LOAD_FAILED`|首次自动重试一次，第二次「异常」|
|提交后结果不明|登记后上报 `unknown`，本批次结束|任务「结果待核实」，账号暂停执行|
|遇到验证码|上报失败 `CAPTCHA_ENCOUNTERED`，本批次结束|账号暂停执行，任务保留|

界面（页面内面板、弹出页、设置页）与日志里不出现原样的英文错误码：服务端错误码、护栏拦截码、尝试失败码、中止原因码、批次停止原因都换成中文说明（`core/codes.ts`）；认不出的码写「其他原因」。

## 写在代码里的几条规矩

这些是早期实现（amz-purchase-control）踩过的坑，移植时保留：

- **权限最小：只申请 `storage`、`alarms`，不申请 `cookies`、`tabs`。** 查亚马逊标签页按主机权限的地址过滤，用不着 `tabs`（它会让插件读到所有标签页的地址与标题）。不读也不上传 Cookie，不上传页面 HTML。身份只来自页面导航栏与内联脚本里的 customerId；上报的页面地址只有 origin + 路径，不带查询串。遇到验证码转人工，不做任何反检测。
- **令牌只在后台。** 令牌由后台生成，连同它所属的服务端地址存在扩展源下的 IndexedDB（`background/secrets.ts`）：内容脚本跑在亚马逊页面的源下，读得到 `chrome.storage.local`、打不开那个库。令牌不显示、不写日志，只发往它所属的地址。早期版本写在 `storage.local` 的令牌，后台第一次读到时搬走。
- **特权消息只认扩展自己的页面。** 保存设置、重新登记、清日志只接受扩展自己的页面发来的消息（`core/messages.isPrivilegedSender`）：没有 `sender.tab`、地址在扩展源下；设置页是开在标签页里的，它带着 `sender.tab`，所以再放行「文档就是扩展自己的设置页、浏览器报的源就是扩展的源」这一种。内容脚本的地址与源都是亚马逊页面的，一律拒绝。
- **后台没有模块级的租约状态。** MV3 后台空闲约 30 秒被回收，变量归零。标签页租约、当前批次、身份读数存在 `chrome.storage.session`，设置、登记的结论、日志、结果回执、当天定时记录存在 `chrome.storage.local`；「读 → 裁决 → 写」在串行闸里做。
- **后台标签页的定时器会被节流到约 60 秒一次。** 标签页租约有效期 5 分钟、持有者正在执行时再宽限 10 分钟（`core/lease.ts`，纯函数）；批次心跳按租约有效期算（默认 35 秒一次），引擎每一步之前也会按时钟补发，后台还有一路 30 秒的兜底心跳（只在执行页面对 `pc.ping` 答复「还在跑这个批次」、引擎最近还在动时才发）。
- **执行页面一刷新、一跳转、一关闭，引擎就没了，而且来不及说一声。** 后台不信本地的「正在执行」：同一标签页里来了批次开始之后加载的新页面（`pc.hello`）、执行页面离开（`pagehide` → `pc.bye`）、标签页关闭、执行页面对 `pc.ping` 不再答复，任何一个都让后台接管批次：界面上不再显示「正在执行」、放开标签页租约，立即通知服务端结束批次（服务端按租约过期同样处理在途尝试：未登记提交的回到已分配，已登记提交的进结果待核实并暂停账号），不等租约到期，也不再替它续租。插件安装、更新、浏览器重启时清掉留下的「正在执行」。
- **身份按页面加载先后对账（`core/identity.reconcileIdentity`）。** 导航栏是页面加载那一刻服务端渲染的，几小时前打开的页面重读一百遍也只是那一刻的样子：比先后只看页面的加载时刻；较早加载的页面的读数不能覆盖较新的；标签页关掉（或跳到下一页）后，若它是最新加载的一份仍留作证据；已登录但没读到买家号 ID 的读数不取代、也不作废读到 ID 或显示未登录的读数（例如显示另一个买家号的标签页跳到一张读不出 ID 的页面，另一个买家号仍是证据）；读数之间不一致时上报体带 `conflict: true`，服务端把登录状态记为不一致、不解析账号、不让开始批次，插件自己也不开始，提示刷新或关闭较早打开的标签页。分歧时报哪一份看有没有**基准**：本地有进行中的批次时，基准是该批次账号的买家号 ID（开始批次时记下），**绝不报基准**（报较新的、不是它的那一份，进行中的批次在提交前中止）；没有批次时没有基准，报加载最新的强证据。基准不是「上一次上报解析出来的账号」，否则一新一旧两张标签页会让上报在两个买家号之间来回翻。停在 `/ap/signin`（包括已登录时的重新验证页）的标签页读成未登录，同样按分歧处理 —— 往安全的一侧，关掉或完成验证后的下一次页面加载即恢复。
- **结果一定送到。** 后台在发出结果之前先存回执；引擎遇到没说上话或 5xx，在租约预算内按退避重发**同一份**结果（服务端按重复上报认出来），期间照常续租；结果没送到之前绝不结束批次（结束会把已登记的尝试判成结果待核实）。引擎放弃之后后台接管：续租、补交（第一次立即补交，之后按退避），送达后结束批次；租约预算用完、或接管满 10 分钟（与引擎重发结果的上限相同，例如续租成功而结果接口一直 5xx）还送不到就放手：不再续租、不替它结束批次，由服务端在租约到期后清扫在途尝试，回执保留、之后继续补交，最多 24 小时。补交的时机：插件后台启动时、每次心跳成功时（不等退避），以及 30 秒一次的回执闹钟（按退避）。服务端的答复：200（含同一份重复上报的 `duplicate: true`）→ 送达；尝试已是「结果待核实」、或已由控制台核实（已下单 / 未下单）而这份不同 → 409 `CONFLICT`、`detail.late_receipt_recorded=true`（回执已记下，供人工核实）→ 也算送达；其他 4xx（含别的 409）→ 服务端明确不收，不再发；5xx、没说上话 → 留着。服务端暂时不认识这个浏览器（401）时回执留着：后台重新登记后再发。提交登记永远不进回执、永远不补发。有回执没送到时不能改服务端地址。
- **三层互斥。** 本页单飞闸（重复点击、手动与定时同时触发只开一个）→ 本浏览器标签页租约（多个亚马逊标签页只有一个去申请批次）→ 服务端执行批次（跨电脑、跨浏览器的全局权威）。
- **HTTP 200 不等于业务成功。** 每个接口都校验响应形状；护栏只有 `verdict === "pass"` 才算放行；提交登记只认 HTTP 200。
- **只对「没说上话」重试，而且只对可以重复的请求。** 开始批次、领取、提交登记不自动重试（登记这个浏览器是幂等的，再试的节奏由后台按退避决定）；护栏在后台到服务端这一段没说上话（连不上、超时）时原样再发（同一份事实的重新裁决），服务端 5xx 或插件后台没有响应时不再发；结果、进度、批次心跳、结束批次在服务端 5xx（事务已回滚）或插件后台没有响应时也原样再发。提交登记的响应没拿到时，插件停止并停止续租，交给服务端清扫（已登记 → 结果待核实，账号暂停），绝不再登记或点击第二次；浏览器在连接断开后把同一个 POST 重发、服务端回「该尝试已登记提交」（409，`attempt_status=submitting`）时，插件明白这就是「已登记、没点击」，上报 `unknown` 并结束批次，不当成「被拒」。护栏拦截的响应丢了、重发得到「尝试已结束（失败）」时按拦截计，继续下一笔；buyer 项拦截的响应丢了、重发得到「批次已结束」（409 `LEASE_LOST`，`detail.end_reason = identity_mismatch`）时按「买家号变了」结束本批次。
- **所有等待都有界。** 每个请求 15 秒超时；后台消息有上界；单批次最多领取 200 笔。
- **NULL 不是 0。** 读不到的金额、天数保持空值，交给服务端按「数据不可靠」拦截。

## 与服务端的约定细节

- `POST /plugin/v1/register {device_token, ext_version, workspace_id?}`（不带 `Authorization`）→ `{device_id, device_name, workspace_id, workspace_name, created}`。其余接口带 `Authorization: Bearer <令牌>`；所有请求都是 `Content-Type: application/json` 的 POST。
- 心跳 `POST /heartbeat {ext_version, identity?}` 与身份上报 `POST /identity {signed_in, customer_id, site, page_url, conflict, ext_version}` 返回同一形状：`{device: {id, name}, login: {state, customer_id, at, stale}, account, device_run, server_time, bj_date, simulation_only}`。`login.state` 取 `unknown / signed_out / no_id / conflict / unregistered / ignored / ready`，认不出的按 `unknown`；`account` 只在 `ready` 时有；没有 `device.id` 或 `login` 的答复按「不是约定的形状」处理（旧版服务端）。
- `POST /runs {customer_id, trigger, slot?, simulated: true}` → `{run_id, lease_ttl_s, lease_expires_at, account: {id, name}}`，插件按 `lease_ttl_s` 定续租节奏；早期的 `{id}`、`{run: {id}}` 也认。`slot` 只在 `trigger = "scheduled"` 时带。
- 开始批次的拒绝：409 `DEVICE_BUSY`（`detail {run_id, account_name, since, lease_expires_at}`）、409 `ACCOUNT_BUSY`（`detail {holder_device_id, holder_device_name, since}`）、409 `SLOT_DONE`、403 `IDENTITY_MISMATCH`（`detail {login_state, identity_at, stale}`）、403 `ACCOUNT_NOT_REGISTERED`、403 `ACCOUNT_PAUSED`、403 `REAL_PURCHASE_DISABLED`、422（定时的时间点不对）。
- `POST /runs/{id}/finish` 的 `reason` 恒为契约缺省的 `finished`，插件的细分原因放在 `detail`（completed、stopped、attempt_cap、result_unknown、submit_rejected……）；返回 `{run_id, ended_at, end_reason, stats}`，插件不读它的内容。
- 批次的结束原因（服务端的 `end_reason`）是封闭取值：`finished`（插件结束）、`lease_expired`、`simulation_reset`、`identity_mismatch`（护栏 buyer 项拦下、服务端自己结束，插件不调用 `/finish`），历史批次里还有 `device_revoked`（「浏览器的授权已撤销（旧版）」，与服务端、控制台同一句）。批次失效后的请求一律 409 `LEASE_LOST`：已结束的是「执行批次已结束（<结束原因>），请重新开始批次」、`detail {run_id, end_reason}`，租约过期的是 `detail {run_id, lease_expires_at}`。
- 护栏的返回 `{verdict, code, reasons, checks, delivery_days, total_for_cap, fulfillment}`：插件只看 `verdict`、`code`、`reasons`。`code = IDENTITY_MISMATCH` 时 200 的形状不变（没有额外的键），「批次已由服务端结束」是这个拦截码的约定；提交登记复核处的 409 `GUARD_BLOCKED` 则在 `detail` 里写明 `{block_code, reasons, attempt_status: "aborted", order_status, run_ended: true, end_reason: "identity_mismatch"}`。
- 进度返回 `{continue, cancel_reason, cancel_code}`（契约 §5 第 7 步）：`cancel_code` 在 continue=true 时为 null，否则取 `UPSTREAM_CANCELLED` / `ACCOUNT_ARCHIVED` / `ACCOUNT_PAUSED` / `IDENTITY_MISMATCH` / `IDENTITY_STALE` / `SOURCE_HOLD` / `SOURCE_CHANGED` / `ATTEMPT_FINISHED`（上报规则见上表）。
- 批次心跳的 `stop_reason` 取 `account_paused` / `account_archived` / `identity_mismatch`。
- 护栏事实（契约 §4）多一项 `customer_id`。
- 领取返回 `{attempt: null, reason, retry_after_s}` 时稍后再领：`retry_after_s` 只要是不小于 0 的数就算（小数、数字字符串也认）。
- 几分钟前读的、这一轮哪个标签页都没读到的身份结论不再当成「刚读到」上报（服务端看到的「最近上报」得是真的）；有分歧的结论例外，它只会让服务端拒绝。
- 登记的 429 `RATE_LIMITED` 读 `detail.retry_after_s`，没有时读 `Retry-After` 响应头，再没有按 60 秒。
- 错误码表（`core/codes.ts` 的 `SERVER_CODE_LABEL`）与开发契约 §8、控制台的 `API_ERROR_CODES` 同序，测试钉住。`IDENTITY_MISMATCH` 是中止类，不是账号级。
- 插件上报的尝试失败码：`OUT_OF_STOCK`、`PAGE_LOAD_FAILED`、`CAPTCHA_ENCOUNTERED`、`ABORTED_UPSTREAM_CANCELLED`、`ABORTED_BY_SERVER`（只在服务端给了 `cancel_code` 时；服务端按中止类处理）、护栏拦截码（原样；护栏没给拦截码时 `GUARD_BLOCKED`；提交前复核护栏不过时取 `detail.block_code`；护栏或提交前的复核以 `IDENTITY_MISMATCH` 拦截时服务端已经中止了这一笔并结束了批次，插件不再上报，也不结束批次），以及少见的 `SUBMIT_REJECTED`（登记被拒且不是上游取消、也不是复核护栏不过）、`PLUGIN_SIMULATION_ONLY`（服务端下发了非模拟尝试，插件拒绝执行；账号级，服务端暂停账号，本批次结束）。
- 批次心跳的 `stop=true` 在当前这一笔结束后生效（模拟的一笔在毫秒级完成）。真实驱动接入时需要在每一步之间检查。

## 还没有实机核实的浏览器行为

下面几条是按 Chrome 的文档与常识写的，没有在真实浏览器里跑过，上线前请逐条确认：

- 亚马逊各类页面（首页、搜索、商品、购物车、订单历史、结算）的内联脚本里到底有没有 `customerId`、是哪种写法。夹具是按常见形态造的；参考项目只在订单历史页读它。
- 设置页（开在标签页里）发给后台的消息确实带着 `sender.tab`、`sender.url` 与 `sender.origin`，弹出页的没有 `sender.tab`（特权消息的来源检查依赖这一点）。
- 封闭 Shadow DOM 里的「复制买家号 ID」：`navigator.clipboard.writeText` 在亚马逊页面上是否可用，不可用时退回的「选中 + 复制命令」是否生效（都不行时面板提示手动选中复制）。
- 后台用 `chrome.tabs.create` 打开订单页与控制台（没有申请 `tabs` 权限）。
- `chrome.alarms` 的最短间隔：打包安装时 10 秒的快心跳、5 / 15 秒的登记重试会被浏览器放宽到 30 秒（看得见的面板另有 10 秒一次的同步）。
- 扩展更新后旧版留下的令牌（IndexedDB）与设置能否原样读到。
- AdsPower 环境里的几点，见上面「安装到 AdsPower」。
