# 采购助手（浏览器插件）

采购控制台的浏览器插件：Chrome MV3 + TypeScript + Vite，本机 Chrome 与 AdsPower 浏览器环境都能加载。一个浏览器环境（一个 Chrome 用户，或一个 AdsPower 环境）装一份、配对一次。

**本版本只做模拟执行，不产生真实订单。** 插件领取服务端分配给本账号、已到采购日期的任务，按任务数据推出一份结算信息交给服务端护栏裁决，再走提交登记与结果上报；它不打开、不点击、不修改任何亚马逊页面。真实下单流程在后续 PR 加入，并且由服务端单独开关。

|能做的|说明|
|---|---|
|配对|设置页填写控制台生成的 8 位配对码，换取设备令牌（只存在本浏览器的插件存储里）|
|心跳|每分钟一次，带上最新身份；缓存服务端下发的账号配置（执行方式、执行时间、额度、配送上限等）|
|身份识别|亚马逊页面上读登录状态与买家号 ID（customerId），上报服务端比对：一致 / 不一致 / 未登录 / 未知|
|页面内面板|订单历史页默认展开，其他亚马逊页面右下角是收起的悬浮按钮|
|模拟执行|手动点「开始执行（模拟）」，或到了控制台配置的执行时间自动开始|

## 构建与测试

需要 Node.js 18 以上（开发时用的是 22）。

```bash
cd extension
npm install
npm run build     # 类型检查 + 构建 → extension/dist（可直接「加载已解压的扩展程序」）
npm test          # 编译纯函数与协议客户端 → Node 单测（node --test）
npm run pack      # 构建并打包 → extension/release/采购助手-<版本>.zip（AdsPower 上传用）
```

`npm test` 覆盖：执行时间换算（北京时间、跨日、与本机时区无关）、标签页租约裁决与串行闸、协议客户端（错误映射、ACCOUNT_BUSY 详情、只对断网重试、提交登记绝不自动重试、HTTP 200 也校验形状）、模拟执行引擎对着内存假服务端（`test/fake-server.mjs`，按开发契约 §4、§5 实现）的各条路径、身份解析器对着导航栏夹具（`test/fixtures/`，虚构数据）。

## 安装到本机 Chrome

1. `npm run build`。
2. 打开 `chrome://extensions`，右上角打开「开发者模式」。
3. 点「加载已解压的扩展程序」，选择 `extension/dist` 文件夹。
4. 首次安装会自动打开设置页；之后也可以点工具栏的插件图标 →「打开设置」。

更新代码后重新 `npm run build`，再在 `chrome://extensions` 里点插件卡片上的刷新按钮，并刷新已打开的亚马逊页面。

## 安装到 AdsPower

AdsPower 的菜单名称随版本变化，以下是一般步骤，**请所有者在自己的 AdsPower 版本里核对实际入口**：

1. `npm run pack`，得到 `extension/release/采购助手-0.1.0.zip`。
2. 在 AdsPower 客户端里找到扩展管理（常见名称为「扩展」「应用中心」或「插件」），选择上传本地扩展，上传上面的 zip。
3. 把扩展分配给要使用的浏览器环境（可按分组或逐个环境开启）。
4. 打开该环境，点工具栏的插件图标 →「打开设置」完成配对。每个环境单独配对、单独起设备名称。

如果 AdsPower 的浏览器允许打开 `chrome://extensions`，也可以按上面 Chrome 的步骤直接「加载已解压的扩展程序」选择 `extension/dist`。插件要求浏览器内核不低于 Chromium 103。

## 配对

1. 先在本机启动服务端（`cd backend && python cli.py serve`，默认 `http://127.0.0.1:8790`）。
2. 控制台「账号与设备」→ 生成配对码（8 位，10 分钟内有效，只能用一次）。
3. 插件设置页填写：服务端地址（默认 `http://127.0.0.1:8790`，当前版本只支持本机）、配对码、设备名称（例如 `Mac-AdsPower-环境1`）、浏览器（Chrome / AdsPower / 其他），点「配对」。
4. 配对成功后，在控制台把这个设备绑定到对应的买家账号。设置页会显示绑定账号、身份状态和服务端下发的账号配置。
5. 打开任意亚马逊页面，插件读取登录状态并上报；身份状态变成「身份一致」后才能开始执行。账号还没登记买家号 ID 时显示「身份未知」，可在控制台「采用插件识别的 ID」。

「解除配对」只删除本浏览器里的设备令牌；要让服务端也作废，在控制台撤销该设备。

## 页面内面板

- 显示：服务端连接、设备名称、绑定账号、身份状态、「模拟模式」标签、今日额度、执行方式（定时则列出北京时间）、当前模拟结局、当前批次与尝试进度、最近 50 行日志（北京时间）。
- 按钮：「开始执行（模拟）」、「刷新身份」；执行中变为「停止执行」（当前这一笔结束后停止）。
- 面板挂在封闭的 Shadow DOM 里，亚马逊页面的样式进不来，面板的样式也不影响页面。外观按 EasyQuick 设计系统（青绿主色、圆角、系统字体，跟随系统浅色 / 深色）。

## 定时执行

- 账号的执行方式为「定时」时，插件按控制台配置的执行时间（如 `14:00`）设闹钟，**一律按北京时间理解**，与电脑所在时区无关。
- 到点时如果本浏览器有打开的亚马逊页面，就在该页面开始一个定时批次；没有的话，日志记一次「等待环境」。
- 错过的时间点在**同一个北京日期**内补执行一次：电脑开机、浏览器启动、打开亚马逊页面时都会检查；跨过北京时间零点不再补（方案 v2 默认值 4）。
- 每个时间点每天只处理一次。服务端拒绝（身份不一致、账号暂停等）也算处理过，日志写明原因；没连上服务端则稍后自动重试。
- 当天新增一个已经过去的执行时间，会被当作「今天错过的」立即补执行一次。

## 模拟执行做什么

按开发契约 §5 一步一步走，服务端的护栏、提交登记、结果处理、额度与状态机全部走真实代码路径，只有「读结算页」这一步是推出来的：

1. `POST /runs {trigger, simulated: true}` 开始批次（409 `ACCOUNT_BUSY` 时显示占用的设备与开始时间）。
2. 循环 `POST /runs/{id}/next` 领取，直到没有任务（`attempt: null`）。
3. 每一笔：进度（开始、读结算信息、登记前）→ 护栏（模拟的结算事实）→ 提交登记（只认 HTTP 200）→ 上报结果。
4. `POST /runs/{id}/finish` 结束批次。期间每 35 秒发一次批次心跳。

模拟的结算事实：小计 = 采购单价 × 数量（按整数分计算），运费 0，税费 0，总额 = 小计，送达日期 = 洛杉矶今天 + min(3, 配送上限)，邮编取任务的，卡尾号取账号期望卡尾号（未设置则为空），币种 USD，配送方 amazon。成功时单号为 `SIM-<北京日期 YYYYMMDD>-<尝试号>`。模拟结果不写回飞书，可在控制台「清除模拟结果」。

设置页可以选模拟结局，用来验证服务端的各条处理路径：

|模拟结局|插件的动作|服务端应有的结果|
|---|---|---|
|正常通过（默认）|护栏放行 → 登记 → 上报成功|任务「已采购」|
|结算总额超过限价|总额 = 限价 + 1 美元|护栏拦截 `PRICE_OVER_CAP`，任务「异常」，其他任务继续|
|配送时长超过上限|送达日期 = 洛杉矶今天 + 上限 + 1 天|护栏拦截 `DELIVERY_TOO_LONG`|
|商品缺货|护栏之前上报失败 `OUT_OF_STOCK`|任务「异常」|
|页面加载失败|上报失败 `PAGE_LOAD_FAILED`|首次自动重试一次，第二次「异常」|
|提交后结果不明|登记后上报 `unknown`，本批次结束|任务「结果待核实」，账号暂停执行|
|遇到验证码|上报失败 `CAPTCHA_ENCOUNTERED`，本批次结束|账号暂停执行，任务保留|

上游在提交登记之前取消时，进度返回 `continue=false`，插件上报失败 `ABORTED_UPSTREAM_CANCELLED`（不走护栏与登记），继续下一笔。

## 写在代码里的几条规矩

这些是早期实现（amz-purchase-control）踩过的坑，移植时保留：

- **不申请 `cookies` 权限，不读也不上传 Cookie，不上传页面 HTML。** 身份只来自页面导航栏与内联脚本里的 customerId；上报的页面地址只有 origin + 路径，不带查询串。遇到验证码转人工，不做任何反检测。
- **后台没有模块级的租约状态。** MV3 后台空闲约 30 秒被回收，变量归零。标签页租约、当前批次存在 `chrome.storage.session`，设置、令牌、日志、当天定时记录存在 `chrome.storage.local`；「读 → 裁决 → 写」在串行闸里做。
- **后台标签页的定时器会被节流到约 60 秒一次。** 标签页租约有效期 5 分钟、持有者正在执行时再宽限 10 分钟（`core/lease.ts`，纯函数）；批次心跳 35 秒一次，引擎每次领取前也会按时钟补发，后台还有一路 30 秒的兜底心跳（只在执行标签页还在、引擎最近还在动时才发）。
- **三层互斥。** 本页单飞闸（重复点击、手动与定时同时触发只开一个）→ 本浏览器标签页租约（多个亚马逊标签页只有一个去申请批次）→ 服务端执行批次（跨电脑、跨浏览器的全局权威）。
- **HTTP 200 不等于业务成功。** 每个接口都校验响应形状；护栏只有 `verdict === "pass"` 才算放行；提交登记只认 HTTP 200。
- **只对「没说上话」重试，而且只对可以重复的请求。** 配对、开始批次、领取、提交登记不自动重试；提交登记的响应没拿到时，插件停止并停止续租，交给服务端在租约到期后清扫（已登记 → 结果待核实，账号暂停），绝不再登记或点击第二次。
- **所有等待都有界。** 每个请求 15 秒超时；后台消息有上界；单批次最多领取 200 笔。
- **NULL 不是 0。** 读不到的金额、天数保持空值，交给服务端按「数据不可靠」拦截。


## 与契约的约定细节

- `POST /runs` 的返回形状契约没有规定，插件接受 `{id}`、`{run_id}`、`{run: {id}}`。
- 身份单独上报用 `POST /plugin/v1/identity`（请求体为身份字段本身）；服务端没有这个接口（404 / 405 / 422）时改由心跳捎带。
- 插件上报的尝试失败码：`OUT_OF_STOCK`、`PAGE_LOAD_FAILED`、`CAPTCHA_ENCOUNTERED`、`ABORTED_UPSTREAM_CANCELLED`、护栏拦截码（原样），以及少见的 `SUBMIT_REJECTED`（登记被拒且不是上游取消）、`PLUGIN_SIMULATION_ONLY`（服务端下发了非模拟尝试，插件拒绝执行）。
- 批次心跳的 `stop=true` 在当前这一笔结束后生效（模拟的一笔在毫秒级完成）。真实驱动接入时需要在每一步之间检查。
