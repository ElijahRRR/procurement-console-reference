# 开发契约 v2

本文件是实现层的唯一约定：目录与分层、数据模型、状态机、分配与额度算法、护栏、执行协议、HTTP 接口。业务定稿见 [方案 v2](采购控制台方案-v2.md)。改动本文件中的任何契约，须同时改代码与测试。

## 0. 目录与分层

```
backend/                 Python 3.12+，在此目录内运行一切命令
  cli.py                 唯一命令入口：db_init / user_create / serve / allocate / sweep / feishu_intake / feishu_writeback / feishu_grant
  scheduler.py           serve 的 HTTP 服务与后台调度（与 cli.py 同为入口层）
  registry/              接线盒：settings.py（环境变量）、db.py（连接唯一入口）、paths.py
  api/                   外部接口适配：feishu.py（飞书开放平台），只做认证、重试、分页、限速
  services/              业务积木（纯 SQL + 纯函数），全部业务判断在这里
  workflows/             命令与后台任务：每个文件一个 run(**params) -> dict 摘要（见下）
  server/                FastAPI：app.py、deps.py、limits.py、ratelimit.py、serialize.py、routes/*.py（每个文件一个 router）
  refdata/schema.sql     幂等建表（db_init 执行）
  tests/                 pytest，真实 PostgreSQL（每个测试会话建临时库）
web/                     Vue 3 + TypeScript + Vite + Element Plus 2.14 + Tailwind 3（EasyQuick 外观）
extension/               Chrome MV3 + TypeScript + Vite（插件）
```

分层只准自上而下：`cli.py / scheduler.py → (server | workflows) → services → api → registry`。`server` 与 `workflows` 同层，互不导入；`api` 不导入 `services`；任何层不导入入口层。路径、DSN、端口、密钥、可调参数只从 `registry` 取。

工作流：每个工作流暴露 `run(**params)`（命令行参数按 `-p key=value` 以文本传入），返回可打印的摘要。可在调用方事务里执行的另收关键字 `conn`（allocate、feishu_grant、sweep、user_create；不传时自己开事务并提交，传入时在它上面执行、不提交），调度用的另收 `now`（feishu_intake、feishu_writeback、sweep）；db_init 收 `dsn`。`serve` 例外，入口在 `scheduler.py`。

- `python cli.py db_init`：库不存在时先连同一服务器的维护库 `postgres` 执行 `CREATE DATABASE`，再执行 schema.sql（幂等，可在新库、旧库上反复执行：新库直接建成当前结构，已是当前结构的库不受影响，旧库由脚本后面的「追加」段升级，见 §1.2）；摘要 `{schema, ok, database, database_created}`，说明打印在标准错误输出。
- `python cli.py user_create -p username=… [-p workspace=…]`：密码缺省交互输入（不回显，输两次）或读标准输入第一行；`-p password=…` 仍可用但不建议（会留在 shell 历史和进程列表里），给了会在标准错误输出打印提示。
- `python cli.py feishu_grant -p workspace_id=… -p app_token=…`：飞书表格授权（见 §6），由部署所有者在服务器上执行。
- `python cli.py serve`：建应用、起调度之前先检查库结构（`workflows/db_init.schema_problem`，只读 information_schema），不是当前版本就把说明打印到标准错误输出并以退出码 1 退出：结构是旧版（缺当前结构的列，或旧列、旧表还在）→「数据库结构是旧版：请先运行 python cli.py db_init」；还没建表 →「数据库还没有建表：请先运行 python cli.py db_init」；连不上数据库 →「启动失败：连不上数据库（…）。库还不存在时请先运行 python cli.py db_init」。升级顺序：停服务 → `python cli.py db_init` → 启动 → 重新加载插件（控制台前端同时重新构建，见 §1.2）。

通用约定：

- 时间：库内一律 `timestamptz`（UTC）。业务日期一律**北京日期**（`Asia/Shanghai`），由 `services/clock.py` 的 `bj_today()` / `bj_date(ts)` 计算；不依赖数据库会话时区。亚马逊站点日期（算配送天数）用 `America/Los_Angeles`（`site_today()`）。
- 金额：`numeric(12,2)`，Python 侧用 `Decimal`，JSON 输出为字符串（如 `"52.00"`）。币种首期只有 USD。解析一律经 `services/models.money` / `money_cap`：数字按值；文本去掉首尾空白后，开头只认一个正负号、`US` / `USD` 与 `$`（如 `$25.50`、`US$25.50`、`-$5`、`$-5`），结尾只认 `USD`（如 `52 usd`；`US` / `USD` 不分大小写），中间的数字只认普通写法或千分位逗号（`1,234.50`）；`$`、`US` 出现在别处（`40$5`、`4US0`、`12US`、`40$`）、正负号出现两次（`-$-5`）、开头的 `US` / `USD` 与结尾的 `USD` 同时出现（`usd40usd`）、指数写法（`1e3`）、`12,5`、`1.234,50` 一律读不出（控制台 `web/src/utils/format.ts` 的 `parseAmount` 用同一规则）；读不出、非有限值、绝对值 ≥ 10^10（`numeric(12,2)` 放不下）一律为 None，不抛异常、不当 0。来源金额（§1.1）走同一套规则，只多把全角逗号「，」换成半角。两者都先按 6 位小数四舍五入抹掉浮点噪声，`money` 再四舍五入到分，`money_cap`（限价）向下取整到分。
- 空值：`NULL` 表示「没有或没读到」，不得当作 0。
- 工作区：除 `workspaces`、`users` 外每张表都有 `workspace_id`（`import_rows` 也带，查询按它过滤）。控制台与插件的查询一律带工作区条件（工作区由会话或浏览器决定，请求不能指定：浏览器的工作区在登记时确定、之后不变，买家号 ID 只在它所属的工作区内找账号）；跨工作区访问一律返回 404（不泄露存在性）。例外：认证时按令牌的哈希找会话、浏览器（`devices` 行）；浏览器登记时确定工作区（数工作区个数，系统里有多个工作区时按插件带来的 id 取工作区）；后台任务（清扫（含清理长期没有联系的浏览器行）、每日分配、飞书读取与写回）跨工作区挑出到期的行，之后按行上的工作区处理；`feishu_base_grants`（飞书多维表格 app_token → 工作区的授权登记）是跨工作区的登记表，与 `users` 一样不按工作区分区，只在表格授权检查与 `cli.py feishu_grant` 里读写。
- 事件：每次状态变化、人工动作、来源变化都写 `procure.events`（谁、何时、什么、细节）。
- 错误：服务层抛 `services.errors.DomainError(code, message, http_status, detail)`；路由层统一转 JSON `{ "code", "message", "detail" }`（码与状态见 §8）。
- 事务：services 不提交；事务边界在入口层（路由的请求依赖、workflows 的 `with db.pg_conn() as conn:`）。

## 1. 数据模型

完整 DDL 见 `backend/refdata/schema.sql`（schema 名 `procure`）。核心对象：

|表|含义|
|---|---|
|`workspaces` / `users` / `workspace_members` / `sessions`|工作区、控制台用户、成员关系、登录会话|
|`workspace_settings`|全局默认配送上限（初始 10 天）、模拟模式开关、文件导入的准入规则（`file_admission`）等|
|`buyer_accounts`|买家账号：登记的买家号 ID（`amazon_customer_id`，亚马逊 customerId，即执行身份）、金额区间、每日额度、优先级、配送上限覆盖值、采购/同步开关、暂停执行、执行模式与时间、归档时间|
|`devices`|浏览器（一行 = 一个装了插件的浏览器环境，由插件自动登记；表名、字段名、接口路径沿用 device）：令牌哈希、最近联系时间、最近上报的登录状态、移除时间（见 §1.2）|
|`ignored_buyer_ids`|所有者选择忽略的买家号 ID（不出现在「待登记的买家号」里；登记成账号时删掉对应的行）|
|`feishu_connections` / `feishu_sync_runs`|飞书连接（表定位、字段对应、准入规则、写回对应与写回列类型、写回验收）、每次读取记录|
|`feishu_base_grants`|飞书多维表格的工作区授权（一个表格同一时刻只归一个工作区）|
|`import_templates` / `import_batches` / `import_rows`|工作区共用的导入模板、上传批次（含原件、预览时用的准入规则 `admission`）、批次行（预览结论）|
|`purchase_orders`|采购任务（一笔上游采购单 = 一个任务），含原值、控制台覆盖值、状态、冲突、分配|
|`order_sources`|任务与来源记录的关联（飞书记录 / 文件行），含快照、规范化记录与指纹、是否写回目标|
|`purchase_attempts`|每次采购尝试（含模拟与来源带来的外部单号），领取时的任务快照与来源基线、护栏输入与裁决、提交登记时间、结果、金额、人工核实|
|`execution_runs`|账号执行批次（账号级执行权租约），含开始时的北京日期 `bj_date` 与定时时间点 `scheduled_slot`（手动批次为 NULL）|
|`writebacks`|飞书写回队列（按结果版本去重）|
|`allocation_runs`|每次分配的摘要（未覆盖账号与原因）|
|`events`|事件流水|

在途状态 = `claimed`、`checking`、`guard_passed`、`submitting`、`verifying`。关键唯一约束：

- `purchase_orders (workspace_id, upstream_order_no)`：同一工作区内上游采购单唯一。
- `execution_runs (account_id) WHERE ended_at IS NULL`：一个账号同时只有一个执行批次。
- `execution_runs (device_id) WHERE ended_at IS NULL`：一个浏览器同时只有一个执行批次。
- `execution_runs (account_id, bj_date, scheduled_slot) WHERE trigger = 'scheduled' AND scheduled_slot IS NOT NULL AND (ended_at IS NULL OR end_reason = 'finished')`：一个账号的一个定时时间点一天只执行一次（未结束或正常结束的定时批次占着这个时间点；租约过期、被清除模拟结果结束的不占）。
- `purchase_attempts (purchase_order_id) WHERE status IN 在途状态`：一笔任务同时只有一个在途尝试。
- `purchase_attempts (account_id) WHERE status IN 在途状态`：一个账号同时只执行一笔。
- `purchase_attempts (workspace_id, amazon_order_no) WHERE amazon_order_no IS NOT NULL AND NOT simulated AND status = 'succeeded'`：同一亚马逊订单号只能是一笔成功的真实尝试（防串单）。结果上报时，真实尝试的单号已登记在工作区里任何别的成功真实尝试上（含本任务之前的尝试、来源带来或人工接受的外部单号）→ 尝试 `unknown`、任务 `result_unknown`、暂停账号，error_detail 写明单号已登记在哪里；写库时唯一索引冲突（并发漏网）同样处理，不报 500。
- `buyer_accounts (workspace_id, amazon_customer_id) WHERE amazon_customer_id IS NOT NULL AND archived_at IS NULL`：同一工作区里同一个买家号 ID 只登记在一个未归档账号上（按买家号 ID 找账号至多一行；执行权互斥按账号行算）。
- `devices (token_hash)`：一个令牌只对应一行浏览器（并发登记同一个令牌只会有一行）。
- `ignored_buyer_ids (workspace_id, customer_id)`：主键，忽略是幂等的。
- `feishu_base_grants (app_token)`：一个飞书多维表格同一时刻只授权给一个工作区。
- `order_sources`：同一飞书记录（连接 + record_id）、同一文件行（批次 + 行号）各只关联一笔任务；每笔任务至多一个写回目标。
- `writebacks (purchase_order_id, connection_id, result_version)`：写回按结果版本去重。

### 1.1 上游记录的标准形状（`services/models.UpstreamRecord`）

飞书记录与文件行都先转成这个形状，再交给 `services/orders.ingest`。全部字段可为 `None`，只有 `upstream_order_no` 必填。

|字段|类型|说明|
|---|---|---|
|upstream_order_no|str|平台订单号（去除首尾空白）；表格错误值（#N/A 等）、多个不同的值、科学计数法文本 → 不可用（invalid，原因写在 issues[0]）|
|order_line_id, store_name, sales_po_no, sku|str|展示与对账|
|asin|str|大写；不符合 `^[A-Z0-9]{10}$` 视为缺失并记问题|
|quantity|int|1–999；不是正整数或超出范围视为不可靠（None + 问题，如「数量超出合理范围（1–999）：…」，任务停在资料待补齐），与控制台覆盖数量同一上限|
|unit_price, sales_total, price_cap|Decimal|美元，按 §0 的金额规则解析（`12,5`、`1.234,50`、`1e3` 不认，绝对值须小于 10^10）；price_cap 向下取整到分（78.685 → 78.68），其他金额四舍五入|
|order_time|datetime(tz)|下单时间。飞书日期字段为毫秒时间戳；文本按北京时间解析；年份须在 2000–2100|
|ship_days|int|配送天数（审核时采集值），0–60，超出视为不可靠（None + 问题）|
|suggested_purchase_date|date|来源给出的建议采购日期；年份须在 2000–2100|
|ship_method|str|如 FBA|
|recipient_name, address1, address2, city, state, postal_code, phone, country, district|str|收件信息；country 缺省 `US`；美国地址的邮编单元格为数字且只有 3–4 位时补前导 0（记问题）|
|review_value|str|人工审核原文|
|review|str|`approved` / `rejected` / `unknown`（由准入规则判定）|
|purchaser|str|采购方原文|
|purchase_status_value|str|来源里的采购状态原文|
|after_sale_value|str|售后状态原文|
|upstream_cancelled|bool|由准入规则判定|
|external_amz_order_no|str|来源已有的 AMZ 订单号；可信格式 `^\d{3}-\d{7}-\d{7}$`；占位写法（— 无 N/A null 0 等）视为 None 并记问题；其他不符合格式的原样保留并判待核实，不当作已采购|
|external_buyer_account, external_buyer_customer_id|str|来源已有的买家号与买家号 ID|
|issues|list[str]|规范化时发现的问题（如「ASIN 格式不对」「数量不是正整数」）|

文本字段里的表格错误值视为 None 并记问题。取值字段（人工审核、售后状态、采购状态）为多选时逐项比较：任一项是取消值即取消，任一项是拒绝值即拒绝，全部是通过值才算通过，任一项命中 `skip_purchase_status_values` 即命中。

来源引用 `services/models.SourceRef`：`kind`（`feishu`/`file`）、`connection_id`+`record_id`，或 `batch_id`+`row_no`；`snapshot`（原始字段 → 值）。

### 1.2 浏览器行、登录状态与旧库升级

`devices`：`workspace_id`（登记时确定，之后不变）、`name`（「浏览器 <编号>」，之后只能在控制台改名）、`token_hash`（sha256(令牌)，唯一；令牌只是会话标识，不代表身份）、`ext_version`、`user_agent`、`last_seen_at`、`identity`（jsonb：`{signed_in, customer_id, site, page_url, conflict, at}`，清洗后的最近一次上报，`at` 为服务端时刻）、`identity_at`、`login_customer_id`（已登录、读到合格 ID 且各标签页读数一致时的买家号 ID，否则 NULL；索引 `(workspace_id, login_customer_id)`）、`created_at`、`hidden_at`（控制台「移除」的时间；浏览器再次联系时清空）。`browser` 是历史列，不再写入。库里不存「身份状态」：登录状态与解析结果每次由浏览器行现算（§5 第 3 步）。

旧库升级（schema.sql 的「追加」段，可重复执行；新库上都是空操作），顺序固定：

1. **旧版关联回填**（旧列 `devices.bound_account_id`、`devices.revoked_at` 都还在时才做）：对每个未归档、还没登记买家号 ID 的账号，取旧版里关联到它（`bound_account_id`）、没有失效（`revoked_at` 为空）的浏览器行中「已登录且 ID 合格（`^A[0-9A-Z]{8,}$`）」的 ID 集合；集合恰好一个值、这个 ID 没被同工作区其他未归档账号登记、也没有另一个账号在这次回填里要拿同一个 ID → 写进账号，并记事件 `account.customer_id_adopted`（actor_kind system，detail `{customer_id, device_id, via: "legacy_binding"}`；这个事件种类只由升级产生）。拿不准的一律不动，由所有者在控制台登记。
2. `devices`：加 `login_customer_id`、`hidden_at`；用存下的身份回填 `login_customer_id`（只在旧列还在时做一次，之后由服务端在每次身份上报时维护）；旧版里已失效的行记 `hidden_at`（= 原 `revoked_at`）；删 `bound_account_id`、`identity_status`、`revoked_at`。
3. `buyer_accounts`：删 `default_device_id` 及其外键。
4. 删表 `device_pairings`。
5. `execution_runs`：加 `bj_date`（旧行按开始时刻的北京日期回填后 NOT NULL）、`scheduled_slot`（CHECK 为 `HH:MM`）；同一浏览器留着多个未结束批次时只留最新的，其余置 `lease_expired`（它们的在途尝试由下一轮清扫收尾）；建唯一索引 `execution_runs_one_active_per_device`、`execution_runs_slot_once`。

升级后新版插件沿用旧版留下的令牌，不用重新登记（旧版插件本身会被版本闸拦下，§5 第 1 步）；旧版里已失效的行令牌哈希早已清空，那个浏览器装上新版插件后会登记成新的一行。升级前的结构存为测试夹具 `backend/tests/data/schema_v1.sql`，迁移测试在独立的临时库里先建旧结构、插入旧形状的数据，执行新脚本两遍，核对回填结果，并断言升级后的列、索引、约束与新库完全一致。服务端托管的控制台前端（`web/dist`）不入库，升级时要重新构建。

## 2. 采购任务状态机

`purchase_orders.status`：

|状态|中文|进入条件|
|---|---|---|
|`pending_review`|待确认|人审结果不是「通过」|
|`needs_info`|资料待补齐|已通过人审，但缺少执行所需字段（见下）|
|`conflict`|待核实|不同来源内容冲突，或历史/外部单号与本系统记录矛盾|
|`queued`|待分配|可执行，尚未分配账号|
|`assigned`|已分配|已有账号（建议采购日期可能在未来）|
|`executing`|采购中|有在途尝试|
|`result_unknown`|结果待核实|已登记提交但未确认结果，或插件无法确认是否已下单、上报的成功不合格（见 §5 结果处理）|
|`exception`|异常|本任务暂停（超限价、缺货、超配送时长、页面错误重试后仍失败等），原因见 `status_reason`|
|`purchased`|已采购|有成功尝试（或来源带来的外部单号）|
|`cancelled`|已取消|采购开始前上游取消，或人工取消|
|`repurchase_pending`|待决定重采|亚马逊取消了采购订单（第二个 PR 由物流同步触发；本 PR 提供人工入口）|
|`closed`|已关闭|人工决定不重采|

执行所需字段（缺一即 `needs_info`）：有效 ASIN、有效数量 >0、采购单价、有效限价、建议采购日期（来源给出或可计算）、收件人姓名、地址 1、城市、州、邮编、电话。邮编对美国地址须主体为 5 位数字（如 02134、02134-1234），否则也算缺。`purchase_orders.missing_fields` 存字段键（asin、quantity、unit_price、price_cap、suggested_purchase_date、recipient_name、address1、city、state、postal_code、phone），不存中文名。

「有效值」= 控制台覆盖值优先，否则来源原值：`asin_eff = coalesce(override_asin, asin)`，数量、限价同理。商品小计 `subtotal_eff = unit_price × quantity_eff`。

`services/orders.derive_status(order)` 只用于采购开始前的状态（`pending_review / needs_info / conflict / queued / assigned / cancelled / purchased(外部)`），优先级：上游取消 → `cancelled`；外部单号 → `purchased`；未通过人审 → `pending_review`；冲突未解决 → `conflict`；缺字段 → `needs_info`；已分配 → `assigned`；否则 `queued`。下表的「派生状态」即它可能给出的这七种。

迁移只能经 `services/orders.transition(conn, order, to, reason, actor)`，它校验下表、做乐观并发检查（状态已被别的操作改过 → 409 `CONFLICT`）并写 `order.status_changed` 事件；目标与当前相同时只写列、不记状态事件；进入 pending_review / needs_info / conflict / queued / cancelled / closed（以及开始前因外部单号直接 purchased）时自动解除分配，进入 assigned 时必须有账号。唯一例外：清除模拟结果（`orders.revert_simulation`）绕过迁移表，把只经模拟执行的任务直接退回开始前的派生状态；状态有变化时照样写 `order.status_changed`，detail 带 `simulation_reset: true`、reason「已清除模拟结果」。

|从|允许到|
|---|---|
|pending_review / needs_info / conflict / queued / assigned|彼此之间（由 derive_status 决定）、`purchased`（来源带来外部单号）、`cancelled`、`executing`（仅 assigned）|
|executing|`assigned`（未提交即中止或可重试的失败；随后按派生规则重新校验，见下文「领取后来源变化」，可能转 pending_review / conflict）、`exception`、`result_unknown`、`purchased`、`cancelled`（未提交时收到上游取消）|
|result_unknown|`purchased`（人工核实已下单）、`assigned` / `queued`（人工核实未下单，随后按派生规则重新校验）|
|exception|派生状态（人工恢复后重新校验）、`cancelled`、`closed`|
|purchased|`repurchase_pending`（亚马逊取消）|
|repurchase_pending|派生状态（同意重采：解除原分配、清掉外部单号后重新派生）、`closed`|
|cancelled|派生状态（人工撤销取消）|

冲突（`purchase_orders.conflict`）：`{kind, source_kind, reason, fields: {字段: [当前, 来源]}, incoming, source, at}`，`kind` 取 `fields` / `review` / `external_order_no` / `admission` / `source_key_changed`（同一任务多次冲突合并，按 admission > source_key_changed > external_order_no > review > fields 定处理方式，原因去重拼接）。`resolve-conflict`：keep = 保留现值并清除冲突（review 时记为控制台确认通过）；accept = fields / review 把 `incoming` 写进原值，external_order_no 登记为已采购（单号格式不对或仍属别的任务 → `VALIDATION`），admission → 取消任务，source_key_changed → 取消原任务并解除那条来源关联（下次读取按新订单号接收）；之后开始前的任务按派生规则重新校验，异常的任务保持异常（接受外部单号时转 `purchased`）。

来源更新（`ingest`）只应用来源记录相对上次的变化（上次的规范化记录存在 `order_sources.normalized`）；来源没变就是 unchanged，不会把控制台处理过的冲突、覆盖值、人审结论改回去。对不同状态的影响：

- 开始前（pending_review / needs_info / conflict / queued / assigned）：更新原值并重新派生（人审撤回 → `pending_review` 并解除分配）；已分配但金额已不在账号区间内则解除分配回到待分配；覆盖值不受影响，差异写事件。
- 异常、已取消：更新原值但不改状态（异常在人工恢复时再派生；撤销取消的规则见下）。
- 执行中 / 待核实 / 已采购 / 待决定重采 / 已关闭：不改执行相关原值（展示字段照改），只记录「上游在采购开始后修改了 X」事件并置 `needs_attention`；`order_sources` 的规范化记录与指纹照样前进到最新。
- 领取后来源变化：领取时尝试的 `task_snapshot.source_baseline` 记下任务每条来源关联的指纹与执行相关值（不下发给插件）。提交登记前，来源相对基线出现本系统没有的外部 AMZ 订单号、同种来源的人审结论改变、执行相关字段被改 → 进度 `continue=false`（`SOURCE_CHANGED`）、提交登记 409 `SOURCE_CHANGED`；执行期间来源把暂停写在任务上（`conflict` 非空：人审拒绝、准入变化、平台订单号变化，见下）→ 进度 `continue=false`（`SOURCE_HOLD`）、提交登记 409 `SOURCE_CHANGED`。采购没有完成就结束（插件中止、清扫、未提交失败、护栏拦截、清除模拟结果、结果待核实经人工核实为未下单、已采购被亚马逊取消后同意重采（相对成功尝试的基线））时这些变化落到任务上：人审结论直接采用（撤回 → `pending_review`）；任务由控制台人审时，领取后才出现的来源关联（如新一批文件）带来「拒绝」不直接采用，按人审冲突写进 `conflict`（kind review，控制台「接受 / 保留」），与采购开始前的规则一致；外部单号 / 字段变化写进 `conflict`（`incoming` 为来源新值，控制台「接受 / 保留」），并置 `needs_attention`，再按派生规则定状态（异常保持异常，恢复时派生）；每笔尝试只落一次；已有冲突（如执行期间写在任务上的暂停）时按冲突合并规则合并（种类取处理方式更重的，字段与来源新值合并，原因去重拼接），外部单号、字段变化、人审冲突与已有的暂停都保留；采购期间被推迟的暂停（`order.hold_deferred`，见下）这时按来源现状仍成立的一并转进 `conflict`（记 `order.hold_deferred_applied`）。来源改了又改回、重传相同内容、领取前已「保留」的冲突不算变化。领取后才出现的来源关联（如新一批文件、新的飞书记录）按首次关联的规则比：它没带的列（空值）不算变化；收件信息只有带了姓名 / 地址 1 / 城市 / 州 / 邮编之一时才整组比较；同种来源只能按下单时间算出建议采购日期、而任务的日期来自来源时，不算变化。同一条来源关联的下单时间或配送天数被改、使算出的建议采购日期改变，同样算变化（指纹之外另比被监视的值），`conflict.incoming` 一并带上下单时间与配送天数，「接受」时写回。
- 上游取消：开始前 / 异常 → `cancelled` 并解除分配；执行中且未登记提交 → 置取消标记，插件下一次进度上报得到 `continue=false` 后中止，任务 → `cancelled`；已登记提交 → `result_unknown` 并注明「执行中收到取消」；待核实 / 已采购 / 待决定重采 / 已关闭 → 只置取消标记与 `needs_attention`（已采购时提醒人工处理亚马逊订单）。撤销取消只认发出取消的那条来源记录（上次说取消、这次不说，且没有别的来源仍说取消）；另一种来源或新批次文件说「没取消」不撤销取消，只在预览问题里说明。只由文件快照说取消的任务（没有飞书来源仍说取消），控制台可撤销取消：清掉上游取消标记，事件 `order.uncancelled` 记 {note, overrode_upstream_cancel: true, file_link_ids, previous_cancel_note}；之后同样售后状态的旧文件再上传不再取消，只在预览问题里说明；飞书来源仍说取消时拒绝（422 `VALIDATION`）。
- 人审拒绝从不悄悄丢掉：另一种来源、或控制台人审通过后新关联的来源（如新批次文件）送来拒绝 → 开始前 / 异常转 `conflict`（种类 review）并解除分配；执行中未登记提交 → 冲突写在任务上（插件下一次进度上报得到 `continue=false`）；已登记提交的采购中、结果待核实、已采购、待决定重采 → 置 `needs_attention` 并记 `order.hold_deferred`（{conflict, attempt_id, status}），任务之后回到开始前时（核实未下单、同意重采、清除模拟结果），来源现状仍成立的暂停转 `conflict`（与领取后来源变化合并）；已关闭只置 `needs_attention`；已取消的不再暂停。控制台人审通过之前同样的拒绝已出现过（旧文件重传）→ 不再转冲突。另一种来源的其他人审差异只在预览问题里说明。
- 准入变化（来源接收时传入准入规则）：采购方已不在 `purchaser_values` 内、或采购状态命中 `skip_purchase_status_values` 且没有可信 AMZ 订单号 → 开始前 / 异常转 `conflict`（种类 admission）并解除分配；执行中未提交同上写在任务上；已登记提交的采购中、结果待核实、已采购、待决定重采 → 置 `needs_attention` 并记 `order.hold_deferred`（{conflict, attempt_id, status}），任务之后回到开始前时（核实未下单、同意重采、清除模拟结果）按来源现状仍成立的转 `conflict`；已关闭只置 `needs_attention`；已取消的不再暂停。本系统曾真实采购成功（非模拟、非外部单号）的任务不看采购状态（那是写回写的；模拟结果永不写回）。同一来源反复送来相同的值只处理一次；新一批文件重传控制台已「保留」的同样取值不再暂停，只在预览问题里说明。
- 同一来源记录的平台订单号变了 → 原任务开始前 / 异常转 `conflict`（种类 source_key_changed，带 link_id）并解除分配（只在第一次发现时转）；执行中未登记提交 → 冲突写在任务上（插件下一次进度上报得到 `continue=false`，`SOURCE_HOLD`），中止后转 `conflict`；已登记提交的采购中、结果待核实、已采购、待决定重采 → 置 `needs_attention` 并记 `order.hold_deferred`（回到开始前时那条来源关联仍挂在本任务上的转 `conflict`）；已取消、已关闭只置 `needs_attention`；不新建任务。
- 跨来源：任务首次出现的来源种类为主来源。另一种来源送来同键记录且执行相关字段（ASIN、数量、限价、单价、收件信息、建议采购日期）不同 → 开始前转 `conflict`（种类 fields，来源新值存进 `incoming` 供「接受」），不覆盖；字段相同只追加来源关联；另一种来源只能补上「未知」的人审结论。同种来源（同一飞书记录或新批次文件）视为正常更新。
- 外部单号：开始前 / 异常出现可信单号 → `purchased`（创建 `kind='external'` 的成功尝试记录单号与买家号，不计额度）；单号格式不对或已属别的任务 → `conflict`（种类 external_order_no）；正在执行、待核实、已取消或本系统已有不同单号 → 只记事件并置 `needs_attention`（执行中且未登记提交时插件会被叫停，中止后按「领取后来源变化」转 `conflict`）。开始前 / 异常登记了可信的外部单号时，任务上待核实的 external_order_no 冲突（同一单号、或之前格式不对 / 重复的单号）作废（记 `order.conflict_superseded`）。同意重采时，待核实的单号正是本任务已登记（刚被亚马逊取消）的那一单，同样作废。「接受」一个已登记在本任务成功尝试上的单号 → 422 `VALIDATION`。
- 同种来源送来新值后，任务上同种来源写的冲突（如领取后来源改了字段、中止后写的 fields 冲突）里这些字段的旧「来源新值」作废（fields 冲突的字段全作废 → 冲突清除，任务按派生规则离开待核实）；「接受」主来源写的冲突时，冲突之后任务原值已被改过的执行相关字段跳过（记 `applied.skipped_stale`）。

## 3. 分配与额度

### 3.1 额度

账号 A 在北京日期 D 的已用额度 `used(A, D)` = `purchase_attempts` 中 `account_id = A`、`bj_date = D`、`simulated` 与当前批次相同、`kind <> 'external'`、状态不在 (`failed`, `aborted`) 的尝试数（在途、待核实、成功都占用；人工核实「未下单」后该尝试改为 `failed`，释放额度）。一次成功计 1 单，与商品数量无关。`bj_date` 取尝试创建时的北京日期，跨零点不变。

### 3.2 分配算法（`services/allocation.allocate(conn, workspace_id, today, trigger)`）

参与的账号：未归档、`purchase_enabled`、未 `execution_paused`、站点相符。参与的任务：`queued`，以及 `assigned` 且 `assignment_kind='auto'` 且无在途尝试的任务（自动分配可重算）；`assignment_kind='manual'` 的任务固定不动，但占用计划额度。

计划日期 `plan(t) = max(suggested_purchase_date, today)`。按计划日期从早到晚逐日处理，日期 D 内：

- `cap(A, D) = daily_limit − used(A, D) − fixed(A, D)`，`fixed` 为 D 日固定（人工）分配且尚无尝试的任务数。
- `covered(A, D)`：D 日 A 已有采购尝试（不论结局，失败、中止也算；外部单号与「清除模拟结果」中止的不算）或已有固定分配。
- `eligible(t, A)`：`min_amount ≤ subtotal_eff(t) ≤ max_amount`（端点含；`max_amount` 为空表示不限）且 `cap(A, D) > 0`。

1. **保底**：未覆盖且有额度的账号与当天任务做最大二分匹配（增广路）。账号按（可选任务数升序、优先级降序、名称升序）尝试；候选任务按（可选账号数升序、建议采购日期、下单时间、id）。匹配成功的标注「保底：当天首单」。这保证 A 只接 20–30、B 接 20–50、有 25 和 45 两单时 A 得 25、B 得 45。
2. **填充**：剩余任务按（建议采购日期、下单时间、id）依次分给可选账号中优先级最高者，同优先级按名称升序；标注「按优先级填充」。
3. 分不出去的任务留在 `queued`，`status_reason` 写明原因：「金额 $X 不在任何启用账号的区间内」或「匹配账号当天额度已满」。未被覆盖的账号在 `allocation_runs.uncovered` 写明原因：「没有金额匹配的订单」「当天额度已用完」「订单数量不足」。

人工改派（`assign_manual`）：目标账号必须启用、金额区间匹配、计划日期当天有剩余额度；成功后 `assignment_kind='manual'`。关闭采购开关只影响新分配；暂停执行的账号不参与自动分配，已分配任务保留。账号归档：有未结束的执行批次、在途或待核实的尝试时拒绝（409）；已分配的开始前任务解除分配后重新分配。归档后它登记的买家号 ID 不再被任何未归档账号占用：仍登录着这个买家号的浏览器回到「未登记」（`unregistered`），这个 ID 重新出现在待登记的买家号里（§8）。

分配触发：来源导入/同步后、人工点击「重新分配」、账号配置变化后（新建、改动影响分配的字段、恢复执行、归档）、每天北京时间 00:01（每个工作区每个北京日期只做一次，按 `allocation_runs` 里 `trigger='daily'` 的记录去重，进程重启不重做；当天没做过的在启动后补做一次）。任务上的人工动作不自动触发重新分配。

### 3.3 执行时再校验（领取任务时）

领取条件：任务 `assigned` 给该账号、`suggested_purchase_date ≤ bj_today()`、人审通过、未上游取消、无冲突、按派生规则仍是 `assigned`、`used(A, today) < daily_limit`、金额仍在区间内。顺序：建议采购日期、下单时间、id；`FOR UPDATE SKIP LOCKED`。金额已不在区间 → 解除分配回 `queued` 并跳过。另要求账号未暂停、未归档、这个浏览器最新的登录状态是「登录着批次账号当前登记的买家号 ID」（§5「执行中的身份检查」）且在 `identity_fresh_s`（10 分钟）内上报过、账号在别处没有在途尝试，否则返回 `{attempt: null, reason}`。候选任务只是被别的事务锁着（导入、同步、分配）时返回 `{attempt: null, reason, retry_after_s}`（`retry_after_s` 取 registry 的 `claim_busy_retry_s`，环境变量 `PC_CLAIM_BUSY_RETRY_S`，缺省 5 秒），插件等待后再领，不结束批次。开始批次与领取取工作区执行闸门的共享锁（清除模拟结果取独占锁）。

## 4. 护栏（`services/guard.evaluate`）

插件在结算页、点击下单前上报事实（`customer_id` 是插件取事实那一刻从结算页读到的买家号 ID；模拟执行时取当前页面的读数，读不到为 null，不拿别的值顶替）：

```json
{
  "items": [{"asin": "B0DEMO0001", "quantity": 1, "unit_price": "41.97"}],
  "subtotal": "41.97", "shipping": "0.00", "tax": "2.52",
  "total_before_tax": "41.97", "total": "44.49",
  "gift_card_amount": null,
  "currency": "USD",
  "delivery": {"text": "Arriving Nov 8", "date": "2026-11-08", "days": null},
  "ship_to": {"postal_code": "32960"},
  "card_last4": "0000",
  "fulfillment": "amazon",
  "customer_id": "A1DEMO00000"
}
```

逐项判定（全部通过才放行；拦截码取顺序中第一个不通过的检查；结果写入尝试的 `guard_verdict`）：

|检查|规则|拦截码|
|---|---|---|
|买家号（buyer）|`customer_id` 与批次账号**当前**登记的买家号 ID 相同（都先去空白、转大写）；读到了 ID 而账号现在没有登记 ID 也算不通过|IDENTITY_MISMATCH|
|商品|items 恰好一项，ASIN 与有效 ASIN 相同，数量与有效数量相同|ITEM_MISMATCH|
|邮编|`ship_to.postal_code` 前 5 位与任务邮编前 5 位相同|ZIP_MISMATCH|
|金额区间|subtotal 在账号区间内（端点含；上限为空表示不限）|SUBTOTAL_OUT_OF_RANGE|
|限价|`total` 加上礼品卡抵扣额（`gift_card_amount` 按绝对值加回，null 表示没有礼品卡）≤ 有效限价（相等放行）|PRICE_OVER_CAP|
|配送时长|配送天数 = `delivery.date − 站点今天`（洛杉矶日期），无日期时用 `delivery.days`；≤ 有效配送上限（账号覆盖值或全局默认）；日期早于站点今天视为读取不可靠|DELIVERY_TOO_LONG|
|数据可靠|total、subtotal 可解析，配送天数可得，币种为 USD，结算页读到了买家号 ID|DATA_UNRELIABLE|
|卡尾号|账号设置了期望卡尾号时必须相同|CARD_MISMATCH|

有效限价按 `models.money_cap` 向下取整到分（宁可少放行 1 美分）。读不到的小计、总额、配送天数不当 0：依赖它们的检查记为无法判定（ok=null，不单独拦截），由数据可靠检查统一拦截。买家号 ID 同理：缺失、类型不对或形状不对（不符合 `^A[0-9A-Z]{8,}$` 或超过 64 位）按没读到，买家号一项记为无法判定，由数据可靠检查拦截为 `DATA_UNRELIABLE`，绝不因为缺失而放行（旧版插件不带这个键，同样被拦）。买家号一项把「谁在下单」钉在下单那一页：浏览器的登录状态是各标签页对账后上报的，结算页自己读到的才是这一单真正的下单人。插件上报的事实先经 `guard.sanitize_facts` 规范化：只留上例中的键；`card_last4` 只留后 4 位；`customer_id` 去空白、转大写（形状或类型不对换成 `"<invalid>"`，判定时按没读到）；`delivery` 只留 text（≤200 字）/ date / days；`ship_to` 只留 postal_code；items 最多 20 项，每项只留 asin / quantity / unit_price；类型不对、超长或超出 10^12 的值换成 `"<invalid>"`（仍判为格式不对）。判定与入库（`guard_input`）都用规范化后的事实，不返回 422。

`guard_verdict`：`{verdict: pass | block, code, reasons, checks: {buyer|item|zip|subtotal|price_cap|delivery|data|card: {ok: true | false | null, expected, actual}}, delivery_days, total_for_cap, fulfillment}`。`fulfillment` 只记录，不拦截。判定按任务与账号**当前**有效值（登记的买家号 ID、限价、金额区间、有效配送上限、期望卡尾号）与站点今天。拦截 → 尝试 `failed`（error_code 为拦截码）、任务 `exception`（原因为拦截码的中文说明；上游已取消 → `cancelled`；领取后被挡住的来源变化同样落到任务上），其他任务继续。买家号一项被拦下（`IDENTITY_MISMATCH`）同样按护栏拦截处理：尝试 `failed`、任务 `exception`（原因里写明「结算页登录的买家号（…）不是这个批次的买家号（…）」），不暂停账号、不占额度；不按 §5 结果处理里中止类的「回已分配」（否则只要浏览器上报的登录状态没变，同一批次会立刻再领到同一笔）。

## 5. 执行协议（插件 ↔ 服务端）

前缀 `/plugin/v1`。**买家号的身份 = 亚马逊 customerId（下称「买家号 ID」）**，由插件从当前亚马逊页面读出后上报。账号（`buyer_accounts`）由所有者在控制台登记；账号上登记了哪个买家号 ID，任何登录着这个买家号的浏览器都能执行它的任务，与哪台电脑、哪个浏览器无关。浏览器由插件自动登记，没有任何人工步骤，浏览器与账号之间也没有固定关系。插件不自动创建账号：没登记过的买家号 ID 只记在浏览器行上，由控制台「待登记的买家号」列出（§8）。用词：「浏览器」= 一个装了插件的浏览器环境，即库里的一行 `devices`（表名、字段名、接口路径沿用 device）；「买家号」= 一个亚马逊买家登录；「账号」= 控制台里登记的买家号。为什么这样设计见 [方案 v2](采购控制台方案-v2.md)「2026-11 修订：执行入口」与 [参考插件执行逻辑](参考插件执行逻辑.md)。

**信任边界与入口闸**（`server/limits.PluginGateMiddleware`，最外层中间件，先于 Host / Origin 检查、请求体限制、限速、认证与请求体解析）：能访问本机端口的程序被视为所有者自己；跨机器部署需要另加接入密钥，当前版本不支持，服务端直接拒绝非本机的插件请求。路径以 `/plugin/` 开头的请求（不论方法）按顺序检查，不过 → 403 `FORBIDDEN`（`detail` 为空对象），不进后面的任何一层：

1. 对端地址（套接字对端 `scope["client"][0]`；`serve` 以 `proxy_headers=False` 运行，不信 `X-Forwarded-For`）必须是回环，只认 `127.0.0.1`、`::1`、`::ffff:127.0.0.1` 三个字面地址 → 否则「插件接口只接受本机请求：跨机器部署需要接入密钥，当前版本不支持」。
2. Host 头必须是本机名（`127.0.0.1` / `localhost` / `::1`，不看端口），**不**看 `PC_HOST` 与 `PC_ALLOWED_HOSTS` → 否则「插件接口只接受发往本机地址（127.0.0.1 或 localhost）的请求：请在插件设置里把服务端地址改成本机地址」。
3. `Origin` 头是网页来源（http / https，或不透明来源 `null`）→「插件接口不接受网页来源的请求」。配置了 `PC_PLUGIN_EXTENSION_IDS` 时，Origin 还必须是 `chrome-extension://<名单里的 ID>`（不分大小写），没带 Origin 也拒绝 →「插件接口只接受名单里的扩展：这个扩展的 ID 不在 PC_PLUGIN_EXTENSION_IDS 里」。
4. POST 必须带 `Content-Type: application/json`（允许 `; charset=…`；没有请求体的 POST 也要带）→ 否则「插件接口只接受 JSON 请求」。

入口闸的两条已知边界：本机的反向代理不要转发 `/plugin` 路径（经代理转来的远端请求，在服务端看来对端与 Host 都是本机，入口闸拦不住）；扩展 ID 名单为空时，同一个浏览器里对本机地址有主机权限的其他扩展也能调用插件接口。

**认证**：`/register` 不需要令牌；其余接口带 `Authorization: Bearer <浏览器令牌>`。令牌由插件生成，库里只存 sha256；它只是会话标识（把批次、尝试、回执归到同一个浏览器），不代表身份，服务端也不会吊销它。令牌缺失、没登记过或浏览器行已被清扫删除 → 401 `UNAUTHORIZED`「这个浏览器还没有登记，插件会自动重新登记」；401 表示这次请求完全没有被处理，插件收到后用同一个令牌重新登记，再把原请求重发一次。从控制台列表里移除的浏览器照样能认证。工作区在浏览器登记时确定、之后不变，请求不能指定；批次 / 尝试不属于这个浏览器 → 404。插件请求不需要控制台的防跨站请求头。批次已结束或租约已过期时，批次与尝试类请求一律 409 `LEASE_LOST`（结果上报的例外见第 11 步）。

1. **登记**：`POST /register {device_token, ext_version?, workspace_id?}`（不带令牌头）→ `{device_id, device_name, workspace_id, workspace_name, created}`。
   - `device_token` 由插件生成（`crypto.getRandomValues` 取 32 字节，base64url 编码成 43 个字符），须整串符合 `^[A-Za-z0-9_-]{32,128}$`，否则 422 `VALIDATION`（`detail.field = device_token`）。旧版插件留下的令牌符合这个形状，原样沿用。
   - **幂等**：令牌已登记 → 返回那一行（更新最近联系时间与版本，清掉「已移除」），`created=false`，不看 `workspace_id`。并发登记同一个令牌靠 `ON CONFLICT (token_hash) DO NOTHING` + 重查，只会有一行。
   - 新浏览器的工作区：系统里恰好一个工作区 → 它（不看 `workspace_id`）；还没有工作区 → 409 `CONFLICT`「服务端还没有初始化：请先打开控制台创建用户」；有多个工作区 → 必须带存在的 `workspace_id`，否则 409 `WORKSPACE_REQUIRED`「系统里有多个工作区：请在插件设置的「工作区 ID」里填写（控制台「设置」页可以查到）」。
   - 名称：「浏览器 <编号>」（插入后回写），之后只能在控制台改名。新登记写事件 `device.registered`（detail：`ext_version`、`user_agent` 前 200 字）。
   - 上限：工作区内浏览器行数（含已移除的）≥ `PC_MAX_DEVICES`（缺省 500）→ 429 `RATE_LIMITED`「登记的浏览器太多：请稍后再试」（没有 Retry-After 头，`detail` 里也没有 `retry_after_s`）。登记不走失败限速。
   - **版本闸**：登记、心跳、身份上报带来的 `ext_version` 能解析（1–4 段点分整数）且低于 `0.2.0` → 409 `PLUGIN_OUTDATED`「插件版本过旧：请重新构建并加载新版插件（需要 0.2.0 及以上）」，detail `{ext_version, min_ext_version}`，什么也不记；缺失或解析不了的不拦。
   - 插件侧：服务端地址缺省 `http://127.0.0.1:8790`，装好不需要任何设置，也不自动打开设置页。还没有登记成功过、或任何接口回 401 → 单飞地用同一个令牌登记（401 的情形登记成功后把原请求重发一次；重新登记成功后 30 秒内再遇到 401 不再登记）。登记失败按 5 / 15 / 60 秒退避，每次心跳闹钟、面板展开、点「重试」都会再试；429 按 `detail.retry_after_s`，其次 Retry-After 头，都没有按 60 秒；`WORKSPACE_REQUIRED`、`PLUGIN_OUTDATED`、任何 403、422 不自动重试，面板写明原因。改服务端地址时换一个新令牌再向新地址登记（旧令牌绝不发往新地址）；有进行中的批次或未送达的回执时不允许改。保存设置、重新登记这类消息只接受扩展自己的页面发来的，内容脚本发来的一律拒绝。
2. **心跳**：`POST /heartbeat {ext_version?, identity?}` → `{device: {id, name}, login: {state, customer_id, at, stale}, account, device_run, server_time, bj_date, simulation_only}`（形状见 §10「插件心跳」）。更新最近联系时间与版本（版本变了写 `device.ext_version_changed`），清掉「已移除」（被移除的浏览器再次联系时自动回到列表）；带 `identity` 时同第 3 步；不续执行批次的租约。`login.state` 是解析后的状态（第 3 步）；`account` 只在 `login.state = ready` 时非空：模式、执行时间、有效配送上限、开关、暂停状态、当天额度；没有 `expected_card_last4`、`min_amount`、`max_amount`、`daily_limit` 这几个键（卡尾号与金额区间只在领取后的尝试载荷里，每日上限见 `quota_today.limit`）。`account.executable_today` = 已分配给该账号、建议采购日期 ≤ 北京今天、人审通过、未上游取消、无冲突、没有在途尝试的笔数（与领取的挑选条件同口径；不与当天剩余额度取小，也不重验金额区间）；`account.future_assigned` = 已分配给该账号、建议采购日期在今天之后的笔数；`account.active_run` 是账号的未结束批次（`is_mine` = 是不是这个浏览器的）；`device_run` 是这个浏览器自己的未结束批次（不论账号）。插件每 60 秒一次；`login.state = unregistered` 时每 10 秒一次（自这个状态出现起最多 10 分钟），好让控制台一登记面板就更新。
3. **身份与登录状态**：`identity = {signed_in, customer_id, site, page_url, conflict?}`，随心跳捎带，或单独 `POST /identity {signed_in, customer_id, site, page_url, conflict?, ext_version?}`（必须有请求体）→ 与心跳完全相同的形状（同样记最近联系时间、清掉「已移除」、过版本闸）。
   - **清洗**（`devices.clean_identity`，绝不因为买家号 ID 报错）：`customer_id` 去掉所有空白、转大写，须符合 `^A[0-9A-Z]{8,}$` 且不超过 64 位，否则当作没读到（null）；`signed_in` 只认布尔 true；`conflict` 取布尔；`page_url` 只留 origin + path；`site` 截到 8 个字。只有整个身份不是对象时才 422。
   - **存储**：清洗后的身份连同服务端时刻 `at` 存进 `devices.identity`，另记 `identity_at`；`login_customer_id` = 已登录、读到 ID 且没有分歧时的 ID，否则 NULL。这次 UPDATE 锁住浏览器行，与开始批次、提交登记（它们先 `FOR UPDATE` 锁浏览器行）串行。
   - **浏览器的登录状态**（`devices.login_state`，只由浏览器行算出，不看新鲜度）：`unknown`（从未上报）/ `conflict`（各标签页读数不一致）/ `signed_out` / `no_id`（已登录但没读到合格的买家号 ID）/ `signed_in`。
   - **解析**（`devices.resolve_login`，每次心跳、身份上报、列表都现算，不存）：`signed_in` 时在浏览器所属工作区找 `amazon_customer_id = login_customer_id` 的未归档账号 → 有 → `ready`；没有且这个 ID 在 `ignored_buyer_ids` 里 → `ignored`；否则 `unregistered`。其余状态原样。插件与控制台看到的状态全集（`login.state`）：`unknown` / `signed_out` / `no_id` / `conflict` / `unregistered` / `ignored` / `ready`。
   - **过期**：`login.stale` = `identity_at` 距现在超过 `identity_fresh_s`（缺省 600 秒，`PC_IDENTITY_FRESH_S`）；从未上报时为 false。
   - （登录状态、买家号 ID）变化时写 `device.identity_changed`，detail `{from: {state, customer_id}, to: {state, customer_id}}`（state 是浏览器的登录状态，不含解析结果；customer_id 是 `login_customer_id`）。
   - 插件侧读法：登录状态从导航栏读；买家号 ID **只在内联脚本**（`script:not([src])` 的文本）里找 `customerId` 的几种写法，所有形状合格的匹配必须是同一个值，否则当作没读到；不扫标题、属性、正文。不读、不传 Cookie，不上传页面 HTML。
   - 插件侧对账：按页面加载时刻对本浏览器各亚马逊标签页的读数对账：较早加载的页面的读数不能覆盖较新的；标签页关闭后，若它是最新加载的一份仍作为证据；已登录但没读到买家号 ID 的读数不取代、也不作废读到 ID 或显示未登录的读数（同一标签页跳到读不出 ID 的新页面时，上一页的读数同样留作证据）；读数之间不一致时上报体带 `conflict: true`（服务端记为 `conflict`，不解析账号，不让开始批次）。分歧时报哪一份看基准：本地有进行中的批次时，基准 = 该批次账号的买家号 ID（开始批次时记下），绝不上报基准，而上报较新的、不是基准的那一份（进行中的批次在提交前中止）；没有批次时没有基准，上报加载最新的强证据。执行批次进行中，插件每 3 分钟、以及每一笔提交登记之前（登记前最后一次进度确认之前），让本浏览器所有亚马逊标签页重读身份并 `POST /identity` 强制上报（不受 60 秒去重限制）；超过 5 分钟前读的、这一轮没有任何标签页重读到的身份结论不再上报（有分歧的结论除外）。
4. **开始批次**：`POST /runs {customer_id, trigger: manual|scheduled, slot?: "HH:MM", simulated: true}` → `{run_id, lease_ttl_s, lease_expires_at, account: {id, name}}`。`customer_id` 是插件在当前页面读到的买家号 ID。服务端依次：
   1. `FOR UPDATE` 锁浏览器行（与并发的身份上报串行；加锁顺序：浏览器行 → 执行闸门 → 批次 → 任务 → 尝试 → 账号）。
   2. 参数：`trigger`、`simulated`（布尔）取值不对 → 422；`customer_id` 缺失或为空 → 422「插件版本过旧，请更新插件」（`detail.field = customer_id`；旧版插件不带它），去空白、转大写后形状不对 → 422。
   3. 这个浏览器已有未结束批次（不看租约是否已过期）→ 409 `DEVICE_BUSY`「这个浏览器上一个批次还没有结束」，detail `{run_id, account_name, since, lease_expires_at}`。
   4. 取工作区执行闸门的共享锁（§3.3）。
   5. 身份：浏览器的登录状态必须是 `signed_in`、`login_customer_id` 等于请求里的 `customer_id`、且不过期 → 否则 403 `IDENTITY_MISMATCH`，detail `{login_state, identity_at, stale}`（`login_state` 是浏览器的登录状态，不含解析结果；`stale` 给真实值）。文案按情况：从未上报「插件还没有上报这个浏览器的登录状态，请打开或刷新亚马逊页面后重试」/ 未登录「浏览器没有登录亚马逊」/ 读数不一致「这个浏览器的亚马逊标签页显示的买家号不一致，请刷新或关闭较早打开的标签页」/ 没读到 ID「插件没有读到浏览器登录的买家号 ID，请打开亚马逊订单页后重试」/ ID 不同「页面上的买家号与插件最近上报的不一致，请刷新亚马逊页面后重试」/ 过期「插件超过 N 分钟没有上报登录状态，请打开或刷新亚马逊页面后重试」。
   6. 账号：浏览器所属工作区内未归档、登记了这个 ID 的账号；没有 → 403 `ACCOUNT_NOT_REGISTERED`「这个买家号还没有登记：请在控制台「账号」页登记后再开始」，detail `{customer_id}`。
   7. 账号已暂停执行 → 403 `ACCOUNT_PAUSED`（detail `{pause_reason, paused_at}`）；`simulated` 不是 true → 403 `REAL_PURCHASE_DISABLED`（本阶段服务端拒绝一切非模拟批次）。
   8. `trigger = scheduled`：必须带 `slot`（北京时间，`H:MM` 或 `HH:MM`，规范成 `HH:MM`）；账号的 `purchase_mode` 必须是 scheduled、slot 在 `schedule_times` 里、北京时间今天已到点 → 否则 422（`detail.field = slot`，message 说明原因）；同一（账号、北京日期、slot）已有未结束或以 `finished` 结束的定时批次 → 409 `SLOT_DONE`「这个时间点今天已经执行过」。手动批次不记时间点（`scheduled_slot` 为 NULL，带了 `slot` 也不看）。
   9. 账号已有未结束批次 → 409 `ACCOUNT_BUSY`，detail `{holder_device_id, holder_device_name, since}`，message 写明正由哪个浏览器、从北京时间几点起执行。`SLOT_DONE` 先于 `ACCOUNT_BUSY`：同一时间点的并发开始，后到的稳定得到 `SLOT_DONE`。
   10. 插入批次（SAVEPOINT，写 `bj_date = bj_today()` 与 `scheduled_slot`）。并发下先查后插没拦住的唯一索引冲突：先按第 8 步重查时间点（→ `SLOT_DONE`），其余按索引名映射成 `DEVICE_BUSY` / `SLOT_DONE` / `ACCOUNT_BUSY`，调用方事务仍可用。`run.started` 事件 detail `{account_id, trigger, simulated, customer_id, scheduled_slot}`。

   租约 `lease_ttl_s` 秒（缺省 180，`PC_LEASE_TTL_S`），只有批次心跳续期；插件每 min(35 秒, lease_ttl_s / 3) 发一次批次心跳，每一步之前到点就补一次。插件侧（手动）：当前页重读身份 → 交后台对账（其余亚马逊标签页也各自重读）→ 有分歧不开始 → 否则先 `POST /identity` 上报，再 `POST /runs`；本地还有没结束的批次（含回执保管期）时不发请求。插件侧（定时）：本地「今天已处理的时间点」按买家号 ID 分键（只用来少发请求，去重的权威在服务端）；到点 `POST /runs {…, trigger: "scheduled", slot}`：已开始、`SLOT_DONE`、403 `ACCOUNT_PAUSED` → 记为已处理；422 → 刷新配置后这个时间点记为已处理；`ACCOUNT_BUSY`、`DEVICE_BUSY`、其他拒绝与没说上话 → 不记，下一分钟再问；错过的时间点在同一个北京日期内补一次（当天错过多个时合成一次，申请最晚到期的那个），跨零点不补。
5. **批次心跳**：`POST /runs/{id}/heartbeat` → `{lease_expires_at, stop, stop_reason}`（续租 lease_ttl_s 秒）。`stop=true` 只在 stop_reason 为 `account_paused` / `account_archived` / `identity_mismatch`（这个浏览器最新的登录状态不是「登录着批次账号当前登记的买家号」；不看新鲜度）时出现，租约照样续，插件把手上这一笔做完再结束批次；批次已结束（含被清扫）或租约已过期 → 409 `LEASE_LOST`。
6. **领取**：`POST /runs/{id}/next` → `{attempt: {...}, reason: null}` 或 `{attempt: null, reason}`（候选只是被锁着时另有 `retry_after_s`，见 §3.3）。同一批次已有在途尝试时 409 `ATTEMPT_IN_FLIGHT`（detail.attempt_id）。尝试载荷：attempt_id、attempt_no、kind、order_id、upstream_order_no、asin、quantity、unit_price、subtotal、price_cap（向下取整到分）、max_delivery_days、amount_range `{min, max}`、收件信息（recipient_name、address1、address2、city、state、postal_code、phone、country、district）、expected_card_last4、simulated、bj_date、suggested_purchase_date、account `{id, name}`；库里另存同一份载荷与来源基线（`task_snapshot`）。尝试种类：`retry` = PAGE_LOAD_FAILED 的自动重试（上一笔本系统尝试因 PAGE_LOAD_FAILED 失败且任务 page_load_retries > 0；人工恢复异常后为 auto）；`repurchase` = 任务曾有成功尝试（同意重采后）；其余 `auto`。插件对 `retry_after_s`（不小于 0 的数，可为小数）夹在 1 – 30 秒之间等待后再领，至多再领 6 次，等待期间按租约节奏续租、到点补报身份；6 次之后仍被占用则以 detail=completed 结束批次。
7. **进度**：`POST /attempts/{id}/progress {stage, detail}` → `{continue, cancel_reason, cancel_code}`。首次进度把尝试从 claimed 推进到 checking。`cancel_code` 在 `continue=true` 时为 null；尝试已结束 → `continue=false`、`ATTEMPT_FINISHED`；未登记提交时依次检查：上游已取消 → `UPSTREAM_CANCELLED`、账号已归档 → `ACCOUNT_ARCHIVED`、已暂停 → `ACCOUNT_PAUSED`、这个浏览器最新的登录状态不是「登录着批次账号当前登记的买家号」（含未登录、标签页读数不一致、没读到 ID、账号现在没有登记 ID）→ `IDENTITY_MISMATCH`、登录状态超过 `identity_fresh_s`（10 分钟）没有上报 → `IDENTITY_STALE`、执行期间来源把暂停写在任务上 → `SOURCE_HOLD`、领取后来源有执行相关变化（见 §2）→ `SOURCE_CHANGED`，都是 `continue=false`。已登记提交的尝试一律 `continue=true`。插件据此上报中止：`UPSTREAM_CANCELLED` → `ABORTED_UPSTREAM_CANCELLED`；`ATTEMPT_FINISHED` → 不再上报；其余 → `ABORTED_BY_SERVER`。`attempt.progress` 事件记下 `{stage, detail, continue, cancel_reason, cancel_code}`（尝试已结束时不写）。
8. **护栏**：`POST /attempts/{id}/guard {事实}` → `{verdict: pass|block, code, reasons, checks, delivery_days, total_for_cap, fulfillment}`（§4）。放行 → 尝试 `guard_passed`；拦截即结束尝试（failed，error_code 为拦截码）、任务转异常；对已登记提交或已结束的尝试再判 → 409 `CONFLICT`，detail.attempt_status。插件对 attempt_status=failed 的 409 按拦截计、继续下一笔。事实里带 `customer_id`（§4 买家号一项）：以 `IDENTITY_MISMATCH` 拦截时服务端已经把这一笔结束（尝试 failed、任务转异常、不暂停账号），插件不再上报结果，写「浏览器登录的买家号变了，这一笔在提交前中止」并以 detail=buyer_changed 结束本批次；其余拦截码插件照旧上报一次同码的失败（服务端按重复上报回 200）。
9. **提交登记**：`POST /attempts/{id}/submitting` → `{ok: true, submitted_at}`，200 才允许点击下单；登记即写 `submitted_at`（可能已下单）。服务端先 `FOR UPDATE` 锁浏览器行，再做检查与登记，与并发的身份上报串行（要么登记看到新身份而拒绝，要么身份上报排在登记之后、由之后的步骤处理）。拒绝时 409、不改任何状态，依次检查：尝试不在 guard_passed 或护栏未放行（`CONFLICT`，detail.attempt_status）、上游已取消或任务状态已变（`CONFLICT`，detail.order_status）、账号已归档（`CONFLICT`）或暂停（`ACCOUNT_PAUSED`）、这个浏览器最新的登录状态不是「登录着批次账号当前登记的买家号」或已过期（`IDENTITY_MISMATCH`，detail `{login_state, stale, identity_at}`；不符时 stale=false，只是过期时 login_state=signed_in、stale=true）、执行期间来源把暂停写在任务上（`SOURCE_CHANGED`，detail.conflict_kind）、领取后来源有执行相关变化（`SOURCE_CHANGED`，detail.fields / review / external）、按最新配置（账号登记的买家号 ID、有效限价、账号金额区间、有效配送上限、期望卡尾号、站点今天）对存下的结算事实复核护栏不再放行（`GUARD_BLOCKED`，detail.block_code / reasons）。插件的处理：detail.attempt_status ∈ {submitting, verifying}（连接断开后浏览器重发了同一个 POST）视为「已登记、未点击」，上报 outcome=unknown 并结束批次；attempt_status 已是结局 → 结束批次；`GUARD_BLOCKED` → 按 detail.block_code 上报失败（没有 block_code 时上报 GUARD_BLOCKED）、继续下一笔（block_code 为 `IDENTITY_MISMATCH` 时这份失败按结果处理表的中止类处理：尝试 aborted、任务回已分配）；其他 409（CONFLICT、ACCOUNT_PAUSED、IDENTITY_MISMATCH 含 detail.stale、SOURCE_CHANGED）→ 再发一次进度（stage=before_submit），按返回的 cancel_code 上报中止（ABORTED_BY_SERVER / ABORTED_UPSTREAM_CANCELLED）；进度仍为 continue=true 时才上报 SUBMIT_REJECTED（error_detail 为服务端原话）并结束批次。
10. **等待验证**：`POST /attempts/{id}/verifying {note}`（银行人工验证）→ `{ok: true, attempt_status: 'verifying'}`，任务与名额保留，任务说明写「等待银行人工验证」；只限已登记提交的尝试，否则 409 `CONFLICT`。
11. **结果**：`POST /attempts/{id}/result {outcome: succeeded|failed|unknown, amazon_order_no, amounts, card_last4, delivery, error_code, error_detail}` → `{attempt_status, order_status}`。amounts 的键为 subtotal / shipping / tax / total_before_tax / total，读不出或为负的记为 null。未登记提交的结果要求批次有效（否则 409 `LEASE_LOST`）；已登记提交的尝试在租约过期、尚未清扫时照常接收结果。同一份结果重复上报 → 200，另有 `duplicate: true`；尝试已是 `unknown` 时收到不同的结果（迟到的回执）：不改状态、不恢复账号、不自动核实，回执补进尝试空着的列（单号、金额、卡尾号、配送），写 `attempt.late_result` 事件，任务状态说明与提醒补一句；响应 409 `CONFLICT`，detail = `{attempt_status, order_status, late_receipt_recorded: true}`，事务照常提交；同一份回执重复送达不重复记录。已由控制台核实（resolution 为 ordered / not_ordered）的尝试收到不同的结果 → 同迟到回执：记 `attempt.late_result`（另有 resolution、contradicts），不改尝试的状态、核实结论与金额；与核实结论矛盾（核实未下单却送来带亚马逊订单号的成功、核实已下单却送来另一个单号的成功）时任务置 `needs_attention`，真实尝试还按来源暂停的方式挡住重新领取（任务开始前 / 异常 → `conflict`，种类 external_order_no，incoming 为回执里的单号；正被另一笔未登记提交的尝试执行 → 冲突写在任务上，下一次进度 `SOURCE_HOLD`），模拟尝试只提醒；响应同样是 409 `CONFLICT`，detail `{attempt_status, order_status, late_receipt_recorded: true}`，事务照常提交。其他已结束的尝试（中止、未经核实的失败）收到不同的结果 → 409 `CONFLICT`，detail `{attempt_status, reported}`。插件在发出结果前先保存回执（落地方案 v1 §4）：没说上话或 5xx 时，引擎在租约预算内按退避重发同一份结果并照常续租，结果送达之前不结束批次；引擎放弃后由插件后台续租、补交（第一次立即补交，之后按回执退避），送达后结束批次；后台接管最多续租 10 分钟（与引擎重发结果的总时长上限相同）：租约预算用完、或接管满 10 分钟仍送不到（例如续租成功而结果接口一直 5xx）就放手 —— 不再续租、不结束批次，由服务端在租约到期后清扫在途尝试，回执保留、之后继续补交；回执最多保留 24 小时。补交时机：插件后台启动时、每次心跳成功时（不等退避；引擎自己还在重发、尚未被后台补交过的回执不抢着发），以及每 30 秒一次的回执闹钟（按 30 / 60 / 120 / 300 秒退避）。200（含 duplicate）与 409 late_receipt_recorded 视为送达；其他 4xx（含 LEASE_LOST、404、其他 409）不再补交；5xx、没说上话，以及 401（服务端这会儿不认识这个浏览器，后台用同一个令牌重新登记后再发）留着。提交登记永远不进回执、不补发。
12. **结束批次**：`POST /runs/{id}/finish {reason, detail?}` → `{run_id, ended_at, end_reason, stats}`。批次的 end_reason 恒为 `finished`（end_reason 只取 finished / lease_expired / simulation_reset；历史行可能有旧版留下的 device_revoked），reason 原样记进 `run.ended` 事件的 `plugin_reason`（缺省 finished，插件恒传 finished）；detail 为插件的细分原因（completed、stopped、attempt_cap、result_unknown、submit_rejected、success_rejected、non_simulated_attempt、account_level_error、progress_rejected、guard_rejected、buyer_changed、page_reloaded、page_left、tab_closed、engine_gone、engine_ended，领取被拒时为小写的错误码），字符串去掉首尾空白后截到 200 字、其他 JSON 先转成文本再截，记进 `run.ended` 事件的 `plugin_detail`（空为 null）。批次还有在途尝试时按租约过期同样处理（见下文清扫）。批次已结束或租约已过期 → 409 `LEASE_LOST`。执行页面刷新、离开或关闭时，插件后台立即代为结束批次。

**执行中的身份检查**（领取、进度、提交登记）：拿「这个浏览器最新的登录状态」对「批次账号**当前**登记的买家号 ID」——登录状态是 `signed_in`、`login_customer_id` 等于账号现在登记的 ID、且在 `identity_fresh_s` 内上报过。不符 → 领取返回 `{attempt: null, reason}`、进度 `cancel_code = IDENTITY_MISMATCH`、提交登记 409 `IDENTITY_MISMATCH`；只是过期 → 领取同样不领、进度 `IDENTITY_STALE`、提交登记 409 `IDENTITY_MISMATCH`（`detail.stale = true`）。批次心跳的 `identity_mismatch` 不看新鲜度。**结果上报、结束批次、迟到回执不做身份检查**（回执不丢）。执行中途换了买家号：未登记提交的那一笔中止（插件按进度的 cancel_code 上报 `ABORTED_BY_SERVER`），任务回已分配，不暂停账号，不占额度，之后由登录着正确买家号的浏览器领取；已登记提交的照常收结果，非成功结局照旧进结果待核实并暂停账号。账号有未结束批次、在途或结果待核实的尝试时控制台不能修改或清空买家号 ID（§8）；基准万一还是在执行中变了（例如与开始批次并发的修改），一律按不符处理。

|未提交，任务级错误（OUT_OF_STOCK、QUANTITY_UNAVAILABLE、ADDRESS_FAILED、CART_MISMATCH、UNEXPECTED_PAGE、护栏拦截码、GUARD_BLOCKED、SUBMIT_REJECTED、未识别的错误码）|failed|exception|—|

表中任务回已分配或转异常的情况，上游已取消时一律 → `cancelled`。failed 与 aborted 的尝试不占额度。错误码与中文说明以 `services/models.ERROR_CODES` 为准（category：task / account / retry_once / abort / guard）。`IDENTITY_MISMATCH`（「执行中途浏览器登录的买家号变了」）是中止类：换了买家号不是账号的问题，不暂停账号；它同时是护栏买家号一项的拦截码，那条路径在护栏处就把尝试结束了（failed、任务转异常，见 §4），不经过这张表。

租约清扫（`services/execution.sweep`，每 `PC_SWEEP_INTERVAL_S` 秒，缺省 30；跨全部工作区）：批次租约过期 → 批次结束（`lease_expired`）；所属批次已结束的在途尝试一并收尾。其在途尝试若未登记提交 → `aborted`，任务回 `assigned` 后按派生规则重新校验（§2「领取后来源变化」）；已登记提交 → `unknown`，任务 `result_unknown`，账号暂停执行。被别的事务锁住的批次跳过，下一轮再处理。从控制台移除浏览器不会结束它的批次（有未结束批次的浏览器本来就不能移除，§8）。另清理浏览器行：最近联系时间（从未联系过的按登记时间）早于 `PC_DEVICE_RETENTION_DAYS`（缺省 30）天、且没有任何执行批次、采购尝试引用的行直接删除（不写事件，已有的事件保留；正被别的事务锁着的行跳过）；被删掉的浏览器再来时得到 401，用同一个令牌重新登记成新的一行。摘要 `{expired_runs, orphan_attempts, removed_devices, aborted, unknown}`（前三项是 id 列表，后两项是计数）。

账号被执行模块暂停时，除 `account.paused` 外另写一条 `account.paused_by_execution` 标记 `{cause: result_unknown | account_error, simulated, attempt_id, code, reason}`，供「清除模拟结果」与账号的 `pause_cause`（§10）判断暂停起因。

模拟：模拟尝试的单号形如 `SIM-<日期>-<id>`，不写回飞书。`POST /api/v1/simulation/reset` 先取工作区执行闸门的独占锁（清除期间不会有新的批次或尝试），结束未结束的模拟批次（`simulation_reset`），把这些任务的模拟尝试标为 `aborted`（resolution `simulation_reset`，细节注明「已清除模拟结果」），模拟期间被挡住的来源变化先落到任务上（见 §2；含推迟的人审拒绝、准入变化、平台订单号变化，按来源现状仍成立的转 `conflict`），受影响任务按派生规则回到开始前的状态（原因按派生规则重写；任务有真实尝试时跳过并列出原因），被模拟结果暂停的账号恢复执行（暂停起因都是模拟尝试：模拟的结果待核实或模拟出来的账号级错误；人工暂停与真实尝试造成的暂停不动）。返回 `{runs_ended: [批次 id], attempts_reset: 条数, orders_restored: [任务 id], orders_skipped: [{order_id, reason}], accounts_resumed: [账号 id]}`。

## 6. 飞书接入

- 应用凭证只在服务端环境变量：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`（`backend/.env` 或进程环境）。未配置时控制台显示「未配置飞书应用」（需要飞书的接口返回 409 `FEISHU_NOT_CONFIGURED`），文件导入不受影响。飞书接口报错 → 502 `FEISHU_ERROR`。
- 链接解析：`https://<租户>.feishu.cn/base/<app_token>?table=<table_id>&view=<view_id>`；`/wiki/<token>` 先调知识库接口换出 `obj_token`。
- 表格授权：飞书链接只用来定位表格，不等于授权（v1 §6.1 第 3 步）。一个多维表格（app_token，含其中全部数据表）同一时刻只授权给一个工作区（`feishu_base_grants`）。部署所有者的工作区（第一个工作区）绑定尚未授权的表格时自动登记；其他工作区由部署所有者在服务器上运行 `python cli.py feishu_grant -p workspace_id=… -p app_token=…`（`-p transfer=1` 转授、`-p revoke=1` 撤销，不带参数列出全部授权；授权给某个工作区时，其他所有工作区在该表格上仍启用的连接一律停用（含原授权工作区、表格尚未登记时所有者工作区的连接）；撤销时原工作区的连接停用。部署所有者的工作区重新启用连接、改对应或写回验收时同样登记授权（之后别的工作区要用须 `transfer=1`）。db_init 的回填会停用不持有授权的工作区里的同表连接）。解析链接、读字段、样本预览、建 / 改连接、立即读取、写回验收、写回发送都先检查授权（写回发送没有授权的行只积压、不计失败次数，flush 统计记 `waiting_grant`），无权 → 403 `FORBIDDEN`（不透露表格是否归别的工作区）。按用户的飞书授权（OAuth）是多人阶段的后续项。
- 读取：`POST /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/search`（分页 500），只读字段对应里用到的列。同一连接同时只有一次读取（咨询锁，正在读取 → 409）；读取与样本预览永远跳过连接的 `writeback_test_record`。
- 字段值解析：文本（片段数组 / 字符串）、数字、单选、日期（毫秒时间戳）、公式 / 查找引用（`{type, value: [...]}`）统一转文本、数字或日期。
- 准入（`admission`）：`approved_values`（默认 `["通过"]`）、`rejected_values`（默认 `["拒绝","建议拒绝","钓鱼"]`）、`purchaser_values`（为空表示不过滤）、`skip_purchase_status_values`（默认 `["已拍单","拿回"]`，这些行只作为历史或更新，不新建采购）、`cancel_after_sale_values`（默认 `[]`）、`import_historical`（默认 `false`）。已有任务的同键记录也带着准入规则交给 ingest（见 §2 准入变化）。
- 写回：`writeback_map` 为「结果字段 → 飞书列」。结果字段：`buyer_account`、`buyer_customer_id`、`amazon_order_no`、`purchase_status`（成功写 `已拍单`）、`total_before_tax`、`shipping`、`tax`、`total`、`card_last4`。写回目标列类型不得为公式（20）、查找引用（19）、关联（18/21）、自动编号等系统列；建连接、改写回对应、验收时读取写回列的字段类型，入队时按类型转换写回值。写回按（任务、连接、结果版本）去重，较旧版本在较新版本成功后标 `superseded`；失败按 1、2、5、10、30 分钟退避，最多 10 次。写回目标：只有主来源是飞书的任务，第一个飞书来源自动成为写回目标；文件为主的任务后来出现的同键飞书记录只追加关联，要写回须人工指定（`POST /orders/{id}/writeback-target`）。连接停用或关闭写回期间登记的真实结果照常入队（只积压不发送），重新启用 / 开启写回 / 改写回列时把尚未入队的已采购真实结果补入队列。
- 验收：在连接上指定一条测试记录，服务端写入测试值并读回比对，再把原值写回去；一致才记 `writeback_verified_at`。测试记录已关联采购任务（本工作区同一张表的任何来源记录）→ `VALIDATION`（请改用一条专用测试记录）；验收期间持有该连接的读取锁。未验收时写回队列只积压不发送，界面显示「回填待验证」。

## 7. 文件导入

- 支持 `.xlsx`、`.csv`（UTF-8 / UTF-8-BOM / GBK），10 MB 以内（超过 → 413）；`.xls` 提示另存为 xlsx。
- 标准模板列（列名与飞书统一）：平台订单号、店铺账号、收货人姓名、收货人地址、地址2、收货人城市、收货人州/省、邮编、收货人电话、AMZ订单号、买家号、买家号ID、收货人国家、ASIN、数量、收货人区、人工审核、限价、采购单价、下单时间、配送天数、建议采购日期、店铺、采购订单号、SKU、销售总额、售后状态、备注。只有平台订单号必填。
- 表头自动识别：标准列名、飞书列名及常见别名（如「买家号1」「数量1」「AMZ订单号」/「亚马逊订单号」）。用户可改对应关系并存为工作区模板（同名覆盖，覆盖时保留原创建人；保存、删除都记事件）；控制台保存前会重新读模板列表，名称与已有模板相同时先确认覆盖（写明创建人 created_by_name）；上传时自动匹配覆盖全部已对应列的模板。同一工作区上传过内容完全相同的文件时提示「这个文件已经导入过」。
- 准入：文件的准入规则 = §6 缺省值 + 文件缺省（`import_historical=true`：带 AMZ 订单号的行按历史采购登记；`cancel_after_sale_values=["已取消"]`：售后状态「已取消」视为上游取消）+ 工作区设置 `file_admission`（`PATCH /settings`）+ 预览请求里的 `admission`；实际用的规则存在批次上，提交时沿用；已有任务也做准入检查。
- 预览结论（每行一个）：`new`（新单）、`update`（已有任务，允许更新的字段有变化）、`unchanged`（与已有完全一致）、`conflict`（与另一来源或执行中的任务冲突）、`historical`（带 AMZ 订单号）、`invalid`（无平台订单号、平台订单号不可用、同批次重复，或库里没有的单命中准入规则）。另列问题（缺人审 → 待确认，缺字段 → 资料待补齐）。同一批次中同键重复的行，第一行有效，其余 `invalid`。每次预览整体替换该批次的批次行。
- 提交：逐行经 `orders.ingest`，随后分配一次；提交时某一行出错（业务校验失败或意外的数据库错误）只把该行记为无效并写明「提交失败：…」，其余行照常提交；问题行可下载（原列 + 结论 + 原因 + 原行号）。不修改用户的原文件；放弃的批次清掉原件。
- 导出：按批次或按视图导出结果 xlsx：平台订单号、状态、买家号、AMZ订单号、税前总额、运费、税费、总额、卡尾号、建议采购日期、最近更新时间、异常原因、结果来源（本系统 / 模拟 / 来源已有单号，避免把模拟单号误当真实采购；还没有成功尝试的任务为空）。

统一错误码（`code` 字段）：`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`VALIDATION`、`CONFLICT`、`ACCOUNT_BUSY`、`DEVICE_BUSY`、`ATTEMPT_IN_FLIGHT`、`IDENTITY_MISMATCH`、`ACCOUNT_NOT_REGISTERED`、`ACCOUNT_PAUSED`、`REAL_PURCHASE_DISABLED`、`LEASE_LOST`、`SLOT_DONE`、`WORKSPACE_REQUIRED`、`PLUGIN_OUTDATED`、`FEISHU_NOT_CONFIGURED`、`FEISHU_ERROR`、`INVALID_TRANSITION`、`SOURCE_CHANGED`、`GUARD_BLOCKED`、`RATE_LIMITED`、`METHOD_NOT_ALLOWED`、`INTERNAL`。

HTTP 状态：401 UNAUTHORIZED；403 FORBIDDEN（含插件入口闸），以及开始批次时的 IDENTITY_MISMATCH、ACCOUNT_NOT_REGISTERED、ACCOUNT_PAUSED、REAL_PURCHASE_DISABLED；404 NOT_FOUND（含接口不存在）；405 METHOD_NOT_ALLOWED；409 CONFLICT、ACCOUNT_BUSY、DEVICE_BUSY、ATTEMPT_IN_FLIGHT、LEASE_LOST、SLOT_DONE、WORKSPACE_REQUIRED、PLUGIN_OUTDATED、INVALID_TRANSITION、SOURCE_CHANGED、GUARD_BLOCKED、FEISHU_NOT_CONFIGURED，以及提交登记时的 ACCOUNT_PAUSED、IDENTITY_MISMATCH；400 / 413 / 422 VALIDATION（请求参数校验失败为 422「请求参数不正确」，detail.errors 与 field）；429 RATE_LIMITED（登录失败过多、登记的浏览器到了上限）；502 FEISHU_ERROR；500 INTERNAL（不带堆栈）。前端错误码表（`web/src/api/types.ts` 的 API_ERROR_CODES）、插件的错误码中文表（`extension/src/core/codes.ts` 的 SERVER_CODE_LABEL）与服务端的 `services/models.API_ERROR_CODES` 都与上面的统一错误码同序；插件界面与日志不显示原样的英文码，认不出的码显示「其他原因（插件不认识这个错误码）」。

入口限制：Host 只接受本机地址（127.0.0.1、localhost、::1）、PC_HOST 与 PC_ALLOWED_HOSTS，/api 写请求带 Origin 时也须在名单里，否则 403 `FORBIDDEN`（包括 /auth/setup 与 /auth/login）；插件接口（/plugin）另有更严的入口闸，在这一层之前执行（§5）；请求体 `POST /imports` ≤ 10 MB + multipart 余量、其他 ≤ 1 MB（分块上传同样计数）→ 超过 413；`POST /auth/login`（按 IP + 用户名）窗口 10 分钟内失败 10 次 → 429 `{code: RATE_LIMITED, message: 尝试次数过多，请稍后再试, detail: {retry_after_s}}` 并带 Retry-After（失败 = 401/404/409/422；可由 PC_LOGIN_FAIL_LIMIT / PC_RATE_WINDOW_S 调整；登录成功清掉该键的失败记录）。浏览器登记不走失败限速，数量由 PC_MAX_DEVICES 封顶（满了同样回 429 `RATE_LIMITED`，见 §5 第 1 步）。OPTIONS 一律 204（不做 CORS；发往 /plugin 的预检先过入口闸，网页来源的得到 403）。

已删除的接口（0.1.0 版的执行入口，没有占位路由）：`POST /plugin/v1/pair`，以及控制台的 `POST /devices/pairing-codes`、`POST /devices/{id}/revoke`、`POST /accounts/{id}/adopt-customer-id`。请求它们得到通用的 404 `NOT_FOUND` 或 405 `METHOD_NOT_ALLOWED`（托管了前端时都是 405，单页回退路由只认 GET；没有前端时是 404，只有 `/devices/pairing-codes` 因为路径与 `/devices/{id}` 重合仍是 405），没有专门的提示；0.1.0 版插件在心跳、登记时得到 409 `PLUGIN_OUTDATED`，开始批次时得到 422「插件版本过旧，请更新插件」。

## 9. 后台调度（`cli.py serve`）

`serve` 先检查库结构（不是当前版本就退出，见 §0），再启动 HTTP 服务（默认 `127.0.0.1:8790`，并托管 `web/dist`；以 `proxy_headers=False` 运行，对端地址取套接字对端）和后台线程（清扫与每日分配在核心线程，飞书读取与写回在飞书线程，飞书接口卡住不影响清扫）：

|任务|频率|
|---|---|
|租约清扫（含清理长期没有联系的浏览器行）|`PC_SWEEP_INTERVAL_S`（默认 30）秒|
|飞书读取|每 `PC_INTAKE_CHECK_S`（默认 30）秒查一次到期连接，各连接按 `poll_minutes`|
|飞书写回|`PC_WRITEBACK_INTERVAL_S`（默认 60）秒|
|每日分配|北京时间 00:01（每个工作区每个北京日期一次）|

后台调度调用的就是 `workflows.<任务>.run()`（与单独执行相同；清扫、读取、写回传入调度的当前时刻 `now`）；每个任务自己开事务，一次失败只记日志、不让循环退出。每日分配每个工作区每个北京日期只做一次（重启不重做）。每个任务也可单独执行：`python cli.py sweep`、`python cli.py feishu_intake [-p connection_id=1]`、`python cli.py feishu_writeback`、`python cli.py allocate [-p workspace_id=1]`（缺省 trigger=manual，等同「重新分配」）。`python cli.py user_create` 的密码缺省交互输入或读标准输入第一行（`-p password=…` 不建议，见 §0）。
