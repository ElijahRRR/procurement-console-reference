# 开发契约 v2

本文件是实现层的唯一约定：目录与分层、数据模型、状态机、分配与额度算法、护栏、执行协议、HTTP 接口。业务定稿见 [方案 v2](采购控制台方案-v2.md)。改动本文件中的任何契约，须同时改代码与测试。

## 0. 目录与分层

```
backend/                 Python 3.12+，在此目录内运行一切命令
  cli.py                 唯一命令入口：db_init / user_create / serve / allocate / sweep / feishu_intake / feishu_writeback
  registry/              接线盒：settings.py（环境变量）、db.py（连接唯一入口）、paths.py
  api/                   外部接口适配：feishu.py（飞书开放平台），只做认证、重试、分页、限速
  services/              业务积木（纯 SQL + 纯函数），全部业务判断在这里
  workflows/             后台任务：每个文件一个 run(conn_or_none, **params) -> dict 摘要
  server/                FastAPI：app.py、deps.py、routes/*.py（每个文件一个 router）
  refdata/schema.sql     幂等建表（db_init 执行）
  tests/                 pytest，真实 PostgreSQL（每个测试会话建临时库）
web/                     Vue 3 + TypeScript + Vite + Element Plus 2.14 + Tailwind 3（EasyQuick 外观）
extension/               Chrome MV3 + TypeScript + Vite（插件）
```

分层只准自上而下：`cli.py → (server | workflows) → services → api → registry`。`server` 与 `workflows` 同层，互不导入；`api` 不导入 `services`；任何层不导入入口层。路径、DSN、端口、密钥、可调参数只从 `registry` 取。

通用约定：

- 时间：库内一律 `timestamptz`（UTC）。业务日期一律**北京日期**（`Asia/Shanghai`），由 `services/clock.py` 的 `bj_today()` / `bj_date(ts)` 计算；不依赖数据库会话时区。亚马逊站点日期（算配送天数）用 `America/Los_Angeles`。
- 金额：`numeric(12,2)`，Python 侧用 `Decimal`，JSON 输出为字符串（如 `"52.00"`）。币种首期只有 USD。
- 空值：`NULL` 表示「没有或没读到」，不得当作 0。
- 工作区：除 `users`、`sessions` 外，每张业务表都有 `workspace_id`；所有查询必须带工作区条件。跨工作区访问一律返回 404（不泄露存在性）。
- 事件：每次状态变化、人工动作、来源变化都写 `procure.events`（谁、何时、什么、细节）。
- 错误：服务层抛 `services.errors.DomainError(code, message, http_status, detail)`；路由层统一转 JSON `{ "code", "message", "detail" }`。

## 1. 数据模型

完整 DDL 见 `backend/refdata/schema.sql`（schema 名 `procure`）。核心对象：

|表|含义|
|---|---|
|`workspaces` / `users` / `workspace_members` / `sessions`|工作区、控制台用户、成员关系、登录会话|
|`workspace_settings`|全局默认配送上限（初始 10 天）、模拟模式开关等|
|`buyer_accounts`|买家账号：金额区间、每日额度、优先级、配送上限覆盖值、采购/同步开关、暂停执行、执行模式与时间、默认执行设备|
|`devices` / `device_pairings`|插件安装（一个浏览器环境一个设备）、配对码|
|`feishu_connections` / `feishu_sync_runs`|飞书连接（表定位、字段对应、准入规则、写回对应、写回验收）、每次读取记录|
|`import_templates` / `import_batches` / `import_rows`|个人导入模板、上传批次、批次行（预览结论）|
|`purchase_orders`|采购任务（一笔上游采购单 = 一个任务），含原值、控制台覆盖值、状态、分配|
|`order_sources`|任务与来源记录的关联（飞书记录 / 文件行），含快照与指纹、是否写回目标|
|`purchase_attempts`|每次采购尝试（含模拟），护栏输入与裁决、提交登记时间、结果、金额|
|`execution_runs`|账号执行批次（账号级执行权租约）|
|`writebacks`|飞书写回队列（按结果版本去重）|
|`allocation_runs`|每次分配的摘要（未覆盖账号与原因）|
|`events`|事件流水|

关键唯一约束：

- `purchase_orders (workspace_id, upstream_order_no)`：同一工作区内上游采购单唯一。
- `execution_runs (account_id) WHERE ended_at IS NULL`：一个账号同时只有一个执行批次。
- `purchase_attempts (purchase_order_id) WHERE status IN 在途状态`：一笔任务同时只有一个在途尝试。
- `purchase_attempts (account_id) WHERE status IN 在途状态`：一个账号同时只执行一笔。
- `purchase_attempts (workspace_id, amazon_order_no) WHERE amazon_order_no IS NOT NULL AND NOT simulated`：同一亚马逊订单号不能回填到两笔任务（防串单）。

## 2. 采购任务状态机

`purchase_orders.status`：

|状态|中文|进入条件|
|---|---|---|
|`pending_review`|待确认|人审结果不是「通过」|
|`needs_info`|资料待补齐|已通过人审，但缺少执行所需字段（见下）|
|`conflict`|待核实|不同来源内容冲突，或历史/外部单号与本系统记录矛盾|
|`queued`|待分配|可执行，尚未分配账号|
|`assigned`|已分配|已有账号（建议采购日期可能在未来）|
|`executing`|采购中|有在途尝试|
|`result_unknown`|结果待核实|已登记提交但未确认结果|
|`exception`|异常|本任务暂停（超限价、缺货、超配送时长、页面错误重试后仍失败等），原因见 `status_reason`|
|`purchased`|已采购|有成功尝试（或来源带来的外部单号）|
|`cancelled`|已取消|采购开始前上游取消，或人工取消|
|`repurchase_pending`|待决定重采|亚马逊取消了采购订单（第二个 PR 由物流同步触发；本 PR 提供人工入口）|
|`closed`|已关闭|人工决定不重采|

执行所需字段（缺一即 `needs_info`）：有效 ASIN、有效数量 >0、采购单价、有效限价、建议采购日期（来源给出或可计算）、收件人姓名、地址 1、城市、州、邮编、电话。

「有效值」= 控制台覆盖值优先，否则来源原值：`asin_eff = coalesce(override_asin, asin)`，数量、限价同理。商品小计 `subtotal_eff = unit_price × quantity_eff`。

`services/orders.derive_status(order)` 只用于采购开始前的状态（`pending_review / needs_info / conflict / queued / assigned / cancelled / purchased(外部)`），优先级：上游取消 → `cancelled`；外部单号 → `purchased`；未通过人审 → `pending_review`；冲突未解决 → `conflict`；缺字段 → `needs_info`；已分配 → `assigned`；否则 `queued`。

迁移只能经 `services/orders.transition(conn, order, to, reason, actor)`，它校验下表并写事件：

|从|允许到|
|---|---|
|pending_review / needs_info / conflict / queued / assigned|彼此之间（由 derive_status 决定）、`executing`（仅 assigned）、`cancelled`|
|executing|`assigned`（未提交即中止或可重试的失败）、`exception`、`result_unknown`、`purchased`、`cancelled`（未提交时收到上游取消）|
|result_unknown|`purchased`（人工核实已下单）、`assigned` / `queued`（人工核实未下单）|
|exception|派生状态（人工恢复后重新校验）、`cancelled`、`closed`|
|purchased|`repurchase_pending`（亚马逊取消）|
|repurchase_pending|派生状态（同意重采，形成新尝试）、`closed`|
|cancelled|派生状态（人工撤销取消）|

来源更新（`ingest`）对不同状态的影响：

- 开始前（pending_review / needs_info / conflict / queued / assigned）：更新原值并重新派生；已分配但金额已不在账号区间内则解除分配回到待分配；覆盖值不受影响，差异写事件。
- 执行中 / 待核实 / 已采购：不改执行相关原值，只记录「上游在采购开始后修改了 X」事件并置 `needs_attention`。
- 上游取消：开始前 → `cancelled` 并解除分配；执行中且未登记提交 → 置取消标记，插件下一次进度上报得到 `continue=false` 后中止，任务 → `cancelled`；已登记提交 → `result_unknown` 并注明「执行中收到取消」；已采购 → 保持 `purchased`，置 `needs_attention`（提醒人工处理亚马逊订单）。
- 跨来源：任务首次出现的来源种类为主来源。另一种来源送来同键记录且执行相关字段（ASIN、数量、限价、单价、收件信息、建议采购日期）不同 → 开始前转 `conflict`，不覆盖；字段相同只追加来源关联。同种来源（同一飞书记录或新批次文件）视为正常更新。
- 外部单号：开始前出现 → `purchased`（创建 `kind='external'` 的尝试记录单号与买家号）；本系统已有不同单号或正在执行 → `conflict`。

## 3. 分配与额度

### 3.1 额度

账号 A 在北京日期 D 的已用额度 `used(A, D)` = `purchase_attempts` 中 `account_id = A`、`bj_date = D`、`simulated` 与当前批次相同、状态不在 (`failed`, `aborted`) 的尝试数（在途、待核实、成功都占用；人工核实「未下单」后该尝试改为 `failed`，释放额度）。一次成功计 1 单，与商品数量无关。`bj_date` 取尝试创建时的北京日期，跨零点不变。

### 3.2 分配算法（`services/allocation.allocate(conn, workspace_id, today, trigger)`）

参与的账号：未归档、`purchase_enabled`、未 `execution_paused`、站点相符。参与的任务：`queued`，以及 `assigned` 且 `assignment_kind='auto'` 且无在途尝试的任务（自动分配可重算）；`assignment_kind='manual'` 的任务固定不动，但占用计划额度。

计划日期 `plan(t) = max(suggested_purchase_date, today)`。按计划日期从早到晚逐日处理，日期 D 内：

- `cap(A, D) = daily_limit − used(A, D) − fixed(A, D)`，`fixed` 为 D 日固定（人工）分配且尚无尝试的任务数。
- `covered(A, D)`：D 日 A 已有尝试或已有固定分配。
- `eligible(t, A)`：`min_amount ≤ subtotal_eff(t) ≤ max_amount`（端点含；`max_amount` 为空表示不限）且 `cap(A, D) > 0`。

1. **保底**：未覆盖且有额度的账号与当天任务做最大二分匹配（增广路）。账号按（可选任务数升序、优先级降序、名称升序）尝试；候选任务按（可选账号数升序、建议采购日期、下单时间、id）。匹配成功的标注「保底：当天首单」。这保证 A 只接 20–30、B 接 20–50、有 25 和 45 两单时 A 得 25、B 得 45。
2. **填充**：剩余任务按（建议采购日期、下单时间、id）依次分给可选账号中优先级最高者，同优先级按名称升序；标注「按优先级填充」。
3. 分不出去的任务留在 `queued`，`status_reason` 写明原因：「金额 $X 不在任何启用账号的区间内」或「匹配账号当天额度已满」。未被覆盖的账号在 `allocation_runs.uncovered` 写明原因：「没有金额匹配的订单」「当天额度已用完」「订单数量不足」。

人工改派（`assign_manual`）：目标账号必须启用、金额区间匹配、计划日期当天有剩余额度；成功后 `assignment_kind='manual'`。关闭采购开关只影响新分配；暂停执行的账号不参与自动分配，已分配任务保留。

分配触发：来源导入/同步后、人工点击「重新分配」、账号配置变化后、每天北京时间 00:01（后台调度）。

### 3.3 执行时再校验（领取任务时）

领取条件：任务 `assigned` 给该账号、`suggested_purchase_date ≤ bj_today()`、人审通过、未上游取消、无冲突、`used(A, today) < daily_limit`、金额仍在区间内。顺序：建议采购日期、下单时间、id；`FOR UPDATE SKIP LOCKED`。金额已不在区间 → 解除分配回 `queued` 并跳过。

## 4. 护栏（`services/guard.evaluate`）

插件在结算页、点击下单前上报事实：

```json
{
  "items": [{"asin": "B0CZ164HQ2", "quantity": 1, "unit_price": "41.97"}],
  "subtotal": "41.97", "shipping": "0.00", "tax": "2.52",
  "total_before_tax": "41.97", "total": "44.49",
  "gift_card_amount": null,
  "currency": "USD",
  "delivery": {"text": "Arriving Nov 8", "date": "2026-11-08", "days": null},
  "ship_to": {"postal_code": "32960"},
  "card_last4": "7860",
  "fulfillment": "amazon"
}
```

逐项判定（全部通过才放行；结果写入尝试的 `guard_verdict`）：

|检查|规则|拦截码|
|---|---|---|
|商品|items 恰好一项，ASIN 与有效 ASIN 相同，数量与有效数量相同|ITEM_MISMATCH|
|邮编|`ship_to.postal_code` 前 5 位与任务邮编前 5 位相同|ZIP_MISMATCH|
|金额区间|subtotal 在账号区间内（端点含）|SUBTOTAL_OUT_OF_RANGE|
|限价|`total + (gift_card_amount or 0)` ≤ 有效限价（相等放行）|PRICE_OVER_CAP|
|配送时长|配送天数 = `delivery.date − 站点今天`（洛杉矶日期），无日期时用 `delivery.days`；≤ 有效配送上限（账号覆盖值或全局默认）|DELIVERY_TOO_LONG|
|数据可靠|total、subtotal 可解析，配送天数可得，币种为 USD|DATA_UNRELIABLE|
|卡尾号|账号设置了期望卡尾号时必须相同|CARD_MISMATCH|

`fulfillment` 只记录，不拦截。拦截 → 尝试 `failed`、任务 `exception`（原因为拦截码的中文说明），其他任务继续。

## 5. 执行协议（插件 ↔ 服务端）

所有插件请求带 `Authorization: Bearer <设备令牌>`，前缀 `/plugin/v1`。设备令牌只存哈希。

1. **配对**：控制台生成 8 位配对码（10 分钟有效、一次性）；插件 `POST /pair {code, device_name, browser, ext_version}` → `{device_id, device_token, workspace_name}`。
2. **心跳**：`POST /heartbeat {ext_version, identity?}`，每 60 秒；返回设备、绑定账号的有效配置（模式、执行时间、有效配送上限、开关）、`bj_date`、`server_time`、`simulation_only`、`identity_status`。
3. **身份**：`identity = {signed_in, customer_id, site, page_url}`。服务端与绑定账号的 `amazon_customer_id` 比对：`match` / `mismatch` / `signed_out` / `unknown`（账号未登记 ID）。控制台可「采用插件识别的 ID」。
4. **开始批次**：`POST /runs {trigger: manual|scheduled, simulated: true}`。要求：设备已绑定账号、身份 `match` 且 10 分钟内上报过、账号未暂停执行、`simulated=true`（本阶段服务端拒绝非模拟批次，码 `REAL_PURCHASE_DISABLED`）。账号已有未结束批次 → 409 `ACCOUNT_BUSY`，附持有者设备名与开始时间。租约 180 秒，心跳续期。
5. **批次心跳**：`POST /runs/{id}/heartbeat` → `{lease_expires_at, stop, stop_reason}`（账号被暂停或批次被清扫时 `stop=true`）。
6. **领取**：`POST /runs/{id}/next` → `{attempt: {...}}` 或 `{attempt: null, reason}`。同一批次已有在途尝试时 409 `ATTEMPT_IN_FLIGHT`。尝试载荷：attempt_id、upstream_order_no、asin、quantity、unit_price、price_cap、max_delivery_days、amount_range、收件信息、expected_card_last4、simulated。
7. **进度**：`POST /attempts/{id}/progress {stage, detail}` → `{continue, cancel_reason}`；上游已取消且未登记提交时 `continue=false`。
8. **护栏**：`POST /attempts/{id}/guard {事实}` → `{verdict: pass|block, code, reasons, checks}`。
9. **提交登记**：`POST /attempts/{id}/submitting` → 200 才允许点击下单；护栏未通过、批次失效、任务已取消时 409。登记即写 `submitted_at`（可能已下单）。
10. **等待验证**：`POST /attempts/{id}/verifying {note}`（银行人工验证），任务与名额保留。
11. **结果**：`POST /attempts/{id}/result {outcome: succeeded|failed|unknown, amazon_order_no, amounts, card_last4, delivery, error_code, error_detail}`。
12. **结束批次**：`POST /runs/{id}/finish {reason}`。

结果处理（`services/execution.report_result`）：

|情况|尝试|任务|账号|
|---|---|---|---|
|succeeded（单号非空）|succeeded|purchased；结果版本 +1，非模拟且有写回目标时入写回队列|—|
|已登记提交后的任何非成功|unknown|result_unknown|暂停执行（原因「结果待核实」）|
|未提交，账号级错误（LOGIN_REQUIRED、ACCOUNT_RESTRICTED、CARD_DECLINED、CAPTCHA_ENCOUNTERED、IDENTITY_MISMATCH）|failed|assigned（任务保留）|暂停执行|
|未提交，PAGE_LOAD_FAILED|failed|首次 → assigned（自动重试一次）；第二次 → exception|—|
|未提交，任务级错误（OUT_OF_STOCK、QUANTITY_UNAVAILABLE、ADDRESS_FAILED、CART_MISMATCH、护栏拦截码等）|failed|exception|—|
|未提交，插件主动中止（上游取消）|aborted|cancelled|—|

租约清扫（`services/execution.sweep`，每 30 秒）：批次租约过期 → 批次结束（`lease_expired`）；其在途尝试若未登记提交 → `aborted`，任务回 `assigned`；已登记提交 → `unknown`，任务 `result_unknown`，账号暂停执行。

模拟：模拟尝试的单号形如 `SIM-<日期>-<id>`，不写回飞书。`POST /api/v1/simulation/reset` 把所有模拟尝试标为 `aborted`（细节注明「已清除模拟结果」），受影响任务按派生规则回到开始前的状态，被模拟结果暂停的账号恢复执行。

## 6. 飞书接入

- 应用凭证只在服务端环境变量：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`（`backend/.env` 或进程环境）。未配置时控制台显示「未配置飞书应用」，文件导入不受影响。
- 链接解析：`https://<租户>.feishu.cn/base/<app_token>?table=<table_id>&view=<view_id>`；`/wiki/<token>` 先调知识库接口换出 `obj_token`。
- 读取：`POST /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/search`（分页 500），只读字段对应里用到的列。
- 字段值解析：文本（片段数组 / 字符串）、数字、单选、日期（毫秒时间戳）、公式 / 查找引用（`{type, value: [...]}`）统一转文本、数字或日期。
- 准入（`admission`）：`approved_values`（默认 `["通过"]`）、`rejected_values`（默认 `["拒绝","建议拒绝","钓鱼"]`）、`purchaser_values`（为空表示不过滤）、`skip_purchase_status_values`（默认 `["已拍单","拿回"]`，这些行只作为历史或更新，不新建采购）、`cancel_after_sale_values`（默认 `[]`）、`import_historical`（默认 `false`）。
- 写回：`writeback_map` 为「结果字段 → 飞书列」。结果字段：`buyer_account`、`buyer_customer_id`、`amazon_order_no`、`purchase_status`（成功写 `已拍单`）、`total_before_tax`、`shipping`、`tax`、`total`、`card_last4`。写回目标列类型不得为公式（20）、查找引用（19）、关联（18/21）、自动编号等系统列。写回按（任务、连接、结果版本）去重，较旧版本在较新版本成功后标 `superseded`；失败按 1、2、5、10、30 分钟退避，最多 10 次。
- 验收：在连接上指定一条测试记录，服务端写入测试值并读回比对；一致才记 `writeback_verified_at`。未验收时写回队列只积压不发送，界面显示「回填待验证」。

## 7. 文件导入

- 支持 `.xlsx`、`.csv`（UTF-8 / UTF-8-BOM / GBK），10 MB 以内；`.xls` 提示另存为 xlsx。
- 标准模板列（列名与飞书统一）：平台订单号、店铺账号、收货人姓名、收货人地址、地址2、收货人城市、收货人州/省、邮编、收货人电话、AMZ订单号、买家号、买家号ID、收货人国家、ASIN、数量、收货人区、人工审核、限价、采购单价、下单时间、配送天数、建议采购日期、店铺、采购订单号、SKU、销售总额、售后状态、备注。只有平台订单号必填。
- 表头自动识别：标准列名、飞书列名及常见别名（如「买家号1」「数量1」「AMZ订单号」/「亚马逊订单号」）。用户可改对应关系并存为个人模板。
- 预览结论（每行一个）：`new`（新单）、`update`（已有任务，允许更新的字段有变化）、`unchanged`（与已有完全一致）、`conflict`（与另一来源或执行中的任务冲突）、`historical`（带 AMZ 订单号）、`invalid`（无平台订单号或同批次重复）。另列问题（缺人审 → 待确认，缺字段 → 资料待补齐）。同一批次中同键重复的行，第一行有效，其余 `invalid`。
- 提交：逐行经 `orders.ingest`；问题行可下载（原列 + 结论 + 原因）。不修改用户的原文件。
- 导出：按批次或按视图导出结果 xlsx：平台订单号、状态、买家号、AMZ订单号、税前总额、运费、税费、总额、卡尾号、建议采购日期、最近更新时间、异常原因。

## 9. 后台调度（`cli.py serve`）

`serve` 启动 HTTP 服务（默认 `127.0.0.1:8790`，并托管 `web/dist`）和后台线程：

|任务|频率|
|---|---|
|租约清扫|30 秒|
|飞书读取|每个连接按 `poll_minutes`|
|飞书写回|60 秒|
|每日分配|北京时间 00:01|

每个任务也可单独执行：`python cli.py sweep`、`python cli.py feishu_intake [-p connection_id=1]`、`python cli.py feishu_writeback`、`python cli.py allocate`。
