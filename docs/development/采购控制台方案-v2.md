v1 §11 待定细节采用以下默认值（所有者未提出修改，开发按此执行，可在设置中调整的已注明）：

1. 「每个账号至少 1 单」按北京时间当天统计：当天已有采购尝试或已有计划在当天执行的分配，即视为已覆盖。
2. 额度按采购尝试**开始时的北京日期**计算。跨零点仍在执行或结果待核实的尝试，继续占用开始那天的额度，不扣新一天的额度；防重复保护照常保留。
3. 采购成功后被取消，不返还当天额度（额度统计的是下单次数）。
4. 错过采购时段：插件上线后当天内补执行；跨天不自动补，转入次日计划。
5. 账号配置修改与正在结算的任务：插件在提交前由服务端按**最新已确认配置**做护栏裁决。

## 2. 在 v1 之上的取舍

- **执行权完全在服务端裁决。** 每个买家账号同一时刻只有一个执行批次（跨电脑、跨浏览器环境、跨标签页），每笔采购任务同一时刻只有一个在途尝试，由数据库唯一索引保证。早期实现「同一买家号不会两处同时登录」的前提不再采用。
- **点击下单前必须先向服务端登记「即将提交」。** 登记成功才允许点击；登记之后的任何失败、断网、超时，一律进入「结果待核实」并暂停该账号，不会自动重买。
- **护栏在服务端。** 插件只上报结算页读到的事实（商品、数量、小计、税运费、总额、配送日期、邮编、卡尾号），通过与否由服务端判定。
- **飞书写回分两步启用。** 字段对应与写回目标在连接时设置；只有在测试记录上验收通过后才真正写回，否则界面显示「回填待验证」。模拟结果永不写回。
- **首个 PR 只允许模拟执行。** 服务端在本阶段拒绝一切非模拟的执行批次；模拟结果可在控制台一键清除，任务回到原来的待采购状态。
- **工作区隔离从第一天就做。** 所有业务表都带工作区（跨工作区的飞书表格授权登记等例外见开发契约 §0）；控制台用户、飞书授权、亚马逊买家账号三种身份分开保存。首期只有所有者一个用户。

## 3. 飞书「订单中心」字段对应（默认值）

依据所有者提供的示例导出（47 列，「采购订单」视图）。控制台连接向导会读取实际字段类型，以下仅为默认对应，可在向导中改。

|系统字段|飞书列|用途|
|---|---|---|
|上游采购单唯一键|平台订单号|去重与跨来源合并（= 采购订单号 + SKU）|
|订单行 ID|order_line_id|保留，供以后与 WalmartAPI-Contral 对账|
|下单时间|下单时间|算建议采购日期（北京时间）|
|店铺 / 采购订单号 / SKU|店铺、采购订单号、SKU|展示|
|销售总额|销售总额|展示|
|采购单价|采购单价|账号金额区间匹配：单价 × 数量|
|数量|数量|采购数量|
|建议采购日期|建议采购日期|日期门槛|
|售后状态|售后状态|上游取消信号（取值在向导中设置）|
|人工审核|人工审核|准入：默认取值「通过」|
|采购方|采购方|只接本系统负责的采购方（如「自采购1」），在向导中设置|
|采购状态|采购状态|已为「已拍单」「拿回」的行不新建采购|
|AMZ订单号|AMZ订单号|已有单号的行视为历史采购，不重新下单|
|ASIN|ASIN（缺失时用「来源码」）|采购商品|
|限价|限价|结算总额上限|
|收件信息|收货人姓名、收货人地址（或地址1）、地址2、收货人城市、收货人州/省、邮编、收货人电话、国家|填写收货地址|

## 5. 明确不做

- 反指纹、反检测、验证码绕过：碰到验证码或风控即暂停该账号并转人工。
- 上传或导出 Cookie：插件不申请 `cookies` 权限，登录状态留在浏览器里。
- 改写或伪造物流轨迹（v1 §8）。
- 连接 WalmartAPI-Contral 数据库（Q2）。

账号与店铺的平台风险由所有者承担（见所有者 2026-10-20 的合规进货方案）；系统只负责可控、可审计、出问题能停。
