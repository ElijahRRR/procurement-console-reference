2. 额度按采购尝试**开始时的北京日期**计算。跨零点仍在执行或结果待核实的尝试，继续占用开始那天的额度，不扣新一天的额度；防重复保护照常保留。

5. 账号配置修改与正在结算的任务：插件在提交前由服务端按**最新已确认配置**做护栏裁决。

## 2. 在 v1 之上的取舍

- **谁登录着买家号，谁就能执行它的任务。** 买家号的身份是亚马逊 customerId（买家号 ID），由插件从当前页面读出；账号由所有者在控制台登记并填上买家号 ID，浏览器由插件自动登记，两者之间没有固定关系，也没有逐台浏览器的人工步骤（2026-11 修订，见 §6）。
- **分配有两种方式。** 来源（飞书表格或上传的表格）里写了买家号的订单按来源指定分配，没写的由系统自动分配；来源指定的任务绝不悄悄落到别的账号（2026-11 修订二，见 §7）。
- **执行权完全在服务端裁决。** 每个买家账号同一时刻只有一个执行批次（跨电脑、跨浏览器环境、跨标签页），每个浏览器同一时刻也只有一个执行批次，每笔采购任务同一时刻只有一个在途尝试，定时批次每个账号每个时间点每天只执行一次，都由数据库唯一索引保证。早期实现「同一买家号不会两处同时登录」的前提不再采用。
- **点击下单前必须先向服务端登记「即将提交」。** 登记成功才允许点击；登记之后的任何失败、断网、超时，一律进入「结果待核实」并暂停该账号，不会自动重买。
- **护栏在服务端。** 插件只上报结算页读到的事实（买家号 ID、商品、数量、小计、税运费、总额、配送日期、邮编、卡尾号），通过与否由服务端判定。
- **飞书写回分两步启用。** 字段对应与写回目标在连接时设置；只有在测试记录上验收通过后才真正写回，否则界面显示「回填待验证」。模拟结果永不写回。
- **首个 PR 只允许模拟执行。** 服务端在本阶段拒绝一切非模拟的执行批次；模拟结果可在控制台一键清除，任务回到原来的待采购状态。
- **工作区隔离从第一天就做。** 所有业务表都带工作区（跨工作区的飞书表格授权登记等例外见开发契约 §0）；控制台用户、飞书授权、亚马逊买家账号三种身份分开保存。浏览器在登记时归属一个工作区，之后不变；买家号 ID 只在它所属的工作区里找账号。首期只有所有者一个用户。

分配方式修订（§7）增加的验收条目共 10 条，列在 §7.5，同样全部以自动化测试覆盖。其中第 10 条改写了上一段里「结算页读到的买家号不是批次账号的，护栏拦截」之后的落地：这一笔提交前中止、任务回已分配、批次结束，不进异常、不暂停账号。

## 5. 明确不做

- 反指纹、反检测、验证码绕过：碰到验证码或风控即暂停该账号并转人工。
- 上传或导出 Cookie：插件不申请 `cookies` 权限，登录状态留在浏览器里。
- 改写或伪造物流轨迹（v1 §8）。
- 连接 WalmartAPI-Contral 数据库（Q2）。

账号与店铺的平台风险由所有者承担（见所有者 2026-10-20 的合规进货方案）；系统只负责可控、可审计、出问题能停。

## 6. 2026-11 修订：执行入口

定稿：2026-11-18。本节取代前文与 v1 里关于「配对码、把浏览器环境绑定到买家账号、默认执行设备、撤销设备授权」的写法，与它们冲突处以本节为准。实现细节见 [开发契约 v2](开发契约-v2.md) §1.2、§4、§5、§8、§10；参考项目的执行逻辑与逐项对照见 [参考插件执行逻辑](参考插件执行逻辑.md)。

### 6.1 所有者的反馈

第一版的入口是：控制台生成配对码 → 插件填码配对 → 在控制台把设备绑定到账号 → 等身份一致，账号没登记买家号 ID 时再点一次「采用此 ID」。每个浏览器环境都要走一遍，太麻烦。插件本来就读得到当前登录的买家号，所有者要求照参考项目（小蜜蜂 2.5.5）的逻辑做：**插件读出当前登录的 customerId，按它领任务。**

### 6.2 参考项目的做法

参考插件没有登录、令牌、配对或绑定：人在亚马逊订单历史页点按钮时，从页面里现取 customerId，把它当唯一参数去拉任务；任务归谁由服务端订单行上写的买家号决定（服务端按买家号 ID 筛选是推断，客户端代码里看不到）。在订单行上写买家号这一点，本项目随后也采纳了，与自动分配并存（§7）。

- **照做的是主线**：浏览器里登录着哪个买家号，就按哪个买家号领任务；与哪台电脑、哪个浏览器无关。
- **不照搬的**：请求里只有一个 customerId、没有任何凭据；每次点按钮都上传买家 Cookie；物流同步上传整页 HTML；点击下单前不向服务端登记，下单之后回传不成就没有下文；批次只锁在页面变量里。

### 6.3 新流程

1. **装上插件即可。** 没有必填的设置。插件自己生成令牌，向本机的服务端自动登记；令牌只是会话标识（把批次、尝试、回执归到同一个浏览器），不代表身份。
2. **登录买家号，打开亚马逊页面。** 插件读出登录状态与买家号 ID（customerId）并上报。
3. **买家号的身份就是这个 ID。** 账号仍由所有者在控制台登记（名称、金额区间、额度等）并填上买家号 ID；账号上登记了哪个 ID，任何登录着这个买家号的浏览器都能执行它的任务。
4. **没登记过的买家号**，控制台「账号」页把它列为「待登记的买家号」：所有者点一次「登记」（确认名称、区间、额度），或填到已有账号上，或忽略。插件不自动创建账号。
5. **开始执行**时插件报上当前页面读到的买家号 ID，服务端按它找账号、开批次；之后的领取、进度、护栏、提交登记、结果、回执与原来相同。
6. **定时执行**由任何一个登录着该买家号的浏览器到点触发，服务端按（账号、北京日期、时间点）保证只执行一次；不再有「默认执行设备」。那个时间点的批次还在执行时，别的浏览器得到的答复是这个账号正在别处执行，下一分钟再问；它没跑完就结束（浏览器崩了、租约过期）时，由当时在线的另一个浏览器补上；正常结束之后才算这个时间点今天执行过。

任务分给哪个账号仍由服务端决定，执行入口的修订不涉及分配。分配方式随后另行修订（§7）：来源行写了买家号的按来源指定，这一点与参考项目在订单行上写买家号的做法相同；没写的由服务端按规则自动分配（金额区间、每日额度、优先级），这是参考项目没有的。

### 6.4 保留的保护

- **插件接口只接受本机。** 对端必须是回环地址、不带代理转发头、Host 必须是本机名、拒绝网页来源、POST 只收 JSON。能访问本机端口的程序视为所有者自己，所以可以不要配对码，也不必逐台审批；跨机器部署需要另加接入密钥，本次不做，服务端直接拒绝非本机的插件请求。
- **没登记的买家号不能开始执行。** 登记这一步由所有者在控制台做，插件代替不了。
- **执行权仍由服务端裁决。** 同一账号同时只有一个未结束批次，同一浏览器同时只有一个未结束批次，一笔任务同时只有一个在途尝试（唯一索引 + 租约）。去掉绑定之后同一个买家号可以同时登录在两个浏览器里，互斥只能按账号裁决。
- **每一步都复核登录的还是不是这个买家号。** 开始批次、领取、进度、提交登记都要求浏览器最新上报的登录买家号就是批次账号登记的那个，且 10 分钟内上报过；结算页事实里再带一次买家号 ID，由护栏核对。执行中途换了买家号：未提交的那一笔中止、任务回已分配、不暂停账号；已登记提交的照常收结果。结算页当场读到的不是批次账号的买家号时落地相同（提交前中止、回已分配、不进异常、不暂停账号），服务端另把这个批次结束，免得同一批次马上再领到同一笔（§7.6）。
- **提交登记之后不自动重买、服务端护栏、本阶段只允许模拟执行、模拟结果不写回飞书**，一处不动。
- **不读、不上传 Cookie，不上传页面 HTML，不做反检测。** 买家号 ID 只从页面的内联脚本里读：读到的几个值不一致时当作没读到；页面自己没有 ID、而回显的文本把 customerId 写进了内联脚本时仍可能读错（残余风险见插件 README「还没有实机核实的浏览器行为」），接入真实下单之前改为只认路径白名单里的页面。

## 7. 2026-11 修订二：来源指定买家号

定稿：2026-11-18。本节修订前文与 v1 里「任务归哪个账号只由控制台自动分配或人工调整」的写法，与它们冲突处以本节为准。实现细节见 [开发契约 v2](开发契约-v2.md) §1、§1.2、§2.1、§3.2、§3.3、§7、§8、§10。

### 7.1 所有者的决定

「分配方式需要两种都要。在表里填写则直接读取，没写可以自动分配。」

参考项目是在导入的表格里逐单写买家号；本项目第一版只有自动分配和人工改派。现在两种并存：来源（飞书表格或上传的表格）里写了买家号的订单按**来源指定**分配，没写的照旧由系统自动分配。界面与文档统一叫「来源指定」。

### 7.2 规则

1. **怎么算指定。** 来源行没有可信的 AMZ 订单号，且「买家号ID」或「买家号」填了，这一行就指定了采购账号。两列都空，自动分配。
2. **怎么对应账号。** 买家号 ID 按账号登记的 ID 对应；买家号按账号名称对应（忽略空格、全半角、大小写差异）；两列都填以 ID 为准，名称指向另一个账号时不分配，提示改正其中一个。
3. **带 AMZ 订单号的行不表态。** 这两列此时只是「谁买的」的记录（历史采购、本系统的写回），既不设置也不清除任务上的指定。单号格式不对不算可信，指定照常生效。
4. **绝不悄悄落到别的账号。** 指定的买家号没有登记、账号已归档、ID 与名称指向不同账号，或指定的账号此刻接不了（站点不符、金额不在区间、当天额度已满、每日上限为 0、已关闭采购开关、已暂停执行），任务留在「待分配」，写明原因和下一步；条件满足后的分配自动到位。
5. **没读到不等于清空，按列算。** 飞书表里配着的买家号列找不到（被改名或删除）、或字段对应里没给它配列，这一列的指定保持上次读到的内容，另一列照常读取、照常生效。配着的列找不到时，没有 AMZ 订单号的新记录暂不接收（读不出它有没有指定，建了就会被自动分配），恢复这一列或改字段对应后自动接收；提示在控制台的连接卡片上一直显示（状态点仍是「读取正常」），读取记录与立即同步的结果里也列出。只取消一个字段的对应是所有者自己的设置，不提示、不挡新记录，也不清掉经那一列写下的指定。上传的表格没有「买家号ID」或「买家号」列，同样只算那一列没读到。单元格是表格错误值（#N/A 等），当作一个读不出的指定，任务留在待分配并提示在来源里改正，不会被当成留空而自动分配，也不会分给名叫 #N/A 的账号。「无」「—」这类占位写法按没写处理。
6. **优先级：人工改派 > 来源指定 > 自动分配。** 指定仍遵守账号自己的金额区间、站点、每日额度、采购开关和暂停状态。来源指定的任务先于自动任务占用账号当天的额度，并算作这个账号当天已覆盖。
7. **来源改了就跟着改。** 飞书里改了买家号，下次读取后还没开始的任务改到新账号；清空则回到自动分配。任何状态都记下新的指定并写事件「来源指定的买家号变了」，不产生冲突，不置「需要留意」；采购已经开始的那一次不受影响，本系统已经真实采购成功的任务不再改指定。任务已有指定时，另一种来源第一次送来的不同指定（或一条来源第一次读到的那一列）不采用：预览与读取结果的问题里说明，任务时间线上记「来源指定未采用」；这条来源之后再改买家号，按改后的应用；它清空一个当初没被采用的买家号，不会清掉任务现有的指定。来源送来的指定在它读到的列上与任务现有的相同，什么都不改（例如导出文件原样重新上传）。
8. **人工改派之后。** 任务留在改派账号期间不跟随来源的指定（来源改了照样记下）；解除分配后，下一次分配仍按来源指定：指定的账号接得了就分给它，接不了就停在待分配并写明原因。
9. **同意重采沿用原来的指定。** 之前指定过就还给那个账号，之前是自动就还是自动。
10. **领取时再核一遍。** 指定变了而分配还没重算时（中止后回已分配、清除模拟结果、核实未下单、异常恢复、升级之后），原账号的插件领不到这笔任务，服务端把它退回待分配。插件本身不用改，它不看分配方式。
11. **待登记的买家号。** 来源指定了、还没有账号登记的买家号 ID 也列在「账号与浏览器」的「待登记的买家号」里（没有浏览器登录着它也列出），写明指定了几笔任务；登记或填到已有账号后，这些任务立刻分给它。新建账号、改账号名称、改买家号 ID 都会立即重新分配；忽略或恢复一个来源指定了的买家号 ID 也会重新分配一次：指定它的待分配任务的说明随即写上或去掉「已被忽略」，别的待分配任务照常分配。
12. **导出。** 结果文件的「买家号」「买家号ID」两列写采购用的账号（名称与它登记的买家号 ID），还没采购的写来源指定的两列（一列不丢），另有一列「分配账号」写当前分配。这样导出文件原样再上传，指定、状态、账号都不变；改一改再上传，也不会把系统自动分配的结果变成来源指定。

### 7.3 特意没做的

- **控制台没有「清除指定」的动作。** 指定是来源里的内容：要取消就在飞书里清空（上传的表格见下面第三条），临时换账号用人工改派（改派优先于来源指定）。
- **指定不越过账号的金额区间与额度。** 填了买家号也不能让一个账号买区间外的订单、超过每日上限，采购开关和暂停状态同样有效；接不了就留在待分配并写明原因，由所有者调整账号配置、在来源里改正，或人工改派。
- **文件来源不能靠空着重新上传来清除指定。** 每次上传都是一批新的行，空格子读不出「以前填过、现在清掉了」。要改指定就重新上传并填上新的买家号；要换账号也可以人工改派。飞书来源可以直接清空。

### 7.5 验收

以下 10 条全部以自动化测试覆盖（后端用例的说明里写明对应第几条）：

1. 来源行没有 AMZ 订单号、填了买家号 ID → 任务分给登记了这个 ID 的账号，分配方式「来源指定」；只填买家号 → 分给同名账号（忽略空格、全半角、大小写差异）；两列都空 → 自动分配。
2. 来源指定的买家号没有登记、已归档、ID 与名称指向不同账号、金额不在区间、当天额度已满、账号关闭采购开关或暂停执行 → 任务留在待分配并写明原因，绝不分给别的账号。
3. 带可信 AMZ 订单号的来源行不改变任务的指定（写回读回来仍是 unchanged；同意重采后仍分给原来指定的账号）。
4. 飞书里改了买家号 → 下次读取后任务改到新账号；清空 → 回到自动分配；来源表里找不到买家号列 → 那一列不改指定、没有 AMZ 订单号的新记录暂不接收，并在读取结果、读取记录和连接卡片上提示；只取消一个字段的对应不清除经那一列写下的指定；占位写法（无、—）按没写处理；表格错误值不当成留空。
5. 人工改派后留在改派账号期间不跟随来源；解除分配后下一次分配仍按来源指定（指定的账号接得了就分给它）。
6. 指定变了而分配还没重算时，原账号领不到这笔任务（领取时复核）。
7. 旧库升级后，来源里早已填好买家号、没有真实采购成功的任务（含模拟采购成功、已取消的）带上指定；重复升级不改数据。
8. 来源指定但未登记的买家号 ID 出现在「待登记的买家号」里；登记（新建账号或填到已有账号）后任务立刻分给它。
9. 重复分配不产生任务写入和事件。
10. 结算页读到的买家号不是批次账号的买家号 → 这一笔提交前中止、任务回已分配、批次结束，不进异常、不暂停账号。

### 7.6 一并做的执行入口收尾

- **结算页读到的不是批次账号的买家号**（护栏买家号一项拦截，验收第 10 条）：第一版按护栏拦截把任务转异常；现在按中止处理，这一笔提交前中止、任务回已分配、不进异常、不暂停账号，服务端同时把这个批次结束。插件不再上报这一笔的结果，也不用自己结束批次；登录回原来的买家号后重新开始执行，会再领到这一笔。
- **插件接口多一道闸**：带着代理转发请求头（X-Forwarded-For、Forwarded、X-Real-IP、Via）的请求一律拒绝。代理不一定带这些头，所以本机的反向代理仍然不要转发 `/plugin` 路径。
- **旧版插件还在调的配对接口**留了一个占位，只回「插件版本过旧，请更新插件」；配对码与设备绑定没有恢复。
- 历史批次的结束原因「浏览器的授权已撤销（旧版）」在服务端、控制台、插件三处统一成同一句。

### 7.7 升级

停服务 →（建议先用 `pg_dump` 备份库）→ `python cli.py db_init` → 启动 → 在控制台点一次「重新分配」→ 重新加载插件（控制台前端重新构建）。`db_init` 在给任务表加上指定两列的那一次，把来源里早已填好买家号、没有真实采购成功的任务补上指定（取任务主来源里最近一条表态且非空的记录；行上的单号是任务自己登记过的单号的那条不算；旧版存成「按没读到处理」的表格错误值还原成读不出的指定；写事件）；建表与回填在一个事务里，出错整体回滚；重复执行不再回填、不改数据。回填不触发分配，所以启动后要点一次「重新分配」（按钮只分登录的那个工作区：有多个工作区时每个各点一次，或运行一次 `python cli.py allocate`），让这些任务按指定落位；在那之前，领取时的复核保证它们不会被别的账号买走。从第一版升级会删掉它的配对表与几列旧字段，没有回退，所以先备份。
