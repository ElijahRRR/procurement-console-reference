# 参考插件执行逻辑（小蜜蜂 2.5.5）与本项目对照

整理于 2026-11-18。所有者要求先把参考项目的执行逻辑理顺，再改本项目的执行入口。本文是理顺的结果，也是「去掉配对码与设备绑定、按当前登录的买家号领任务」这次改造的依据。

## 一、结论

1. **怎么知道是谁**：没有登录、令牌、配对、绑定。人在亚马逊「订单历史」页点按钮时，`extractCustomerId` 用正则从当前页面 HTML 里现取 `customerId`，不缓存、不保存，也不核对登录状态。
2. **怎么拿任务**：把这个 `customerId` 当唯一参数请求 `getNeedPurchaseOrders`，一次拿回整批。没有领取、心跳、租约，每一次都是人点出来的。
3. **任务归属由什么决定**：由服务端订单行上写的买家号 ID 决定，不在插件里；插件从不核对任务是不是给自己的。「服务端按买家号 ID 筛选」是推断，筛选条件在客户端代码里看不到。
4. **怎么执行**：在订单历史页里用弹层 iframe 依次打开商品页、购物车、结算页。先清空购物车，再按服务端返回的顺序逐单：加购 → 购物车核对 → 结算 → 改地址 → 换支付卡 → 结算页校验 → 点下单 → 等结果 → 到订单历史读第一张订单卡。
5. **怎么回传**：成功走 `purchaseOrderFinishUpdate`；失败只有一部分路径走 `updateOrderStatus`（状态恒为 99，附文字原因），其余失败只写在抽屉的本地日志里，服务端不知情。回传只带任务的内部 id，不带 `customerId`。

对本项目的含义：

- **值得照做的是主线**：浏览器里登录着哪个买家号，就按哪个买家号领任务；不需要配对码，也不需要把设备和账号绑在一起。改造后的本项目就是这个模型（第七节）。
- **不能照搬的有三点**：每次点按钮都上传买家 Cookie；物流同步上传整页 HTML；程序流程不区分「取不到任务」和「没有任务」，回传只看 HTTP 状态不看业务码，重试没有幂等键（第八节）。
- **参考实现最薄的地方是「点了下单之后」**：下单前不向服务端做任何标记，本地也不留记录；已经下单但没回传成功的订单会不会被再买一次，完全取决于服务端（3.10）。本项目的提交登记、结果待核实、租约都是为了补这一段，这次改造原样保留。

怎么读这份文档：

- **对象**：`reference/smallbee-2.5.5/` 的 `manifest.json`、`js/popup.js`（主脚本）、`js/background.js`，以及 `docs/research/` 下三份调研笔记。
- **方法**：只读代码。主脚本分四段阅读，再由另一人逐条复核；没有安装或运行参考插件，没有访问它的服务端。
- **标注**：不加标注的句子都是代码里能直接确认的事实；「（推断）」是由代码或调研笔记推出来、没有运行验证的；「（未知）」是客户端代码里看不到的，多半是服务端行为。
- **写法**：引用代码写函数名；参考服务端只写接口路径名；界面与日志文案照原文引用。参考里的「拍单」就是本项目的「采购执行」，「买家号ID」就是 `customerId`，本项目叫「买家号 ID」。

## 二、入口与领取模型

### 2.1 注入范围与界面

- **只在订单历史页运行。** 清单的 `content_scripts` 只匹配美国、加拿大、日本三站的订单历史地址，共 10 个模式（`/your-orders/orders?*`、`/gp/css/order-history?*`、`/gp/your-account/order-history*` 等）。商品页、购物车、结算页、订单详情页都不注入：它们是主脚本在订单历史页里用同源 iframe 弹层（随包的 layer 3.1.1）打开的。
- **匹配比看上去窄。** 前两类模式要求地址带问号，不带查询串的订单页不会注入。带语言前缀的只覆盖日本站 `/-/en/gp/css/order-history?*` 一条，而抽屉对非美国站的提示偏偏是「为保证同步数据完整性，请将站点语言修改为英文」。
- **`all_frames: true`，而 `AppController.init` 不判断是不是顶层页面。** 地址匹配的 iframe 里也会各跑一份脚本、各建一套悬浮按钮。下单后打开的订单历史弹层地址不带问号，按原始地址不匹配；是否重复注入取决于亚马逊的重定向，代码无法确定。商品、购物车、订单详情弹层确定不会注入。
- **权限**：`storage`、`tabs`、`scripting`、`cookies`，主机权限 `*://*/*`。扩展自己的脚本实际只用到 `chrome.cookies.getAll`（后台脚本）和 `chrome.runtime.*`，前三个权限一处都没用；清单里没有 `web_accessible_resources`、`externally_connectable`。后台脚本只有一个「取 Cookie」的消息监听，没有调度，没有登录逻辑；弹出页只有两行静态说明。
- **启动时什么都不做。** `AppController.setupEventListeners` → `init` → `isAmazonOrderPage` 为真 → `UIManager.createFloatingElements` 建悬浮按钮「小蜜蜂」和右侧抽屉。不发请求，不读 `customerId`，不起任何定时任务。
- **抽屉**：按钮「开始同步」「开始拍单」「提取 customerId」「Amz To Jc轨迹同步」，加一个日志窗。没有账号选择、任务列表、停止按钮。
- **三项本地设置**存在亚马逊页面的 `localStorage`：只拍 N 天内送达（1–30，缺省 7）、允许使用礼品卡（缺省不允许）、支付卡尾号（留空用默认卡）。它们不上传服务端（送达天数只会出现在失败原因的文字里），按站点域名、按浏览器环境各存一份；用到时才读，所以批次进行中改了会影响后面的订单。

### 2.2 识别买家号：`extractCustomerId`

- 取当前页整页 HTML（`document.documentElement.innerHTML`），先匹配 `customerId: "…"`，再匹配 `customerId: '…'`，取第一处命中。JSON 写法 `"customerId":"…"` 不会命中。
- 四个按钮每点一次都重新取一次；结果不缓存，不写入任何存储。「提取 customerId」按钮只是把结果显示出来，不是其他按钮的前置步骤。
- 取不到：日志「未找到 customerId，两种格式都尝试失败」，调用方再记「请先提取 customerId」并结束，不发任何请求。这句话只在提取失败时出现，容易误读成要先点那个按钮。
- 代码不核对取到的值是不是当前登录的买家；全文件没有登录状态、登录页、验证码页的识别。
- 取到的值只用于拉列表和上传 Cookie，之后整批不再出现：逐单执行、结算、下单前都不复核当前登录的还是不是同一个买家。

### 2.3 拉任务：`ApiService.getPurchaseOrders`

- `GET /system/amazonOrder/getNeedPurchaseOrders?customerId=…`。请求里除了 `customerId` 没有任何凭据：不带令牌、设备标识、鉴权头。由内容脚本在亚马逊页面里直接 `fetch`，不经后台脚本，没有超时，没有重试。（推断：从亚马逊页面跨域请求，需要对方服务端放行跨域，这是浏览器通用行为，不是代码里写的。）
- 业务码 `data.code === 200` 才算成功，返回的数组原样使用，不校验形状。整批只拉这一次，循环中不再重拉。
- **取不到和没有任务走同一条程序分支。** 业务码不是 200，或网络、HTTP、JSON 出错，都返回空数组，随后显示「没有需要拍单的订单」。界面上只多一行日志：业务失败是标红的「获取拍单列表失败: …」（响应里没有原因时显示 undefined），异常是不标红的「获取拍单列表异常: …」。
- **紧接着上传 Cookie，而且在判空之前。** `sendBuyerCookie` 让后台脚本取出与当前页面地址匹配的全部 Cookie（含 HttpOnly 的值），`POST /system/amazonOrder/updateBuyerCookie`，请求体 `{customerId, country, cookie}`。任务为空、甚至拉任务失败时也照传。上传会被等待，挡住批次开始（最多试 3 次，间隔 1 秒、2 秒，请求本身没有超时），但结果不影响是否继续。失败时抽屉里最多出现两行不带上下文的「请求失败，第 N 次重试...」，最终 `ApiService.updateBuyerCookie` 自己吞掉异常，`sendBuyerCookie` 什么都不记（浏览器控制台里的「ck失败」只在别的环节抛错时出现）。
- 客户端从任务里读的字段：`id`、`orderNo`、`products[].asin`、`products[].quantity`，以及收件人姓名、国家、州、城市、区、地址、电话、邮编。没有读任何价格、限价或买家字段。

### 2.4 任务与买家号的关系

- 客户端代码里没有任何分配动作，也从不读取任务里的买家字段。
- 调研笔记记录的是：服务端订单行带 `buyerAccount`、`buyerCustomerId`；导入模板 15 列里有「买家号」「买家号ID」，两者不是一回事；网站端有修改买家号及其 ID 的接口 `updateBuyerInfo`；采购状态 0 待审核、21 待拍单、1 已拍单、99 拍单异常（网站上可以批量重置为待拍单）。
- （推断）服务端按订单行上的买家号 ID 过滤：订单上写着哪个买家号 ID，登录着这个买家号的浏览器来问，就给谁。依据是「唯一输入是 `customerId`」加「订单行带买家号 ID」加调研报告的原话，不是代码。
- （未知）是否只返回待拍单的订单；这次 GET 有没有给任务加锁、打标记或去重；服务端有没有别的来源限制或鉴权。调研时没有实际调用过这些接口。
- 客户端没有「领取」这一步：拉完列表之后，直到失败回报或成功回填之前，不再就这笔任务联系服务端；有些失败路径根本不回报。

### 2.5 页内锁与并发

- 互斥只有 `AppController.handlePurchase` 开头的 `window.purchaseBatchInProgress`，加上按钮置灰。它只是内容脚本窗口上的一个变量：刷新页面、另一个标签页、另一个浏览器都不受约束。
- 客户端没有任何机制阻止同一个买家号在两个标签页或两个浏览器里同时拉取并执行。两边会不会拿到同一份任务取决于服务端（未知）；（推断）服务端不防重的话就会重复下单。
- 两个同步入口既不检查也不设置这个标志，三个按钮各管各的，拍单进行中仍可以点同步。拍单批次结束时的 `layer.closeAll()` 会把同步正在用的弹层一起关掉。
- 没有停止按钮，没有总超时。任何一个不落定的等待都会让批次一直挂着：锁不释放，按钮一直置灰。

## 三、拍单批次流程

调用关系（缩进表示谁调用谁）：

```
UIManager.handleStartPurchase            点「开始拍单」
└ extractCustomerId → AppController.handlePurchase(customerId)
   ├ ApiService.getPurchaseOrders → sendBuyerCookie → 判空
   ├ clearShoppingCart                    批次开始先清车
   └ 逐单 AppController.processPurchaseOrder(order)
      ├ 逐个商品 processSingleProduct      加购
      └ processCartAndCheckout            购物车核对 → 去结算
         └ fillAddressInfo                改地址 → ensurePreferredPaymentCard 换卡
            └ verifyPageInfo / verifyPageInfoJp     结算页校验 → 点下单
               └ waitForOrderSuccess → openOrderHistoryPage → ApiService.updatePurchaseOrderFinish
```

下面每一步写「做什么」和「失败怎么处理」。失败只有两种去向：**上报 99**（`ApiService.updateOrderStatus`，请求体 `{orderId, status: 99, failContent}`）或**只写日志**（抽屉里的本地日志，服务端不知情）。完整清单见第五节。

### 3.1 清车：`clearShoppingCart`、`OrderProcessor.clearCart`

- **做什么**：用弹层打开购物车页，iframe 加载事件触发后固定等 2 秒就开始（没有就绪判断）：反复点第一个删除按钮，每点一次等 1 秒，直到找不到删除按钮；记「购物车清空完成」，再等 2 秒，置 `window.purchaseCartCleanupCompleted`，关弹层。
- **靠不住的地方**：找不到删除按钮就算清空成功，不核对购物车是不是真的空了；弹层里其实是登录页、验证页或没加载完的页面时，同样记成清空完成。循环没有次数上限，按钮点了不消失就一直转。layer 3.1.1 把弹层的 success 回调绑在 iframe 的 load 事件上：每次加载都会触发，而 `clearShoppingCart` 没有防重入，iframe 中途重载会并行再跑一遍；load 一直不触发时既不成功也不失败，批次挂住。
- **失败处理**：取不到 iframe、清车过程抛错、弹层在完成前被关（包括人手动点关闭）→ 失败抛给 `handlePurchase`，日志「拍单失败: …」，`layer.closeAll()`，**整批结束**。清车不向服务端发任何请求。

### 3.2 逐单循环：`AppController.handlePurchase`、`processPurchaseOrder`

- **做什么**：按服务端返回的数组顺序逐单处理，不排序、不过滤、不去重，也不核对任务是不是属于当前买家号。每单开始记一行日志（打印的是收件人姓名）。循环本身不向服务端发「开始处理」之类的请求。
- **单后收尾**：这一单没成功、且还没清过车，就再清一次；然后做下一单。单笔失败本身不停批。
- **中止条件**：代码里显式的中止路径有三条，全是清车失败：批次开头清车失败；`failPurchaseAndClearCart` 清车失败后置的 `window.purchaseCartCleanupFailed`（日志「购物车未能清空，为避免污染下一笔订单，已停止本次拍单任务」）；单后清车失败。列表为空是批次开始前的正常返回。循环里其他没被捕获的异常（例如数组里有空元素）也会中止整批。
- **没有总超时**：任何一个等待不落定，批次就卡死。人能主动打断的只有两种办法：手动关掉「清空购物车」弹层，或刷新、关闭页面（内容脚本的状态全丢，没有断点可续）。
- **批次结束**：`layer.closeAll()` 后一律记「拍单任务全部完成」，哪怕每一单都失败；没有成败统计，也不向服务端发任何汇总请求。
- **失败处理**：订单里没有商品 → 只写日志（随后循环仍会为这单清一次车）；`processPurchaseOrder` 抛异常 → 只写日志，继续下一单。

### 3.3 加购：`processSingleProduct`

- **做什么**：弹层打开当前站点的 `/dp/{asin}?th=1&psc=1`；`waitForProductPurchaseState` 最长等 60 秒，等到可用的加入购物车按钮；数量只靠下拉框选项来选（没有下拉框且数量为 1 时照常继续）；有优惠券就勾（这段只在有数量下拉框时才执行）；再确认一次按钮可用（上限 30 秒，按钮当下可用就立即返回，不保证改数量后的刷新已经完成）；点加入购物车；最长约 30 秒等地址变成购物车页。延保弹窗只尝试拒绝一次。
- **没有做的**：不选变体（尺寸、颜色），不核对页面上的 ASIN 是不是任务的 ASIN，不在商品页读价格或卖家。
- **失败处理**：上报 99 的原因有「商品无库存」「无法访问商品页面」「商品购买区域加载超时」「无法修改商品购买数量」「商品库存不足或已售罄」「商品购买区域刷新失败」「处理商品失败: …」。只写日志的有：加购后 30 秒没跳到购物车、商品弹层取不到或被提前关闭、弹层打不开。任一商品失败，这一单就跳过。
- （推断）人中途关掉商品弹层时，这一步立刻以失败返回，但已经在跑的异步流程不会停，之后仍可能对这笔订单上报 99，而批次那边已经开始清车。

### 3.4 购物车核对：`processCartAndCheckout` 前半

- **做什么**：弹层打开购物车，加载后固定等 3 秒就直接读页面（没有就绪判断）：有效商品行数必须等于任务的商品种数；逐个商品按 ASIN 找到购物车行，读页面上的数量与任务比对。
- **失败处理**：行数不符 → 就地清车，日志「…跳过当前订单，等待下一次执行」，只写日志。数量不符或读不到数量 → 只写日志。购物车里找不到某个 ASIN → 上报 99「商品 … 验证失败，请确认商品状态或库存是否充足」。页面 3 秒内没加载完时行数读成 0，订单被当成行数不符跳过，同样不上报。

### 3.5 去结算：`processCartAndCheckout` 后半

- **做什么**：点「去结算」，`Utils.waitForPageNavigation` 等 iframe 地址稳定（连续 3 次轮询不变）并落在预期页面；遇到中间页就点它上面的继续按钮；最终地址是结算页才调用 `fillAddressInfo`。
- **没有超时**：这两次等待传的最长时间是 0，即无限等。地址稳定在不含预期字样的页面（停在购物车，或跳到登录页）时永远不返回；iframe 变成跨域页面时读地址抛错，也继续轮询。等满 30 秒只记一次「结算页面跳转已等待超过30秒，将继续等待Amazon完成加载」。
- **失败处理**：找不到结算按钮、各种跳转失败、过程中抛错 → 全部只写日志，而且多数不关弹层（留到批次结束的 `layer.closeAll()`）。

### 3.6 改地址：`fillAddressInfo`、`selectShippingAddressAction`、`OrderProcessor.waitForAddressSave`

- **进入地址列表**：结算页上还没有地址列表（`getShippingAddressSection` 返回空）时，先点「更改地址」的入口，最长等 30 秒等列表出现。
- **选哪条地址**：买家账号里已有同国家的地址就**编辑它**（直接覆盖账号里那条地址），没有才新增。国家从已有地址文本的最后一个逗号分段识别，只认 US、JP、CA、CN、UK、DE、FR、IT、ES、AU 十个码；英国必须写 UK，写 GB 匹配不上。只要有一条同国家地址就直接编辑，不管其他地址认不认得出；反过来，没有同国家地址、而账号里有一条地址的国家认不出时，结果一直是「无法确定」，30 秒后跳过。
- **怎么填**：姓名、电话、地址、城市、邮编都是直接给输入框赋值再派发 input 事件，不判空，不做格式处理；表单里没有选国家的代码。州下拉框按选项的文字和值精确匹配（忽略大小写和空白）。日本站：地址行 1 是「城市 + 区」（缺区直接失败），地址行 2 是详细地址，邮编按「-」拆成两段，都道府县靠一张英文名到日文名的对照表（日文名比原样和去空白，英文名比原样和小写），表里的键带后缀（如 `Tokyo-to`），订单只写 Tokyo 不会命中。
- **保存**：点保存；出现校验提示就原样再点一次；出现「地址二次确认」就选原始地址再保存。`waitForAddressSave` 最长等 30 秒，只看结算页上的收货地址元素出没出现，不核对内容（内容核对在 3.8，而且只比邮编）。
- **失败处理**：上报 99 的有「地址列表加载超时」「地址信息不完整，缺少区相关信息」（日本站）「未匹配到洲信息，请检查订单」「地址保存超时」。只写日志的有：找不到更改地址的入口、无法确定选哪条地址、表单字段或保存按钮缺失、订单缺州、`waitForAddressSave` 里 iframe 失效或抛异常这两条分支、函数里任何没预料到的异常（例如日本站邮编为空）。
- **清车细节**：列表超时、州不匹配、保存超时这三条在上报后会再开一个弹层清车（叠在没关的结算弹层上面）；缺区那条不清。这些清车如果失败，异常被就地吞掉，不置失败标志；批次循环随后会再清一次，那一次再失败才中止整批。本函数自己的失败返回都不关结算弹层。

### 3.7 换支付卡：`ensurePreferredPaymentCard`、`failPurchaseAndClearCart`

- **做什么**：读本地设置的卡尾号（必须是 4 位数字，否则当作没设置）。没设置 → 不换卡；当前选中的卡尾号已经等于设置值 → 不换卡。否则依次：找支付方式切换入口（30 秒）→ 找到对应尾号的单选框并选中（30 秒）→ 点确认（10 秒）→ 回到结算页并确认尾号（30 秒）。
- **失败处理**：任何一步不成 → `failPurchaseAndClearCart`：上报 99（「未找到支付方式切换入口」「支付方式列表中未找到尾号 … 的信用卡」「指定支付卡未选中或支付方式确认按钮尚不可用」「支付卡切换后未能确认尾号 …」「切换支付卡时发生异常: …」），清车，最后关掉结算弹层。清车失败时置 `window.purchaseCartCleanupFailed`，这是全文件唯一置这个标志的地方（每个批次开始时复位），批次在这一单之后中止。

### 3.8 结算页校验：`verifyPageInfo`（美、加）与 `verifyPageInfoJp`（日）

美、加流程依次检查：

|检查|规则|不通过时|
|---|---|---|
|收货地址|结算页地址文本里包含任务的邮编。只比邮编子串，不比姓名、街道、城市；任务邮编为空时恒通过|只写日志|
|支付卡|本地设置了尾号时，页面选中的卡尾号必须相同；没设置就用亚马逊当前默认支付方式|上报 99，清车|
|商品|每件的 ASIN 在任务里；价格元素和图片存在（价格文本里取不到数字时按 0，不报错）；配送方式文本含 amazon，否则判为非 FBA|非 FBA 上报 99（不清车）；其余只写日志|
|件数|页面商品种数等于任务的商品种数。数量在这里没有读页面（比的是任务自己的值），页面数量只在 3.4 读过一次|只写日志|
|金额|页面订单总价（允许礼品卡且已抵扣时加回抵扣额）与「页面单价 × 任务数量」之和相比，差异超过 50% 才失败|上报 99，清车|
|送达时间|从各商品块的标题文字解析送达日期，取最晚的一条，距今天数超过 N（缺省 7）即失败|上报 99，清车|
|送达时间读不懂|选出的那条解析不了（或全部解析不了）时弹确认框「跳过 / 继续下单」，没有超时；页面上一条送达文字都没取到时不检查、不弹框，直接下单|选「跳过」上报 99|
|点下单|插件自己点下单按钮，点之前没有人工确认，也不向服务端发任何标记|找不到按钮只写日志|

- **金额校验不是成本保护。** 比的两边都来自页面，没有与任务的价格、预算、限价比较；全文件没有读过任何订单价格字段。单价文本在数字前先出现逗号时算出非数值，校验直接放行。美、加流程在「礼品卡已抵扣但设置不允许」时既不拒绝也不加回，直接拿抵扣后的总价去比。
- **送达时间解析（`parseDeliveryTime`、`parseExplicitDate`、`analyzeDeliveryTimes`）有多处会放行。** 以下结论是复核者用同样的正则在 Node 里实测的，没有运行插件：
  - 实际起作用的只有：`parseExplicitDate`（带年份的缩写月份、英文全月名加日）、today、tomorrow、完整英文星期名、不带年份的缩写月份加日、以及最后的 `new Date(文本)` 兜底；代码里另外几个分支走不到。
  - 文本里有完整星期名时按「下一个该星期」算，后面的月日不参与：两周以后的「Arriving Saturday, Dec 6」也会通过。
  - 不带年份的区间「Nov 20 - Nov 25」取起始日。
  - 不带年份的日期只会落在今年或去年：晚于「现在 + 1 个月」就改成去年，于是一个月以后或跨年的日期被算到过去，直接通过。天数限制只在「同一自然年且一个月以内」有效。
  - 英文全月名带年份（January 12, 2026）被解析成今年 1 月 1 日，不报错也不弹确认框。
  - 兜底会把「Arriving 20 Nov」这类文本解析成 2001 年的日期，同样通过。
  - 多条送达文字里只要有一条能解析，其余解析不了的被静默丢掉。
  - 时区：只有不带年份的缩写月份会多算时差。北京时间的浏览器开美国站，7 天后的日期算成 8 天（实测条件是站点时间上午 10 点），被 7 天限制误拦，回传的送达日期也晚一天；浏览器与站点同时区时没有偏差。
  - 回传用的送达日期是在订单历史页打开时用当时的时间重新解析的：人工验证拖过站点午夜后，today、tomorrow、星期名的结果会后移。
- **日本流程的差异**：先无限期等人亲手点一次下单按钮（提示只出现在插件日志里）。`waitForButtonClick` 只拦这第一次点击（阻止默认行为和冒泡后就移除自己，按钮上别的监听仍会执行），显示遮罩「正在验证订单信息，请稍候...」后才开始校验；全部通过后由插件再点一次下单。礼品卡已抵扣而设置不允许时明确失败。**没有任何金额校验**，读成 0 的单价会一路带到回传。

### 3.9 等结果：`waitForOrderSuccess`

- **做什么**：每秒读一次结算弹层的地址，没有超时。地址是感谢页，或者是购物车页，都算下单成功。读地址时发现 iframe 已跨域，就当作银行卡安全验证：日志提示人工完成验证，一直等。等满 30 秒只记一次「…不会判定下单失败」。
- **没有做的**：不读结算页上的任何错误提示（拒付、库存变化等），不从感谢页读订单号。
- **失败处理**：唯一的出口是人关掉结算弹层 → 记「下单失败」，只写日志，批次清车后做下一单。如果订单其实已经在亚马逊提交，服务端不会知道。

### 3.10 回传：`openOrderHistoryPage`、`ApiService.updatePurchaseOrderFinish`

- **做什么**：关结算弹层，弹层打开订单历史页，最长等 15 秒等订单卡片出现，取**第一张**卡：读亚马逊订单号、商品链接里的 ASIN、收货邮编。代码没有用 ASIN、下单时间或地址去确认这张卡就是刚下的那一单。
- **回传内容**：`POST /system/amazonOrder/purchaseOrderFinishUpdate`，请求体有任务 id、亚马逊订单号、ASIN 列表、送达日期（格式化后的与原文各一份）、支付方式（卡尾号，或字面量「礼品卡」「Amazon默认支付方式」）、邮编、运费、税前金额、税、总额（页面原始文本）、商品明细（来自结算页）。最多试 5 次（间隔 1、2、4、8 秒），原样重发，没有幂等键；只要 HTTP 成功就记「拍单完成信息更新成功」。订单历史卡片上的 ASIN、结算页的商品明细、任务里的商品三者之间不做任何比对。
- **已经下单之后的几种结局**：

|情形|插件做了什么|服务端看到什么|
|---|---|---|
|订单卡片 15 秒没出现|上报 99「回传订单失败，请手动复制AMZ订单号回填至系统」，然后直接返回：不关弹层，等待永不结束，批次挂住|一笔「拍单异常」，而订单其实已下|
|没读到订单号或 ASIN|只写日志，这一单照样算成功|什么也没收到|
|回填 5 次都失败|只写日志「拍单完成信息更新失败」，这一单照样算成功|什么也没收到|
|等结果时人关了结算弹层|记「下单失败」，清车，做下一单|什么也没收到|
|点下单后页面跳回购物车|当成下单成功，把订单历史第一张卡（别的订单）的单号回填给这一单|一条错的成功|

- 插件本地不留已下单记录（`localStorage` 只有三项设置）。这些订单会不会再次出现在待拍列表里，完全取决于服务端。调研笔记指出 99 可以被批量重置为待拍单；（推断）重置前不先查单就会重复采购。

## 四、订单同步与轨迹同步

两个入口都是手动：「开始同步」（`UIManager.handleStartSync` → `AppController.handleOrderSync` → 逐单 `processOrder`）和「Amz To Jc轨迹同步」（`handleStartSyncTracking` → `handleOrderSyncTracking` → 逐单 `processOrderTracking`）。

- **共同点**：先 `extractCustomerId`，再按 `customerId` 拉列表（`/system/amazonOrder/getNeedSyncOrders`、`/system/amazonOrderPig/getNeedSyncOrders`），逐单串行，单与单之间等 1 秒。拉列表不重试，也不看业务码：HTTP 成功但业务失败时直接显示「没有需要同步的订单」，连一行错误日志都没有。没有页内锁，只靠按钮置灰。整个循环只有一层异常处理，任何一单抛错，后面的订单都不再处理。
- **Cookie**：「开始同步」在拉列表之后、判空之前同样调用 `sendBuyerCookie`；轨迹同步不调用。

|项目|订单同步 `processOrder`|轨迹同步 `processOrderTracking`|
|---|---|---|
|打开什么|弹层打开订单详情页，再打开第一条物流链接|任务带物流链接时直接开物流页，不开详情页，也不做取消、退货判断；不带时与订单同步相同|
|状态上报|已取消、已退货 → 91；订单不存在、物流页无物流信息 → 92|已取消、已退货 → 91；无物流信息 → 92；没有「订单不存在」判断|
|成功上传|`/system/amazonOrder/updateTrackingInfo`：运单号、物流链接、`trackingHtml`、轨迹 JSON、邮编、卡尾号、ASIN、下单日期、运费、税前金额、税、总额、承运商、签收照片地址、送达日期|`/system/amazonOrderPig/updateTrackingInfo`：运单号、物流链接、`trackingHtml`、首条轨迹时间、邮编、卡尾号、轨迹 JSON|
|跳过规则|无|轨迹不超过 1 条且 `logisticsType !== 3` 时不上传（严格比较，服务端下发成字符串时条件恒成立；3 的含义代码里没有说明）|

- **状态上报**两条流共用 `/system/amazonOrder/updateAmzOrderStatus`，请求体 `{orderId, orderNumber, amzStatus}`。`getOrderStatusText` 与 `isCancelledOrderStatus` 也是两条流共用。91、92 在代码里没有名字，含义只能从旁边的日志看；92 同时表示「订单不存在」和「无物流信息」，服务端分不出来。
- **整页 HTML**：`extractTrackingInfo` 这条路径（订单同步，以及不带物流链接的轨迹同步）上传的 `trackingHtml` 是物流页整页（`documentElement.outerHTML` 加上页面能读到的样式规则，不压缩）的 Base64。带物流链接的轨迹同步走 `extractTrackingInfoByPlatformTrackUrl`，（推断，按代码字面，未运行验证）上传的是字面量 `<!doctype html>` 换行加 `null` 的 Base64，不是页面。订单详情页的 HTML 不上传，只上传抽出的字段。
- **只取第一个包裹**：详情页上的物流链接去重后只处理第一条，多包裹订单的其余链接不处理。
- **上传前不校验读到了什么**：运单号、承运商可以是空值，金额、邮编、卡尾号没读到时是空字符串。下单日期与各金额是页面原始字符串；送达日期经 `formatDeliveryTime` 处理（空值变成字面量「未知」，能解析时是 YYYY-MM-DD，否则原文），原文另放一个字段。`subtotal` 字段从未被赋值；`total before tax` 与 `item(s) subtotal` 写进同一个字段，后出现的覆盖先出现的。
- **语言覆盖**：日文在取消判断和 `extractOrderInfo`（下单日期、运费、请款额、卡尾号、邮编）里有覆盖；法文只在取消判断里有。退货、订单不存在、物流页的运单号和无物流提示只认英文文案，税额和税前合计的标签也只有英文。
- **等待与卡死**：
  - 详情页是否可用的判定没有超时。三种情况下等待永不结束，整条同步流停在这一单：iframe 的加载事件不触发；iframe 落到跨域地址（推断）；iframe 文档里取不到 body。
  - 详情页被重定向或没有订单区块时，这一单静默跳过，没有日志也没有上报；代码不区分那是登录页还是验证码页。（推断）每个被这样跳过的订单会留下一个不会停的定时器。
  - `extractTrackingInfo` 每 2 秒查一次，总上限 300 秒；连续 10 次页面为空就跳过（推断：约等于打开后 18 秒）。页面有内容、但既没有物流元素也没有异常或无物流提示时，要等满 300 秒。
  - `extractTrackingInfoByPlatformTrackUrl` 不要求页面上有物流元素：任何非空页面都算加载完成，运单号可以为空，`logisticsType` 等于 3 时照样上传；（推断）它实际只有打开后约 5 秒时的一次检查机会。它用到的 `updateEventsTimeInHTML` 只在入参为空、找不到事件容器或抛错时返回原 HTML，其余情况返回重新序列化的整页；它所在的延迟分支按代码字面走不到。
- **失败回报**：只有 91、92 两种状态上报和成功上传。找不到物流链接、超时、解析失败、详情页不可用都只写日志或静默返回。日志里的「保留订单状态，下次同步重试」对应的代码行为只是这次不联系服务端，下次会不会再下发取决于服务端（未知）。上传失败（试满 3 次）不抛错，调用方也不看返回值，流程上与上传成功没有区别。

## 五、失败与回报一览

### 5.1 回报通道

|接口路径|什么时候调用|请求体要点|最多尝试|
|---|---|---|---|
|`/system/amazonOrder/purchaseOrderFinishUpdate`|下单成功，且读到了订单号和 ASIN|任务 id、亚马逊订单号、金额、支付方式、商品明细|5 次|
|`/system/amazonOrder/updateOrderStatus`|拍单的一部分失败路径|`{orderId, status: 99, failContent}`|3 次|
|`/system/amazonOrder/updateAmzOrderStatus`|同步时发现取消、退货、不存在、无物流|`{orderId, orderNumber, amzStatus: 91 或 92}`|3 次|
|`/system/amazonOrder/updateTrackingInfo`、`/system/amazonOrderPig/updateTrackingInfo`|同步读到物流信息|抽取的字段加 `trackingHtml`|3 次|
|`/system/amazonOrder/updateBuyerCookie`|每次点「开始同步」「开始拍单」|`{customerId, country, cookie}`|3 次|

共同特点：

- 除 Cookie 上传外，回传都不带 `customerId`，只凭任务 id；所有请求都没有鉴权头（`ApiService.request` 只加 Content-Type）。
- 成败只看 HTTP 状态和响应能不能解析成 JSON，不看业务码。服务端回 HTTP 200 加业务失败时，`updateOrderStatus` 照样记「订单状态更新成功」。检查业务码的只有 `getPurchaseOrders`。
- `Utils.retry` 对任何异常都重试（包括 HTTP 4xx 和 JSON 解析失败），间隔从 1 秒起翻倍，原样重发，没有幂等键或尝试号。日志里的「已重试 N 次」其实是总共尝试 N 次。最终失败只记日志，流程照常往下走。响应体恰好是 JSON 的 null 时，`updateOrderStatus` 会把已经送达的请求记成失败并重发。
- 没有任何中间状态：全文件 18 处 `updateOrderStatus` 调用的状态都是 99，没有「开始执行」「已领取」「已提交」。

### 5.2 拍单：哪些失败上报，哪些只写本地日志

|阶段|上报 99（`failContent` 原文）|只写本地日志|
|---|---|---|
|取任务|—|`customerId` 取不到；拉列表失败（当成没有任务）|
|订单本身|—|订单无产品信息；处理过程抛异常|
|加购|商品无库存；无法访问商品页面；商品购买区域加载超时；无法修改商品购买数量；商品库存不足或已售罄；商品购买区域刷新失败；处理商品失败: …|加购后没跳到购物车；商品弹层取不到、打不开或被提前关闭|
|购物车核对|商品 … 验证失败，请确认商品状态或库存是否充足|行数不符；数量不符或读不到；无法访问购物车页面；核实过程抛异常|
|去结算|—|找不到结算按钮；各种跳转失败|

从客户端看，只写日志的任务在服务端的状态没有变化。日志原话「跳过当前订单，等待下一次执行」说明作者的预期是下次点按钮时再拉到这一单；服务端是否真的再次下发，代码里看不到（未知）。在下单按钮已经点过的那几条路径上，这就是重复采购的口子。

### 5.3 需要人动手的地方

1. 银行卡安全验证：日志提示人工完成，插件无限期等待。
2. 送达时间解析不了：确认框「跳过 / 继续下单」，没有关闭按钮，没有超时。
3. 日本站：要人亲手点一次下单按钮来触发校验，提示只在插件日志里，结算页上没有。
4. 订单卡片加载超时：发给服务端的失败原因写的是「请手动复制AMZ订单号回填至系统」。这不是界面提示，是给后台看的。
5. 下单后页面卡住：人关掉结算弹层是结束等待的唯一办法。

### 5.4 日志

日志只写进抽屉，每条带本地时间，只有 error 类型标红；最多保留最近 20 条，不持久化，不上传。批次一长，前面的失败原因就滚没了。

## 六、参考插件里没有的东西

以下各项都经过全文件搜索确认：

- **登录、令牌、鉴权头、配对、设备标识、买家号绑定**：token、authorization、bearer、login、password、绑定、配对、deviceId、uuid、`chrome.storage` 都是 0 处。
- **领取与执行权**：没有领取、开始、心跳、租约、尝试号、幂等键；没有「开始执行」「已提交」之类的中间状态。
- **自动触发**：没有启动时的请求，没有用来拉任务的定时器或轮询，后台脚本没有调度；页面刷新后没有任何可恢复的批次状态。
- **归属核对**：不读任务里的买家字段；批次进行中不复核当前登录的买家。
- **登录页、验证码页的识别**：signin、captcha、验证码、登录都是 0 处。
- **对照订单价格的校验**：没有读过任何价格、限价、预算字段；日本流程连页面自洽的金额校验都没有。
- **商品页核对**：不选变体，不核对页面 ASIN，不读价格和卖家。
- **下单保护**：下单前不向服务端做标记，本地不留已下单记录，不从感谢页读订单号。
- **控制手段**：没有停止或暂停按钮，没有总超时，没有成败统计，没有持久化日志。
- **互斥**：拍单与同步之间没有，跨标签页、跨浏览器也没有。
- **多包裹**：只处理第一条物流链接。

另外有几处容易误读的死代码和过期文案：`isPurchaseSupported`、`CONFIG.UI.layerConfig`、文件末尾的 `retryRequest` / `compressHTML` / `clearLogOutput`、`TimezoneUtils` 里的几个太平洋时间换算函数只有定义没有调用；「拍单目前仅支持美国站点，其他站点请等待开放」在当前配置下走不到（三站都已开放）；接口配置键与使用它的函数名是交叉的（键 `updateOrderTracking` 由 `ApiService.updateOrderTrackingInfo` 使用，键 `updateOrderTrackingInfo` 由 `ApiService.updateOrderTrackingInfoPig` 使用），对照时别按名字配对。

## 七、与本项目逐项对照

「本项目做法」写的是 2026-11 执行入口改造之后的做法，细节以 [开发契约 v2](开发契约-v2.md) §4、§5 为准。本项目本阶段只做模拟执行：登记、心跳、批次、领取、护栏、提交登记、结果、回执这套协议是真的，亚马逊页面上的加购、结算、下单流程还没有迁入，所以「购物车清理」一行写的是协议层已有的约束。

|项目|参考做法|本项目做法|为什么不同或相同|
|---|---|---|---|
|身份识别|点按钮时 `extractCustomerId` 对整页 HTML 取第一个 `customerId: "…"`；不看登录状态；取一次后整批不复核|插件从导航栏读登录状态，买家号 ID 只在页面的内联脚本里找（含参考的两种写法），所有形状合格的匹配必须是同一个值，否则当作没读到；同一浏览器的多个亚马逊标签页读数不一致时上报不一致、不开始。随心跳或 `POST /plugin/v1/identity` 上报，服务端清洗（形状不对当作没读到，不报错），超过 10 分钟没上报算过期。开始批次、领取、进度、提交登记时都按最新上报复核，结算页事实里再带一次买家号 ID（护栏的买家号一项）|**主线相同**：身份就是页面上的 customerId，不靠配对或绑定。**不同**：对整页取第一处命中，商品标题、输入框里出现同样的字样就可能读错；参考不看登录状态，中途换了买家号也不知道。本项目要保证的是「下单那一刻登录的还是这个买家号」|
|任务领取与归属|`GET getNeedPurchaseOrders?customerId=…` 一次拿回整批，按返回顺序做；归属写在服务端订单行上（推断按买家号 ID 筛选）；客户端不核对，也没有领取动作|所有者在控制台登记账号并填买家号 ID；没登记过的 ID 由插件发现后列在「待登记的买家号」里，点一次「登记」即可，插件不自动建账号。任务由服务端按规则分配给账号（金额区间、每日额度、优先级）。插件 `POST /plugin/v1/runs {customer_id, …}`，服务端在这个浏览器所属工作区里找登记了该 ID 的账号并开批次，没登记则拒绝（`ACCOUNT_NOT_REGISTERED`）；之后 `POST /runs/{id}/next` 一次领一笔，领取时再校验日期、额度、金额区间|**相同**：谁登录着这个买家号，谁就能执行它的任务，与哪台电脑、哪个浏览器无关。**不同**：参考靠导入表格时逐单写买家号，本项目由服务端分配；一次只领一笔，是为了让取消、改价、暂停在下一笔之前生效，并让服务端始终知道哪一笔在途|
|信任边界与鉴权|请求里只有 `customerId`（拉列表）或任务 id（回传），没有任何凭据；服务端是否另有限制未知|`/plugin/v1/*` 只接受本机回环对端，Host 必须是本机名，拒绝网页来源的请求，POST 只收 JSON。浏览器自动登记，没有人工步骤；设备令牌只是会话标识（把批次、尝试、回执归到同一个浏览器），不代表身份。跨机器部署要另加接入密钥，本次不做，服务端直接拒绝非本机的插件请求|**不同**：知道一个 customerId 就能领任务，放在公网上等于没有鉴权。本项目把边界放在「本机」：能访问本机端口的程序视为所有者自己，所以可以不要配对码，也不必逐台审批|

|购物车清理|批次开始先清空；失败的订单做完后再清；清车失败就中止整批。但找不到删除按钮就算清空成功，固定延时后直接读页面，不核对是否真的空了，循环没有上限|本阶段只做模拟执行，不操作购物车。协议层已有的约束：结算页事实里的商品必须恰好一项，且 ASIN、数量与任务一致（护栏，`ITEM_MISMATCH`）；任务级错误码 `CART_MISMATCH`（购物车内容与任务不一致，任务转异常）。真实页面流程在后续 PR 迁入|**思路相同**：上一单的残留不能带进下一单，清不干净就停。**不照搬**：把「读不到」当成「已清空」。迁入真实流程时的建议见第八节|

|提交后的处理|点下单前不做任何标记；等结果只看地址（跳回购物车也算成功），没有超时；到订单历史取第一张卡当作新订单；已下单但回传不成时，服务端要么不知情，要么收到 99（可被重置为待拍单）|点击下单前必须先 `POST /attempts/{id}/submitting` 登记成功；登记之后的任何非成功结局都进「结果待核实」并暂停账号，绝不自动重买。银行验证有单独的等待状态。结果先在本地存成回执再发，发不出去就补交，迟到的回执照收。同一个亚马逊订单号只能记在一笔成功的真实尝试上。本阶段只模拟，服务端拒绝非模拟批次，模拟结果不写回飞书|**不同**：这是重复下单风险最大的一段，参考实现把它留给了服务端和人工。本项目宁可停下来等人核实，也不猜|
|失败回报|一部分失败走 `updateOrderStatus`（恒为 99 加自由文本），其余只写本地日志（最多 20 条，不留存）；只看 HTTP 状态；重试没有幂等键|每一笔尝试都有结局：插件 `POST /attempts/{id}/result` 上报结果和统一错误码（任务级、账号级、重试一次、中止、护栏拦截），后果由服务端决定（任务转异常、回已分配、暂停账号、结果待核实）；插件没回话的由租约过期清扫收尾。同一份结果重复上报不重复生效；每一步写事件|**不同**：「没回报就等下次再拉到」在本项目不成立，任务不会因为插件没说话就悄悄回到队列里再做一遍|

|站点与注入范围|美、加、日三站的订单历史页，`all_frames: true`；其他页面靠 iframe 弹层打开|首期只做美国站；内容脚本只在 `https://www.amazon.com/*` 的顶层页面运行，面板在任意亚马逊页面可见；没读到买家号 ID 时提示打开订单页|**部分相同**：订单历史页的内联脚本里有 customerId，两边都靠它。**不同**：本项目不要求人恰好停在那一页|

## 八、不能照搬的点与本项目的取舍

**不做的（与项目约定直接冲突）**

1. **上传 Cookie。** 参考插件每次点「开始同步」「开始拍单」都把买家的登录 Cookie 发给服务端。从代码看这一步与按 `customerId` 拉任务互相独立，去掉它不影响领任务。本项目不申请 `cookies` 权限。
2. **上传整页 HTML。** 本项目只上报字段；以后做物流同步也一样。
3. **反检测、验证码处理。** 参考里没有这类代码，本项目也不加：遇到验证码或登录页即按账号级错误暂停该账号，转人工。

**改掉的（参考实现的缺口）**

4. **无鉴权的「凭 customerId 拉任务」。** 参考服务端是否另有限制未知；自建系统必须自己回答「谁有资格拿这个 ID 来领」。本项目的回答是：只有本机上的程序（`/plugin` 入口闸），而且这个 ID 要先在控制台登记成账号。
5. **不区分「取不到」和「没有」。** 本项目的面板把连不上服务端、未登录、没读到买家号 ID、标签页读数不一致、未登记、已忽略、没有任务分别说清，各有各的下一步。
6. **回传只看 HTTP 状态、重试没有幂等键。** 本项目用统一错误码；结果重复上报不重复生效；只对可以重复的请求重试，提交登记不重发。
7. **提交之后没有保护。** 本项目保留提交登记、结果待核实、暂停账号、不自动重买，这次改造一处不动。执行中换了买家号的处理也按这条线分开：未提交的那一笔中止并回到已分配，不暂停账号；已提交的照常收结果。
8. **批次只锁在页面里。** 本项目由服务端按账号和浏览器各保证只有一个未结束批次。
9. **校验和设置都在插件里。** 本项目的护栏和配置都在服务端，插件只读事实、显示服务端确认过的配置。

**迁入真实页面流程时要注意的（建议，尚未定稿）**

本阶段只做模拟执行，下面几条是把参考流程迁进来时不该照抄的写法，具体做法留到那个 PR 定：

10. **把读不到当成通过。** 找不到删除按钮就算购物车已清空、价格取不到数字按 0、送达文字没取到就直接下单、邮编为空恒通过。本项目的规则是没读到的值保持为空并拦截（铁律 7）。
11. **固定延时后直接读页面、无超时等待。** 每一步都要有就绪判断和超时，并落到明确的错误码，不能让批次挂住。
12. **把订单历史第一张卡当成新订单。** 应当用商品、时间等信息确认是刚下的那一单；确认不了就进结果待核实。
13. **覆盖买家账号里已有的同国家地址。** 这会改掉账号原有的地址簿，是否接受需要所有者拍板。
14. **送达日期的解析。** 参考实现的写法在跨月、跨年、带星期名时会放行，不能复用；日期读不可靠就拦截。

**值得保留的**

- 按当前登录的买家号领任务，不配对、不绑定（已采纳）。
- 一次只做一单，按顺序做；上一单的残留清不干净就停，不污染下一单。
- 银行卡验证时不判失败，等人处理（本项目对应「等待验证」状态，名额与任务都保留）。
- 到订单历史页去读 `customerId`（本项目在别的页面没读到时，面板提供「打开订单页」）。
